# Розгін Symbian 9.2 / OMAP 2420: що встановлено

Еталон — Nokia N95 8GB (RM-320), прошивка 35.0.001. Джерела: дизасемблювання
ROM-образу з `../eka2l1/data/drives/z/rm-320/` та заміри на живому апараті
через `SymbianDeployDaemon`.

Файл поповнюється; кожен пункт або підтверджений на апараті, або виведений
із коду ROM — здогадки позначені явно.

> Контекст і межі — `docs/SCOPE.md`. Стисло: це homebrew на **власному**
> розблокованому апараті; технічні терміни нижче (kernel write, patcher,
> реєстр хешів dev-збірок) стосуються модифікації свого пристрою, не чужого.

## 1. Контекст: усі публічні «розгони» Symbian — фейк

- Правка `C:\private\10202be9\20001079.txt` (значення 332) — це конфіг N-Gage,
  до частоти стосунку не має.
- «OC-патчі» для ROMPatcher міняють текстовий рядок МГц у DLL.
- Утиліти на кшталт Todo Speed / Quokie дають ~1% на бенчмарку — ефект
  вивільненої RAM після рестарту.

Апаратний запас при цьому реальний: N800 на тому ж OMAP2420 стартував на
330 МГц і перейшов на штатні 400 МГц з оновленням OS2008; N810 має 400 МГц
серійно. Тобто кремній на 400 МГц розрахований.

## 2. Прошивка містить повний kernel-side DVFS

| Модуль | Роль |
|---|---|
| `dvfs_interface.ldd` | єдина точка входу з користувацького боку |
| `dvfs_engine.dll` | губернатор; політики `AVGn`, `AVGn 2`, `MAW`, `New Thread` |
| `dvfs_hal.dll` | квантування рівнів, читання PRCM |
| `dvfs_conf.dll` | сповіщення до/після зміни, напруга через Menelaus |
| `dvfs_monitor.dll` | збір навантаження |

Усі мають UID2 = `0x100000AF`, тобто це kernel-side модулі.

## 3. Користувацький доступ до DVFS: є, але розгону не дає

Зареєстроване ім'я каналу — **`dvfs_interface`**. Рядок `DVFSInterfaceDriver`
всередині `.ldd` — це назва фабрики; спроба відкритись по ній дає `KErrNotFound`.
Точне ім'я отримано переліком `TFindLogicalDevice` на апараті.

```
DoCreate("dvfs_interface", TVersion(0,0,0)) -> KErrNone
```

Достатньо capability-набору `PowerMgmt WriteDeviceData ReadDeviceData
ReadUserData WriteUserData ProtServ`. `GetCaps` віддає 64 нульові байти.

### Розкладка повідомлень (`HandleMsg` @`0x80148698`)

| `iValue` | Дія |
|---|---|
| `0x80000000` | закриття каналу |
| `< 0` | `DoRequest`, номер = `~iValue` → `0x80148638` |
| `>= 0` | `DoControl` → `0x80148428` |

### `DoRequest(0, status, a1, a2)` → `SetPerformance` @`0x80148460`

```asm
cmp r2, #50          ; r2 = a2. a1 НЕ читається взагалі
> 50  -> ++count; якщо перший -> mov r0,#66 ; виклик power.dll
<= 50 -> --count; якщо впав до нуля -> зворотний виклик
```

Це **бінарна засувка, а не задавач частоти**. Рівень зашитий константою 66.
Розгін через цей інтерфейс неможливий у принципі.

Перевірено на апараті: `reserve(100)` і `release(0)` обидва повертають 0,
частота 322 → 324 → 324 МГц, тобто в межах шуму.

### `DoControl(1, a1)` — читання частоти

```asm
mov r0, #1 ; bl <power.dll 0x800B15DC>   ; GetClockFrequency(MPU)
ldr r1, <3300000> ; b <ekern uidiv>      ; поділити
```

Повертає `частота_МПУ_Гц / 3 300 000`, тобто відсоток від номіналу.
Інші опкоди повертають 0.

### Рівні квантуються до двох (`dvfs_hal` @`0x80146520`)

```asm
sub r0,r0,#1 ; cmp r0,#100 ; bcc   -> дійсний діапазон 1..100, інакше KErrArgument
r2=1: r0 = 50*r2 ; if (perf <= r0) return r0 ; ++r2 ; while (r2 <= 2)
```

`perf 1..50 → 50`, `perf 51..100 → 100`. **Робочих точок рівно дві.**
Зашите значення 66 квантується в 100.

## 4. Хто програмує частоту

Відображення периферії: **віртуальна = фізична + `0x7E000000`**. Підтверджено
двома незалежними влучаннями: `0xC6008240` → `0x48008240` (CM_CLKSEL1_CORE) і
`0xC6028028` → `0x48028028` (GPTIMER1 TCRR).

`kaomap.dll` — це `AsspRegister`, самі примітиви доступу:

```
+0xE8  ldr r0,[r0] ; bx lr     Read32
+0xF0  str r1,[r0] ; bx lr     Write32
+0xF8  Modify32 (з забороною переривань)
```

**PRCM володіє `power.dll`** (codeAddr `0x800A7C98`) — 112 посилань на весь
регістровий файл `0x48008xxx`. Уся DVFS-надбудова лише читає.

### Формат CM_CLKSEL1_PLL (`power.dll` @`0x800B1544`)

```
DPLL = sys_clk * mult / (div + 1)
```

| Поле | Біти |
|---|---|
| множник `mult` | [21:12] |
| дільник `div` (ділити на `div+1`) | [11:8] |
| вибір `sys_clk` | [25:23] → 0 = 19.2 МГц, 2 = 13.0, інакше 12.0 |

Функція спершу перевіряє `CM_CLKEN_PLL & 3 == 3` (DPLL у lock-режимі),
інакше повертає 0.

### Решта ланцюга

- `power.dll` @`0x800B15B0`: core = DPLL × `CM_CLKSEL2_PLL[1:0]`
- `power.dll` @`0x800B15DC`: `GetClockFrequency(id)`; для `id==1` віддає
  MPU = `core / CM_CLKSEL_MPU[3:0]`, у герцах

### Карта важелів

| Регістр | Фізична | Поле | Дія |
|---|---|---|---|
| CM_CLKSEL1_PLL | `0x48008540` | [21:12] / [11:8] | множник / дільник DPLL |
| CM_CLKSEL2_PLL | `0x48008544` | [1:0] | множник core від DPLL |
| **CM_CLKSEL_MPU** | `0x48008140` | **[4:0]** | **дільник лише MPU**; допустимі 1,2,4,6,8 |
| CM_CLKEN_PLL | `0x48008500` | [1:0] | режим DPLL |
| PRCM_CLKCFG_CTRL | `0x48008080` | [0] | фіксація конфігурації |

> **УТОЧНЕНО 2026-08-08.** Поле `CM_CLKSEL_MPU` - **[4:0]**, а не [3:0]: сеттер
> `power.dll @0x800AC410` кличе `Modify32` з маскою `0x1F`. Допустимі значення
> дільника - **1, 2, 4, 6, 8**; таблиця переходів @`0x800AC3D0` відкидає 0, 3,
> 5, 7. Тобто дільника 3 на цьому SoC не існує, хоч поле його й вмістило б.

`dvfs_conf.dll` перемикає рівні записом `1` (100%) або `0` (50%) у
`0x4805A018` плюс запис у Menelaus; ревізію кремнію читає з `0x48014220`, біт 17.

## 5. Абсолютні числа

`dvfs_conf` порівнює `GetClockFrequency(1) / 3300000` зі `100` і з `50`.
Отже **100% = 330 МГц рівно, 50% = 165 МГц**.

Незалежний замір на апараті (ланцюг незалежних `add`, ARM1136 = 1 такт на
інструкцію) дав 323–324 МГц при припущених 258 тактах на ітерацію; при
фактичних ~263 це і є 330 МГц. Сходиться.

**`HAL::Get(ECPUSpeed)` бреше**: стабільно повертає 206438 kHz незалежно від
реального стану. Не спиратись на нього — зокрема й у PS1Emulator.

Базова лінія приладу (`ocprobe`): ALU 17.05 Mitr/s, пам'ять ~510 MB/s.
Під 30 с безперервного навантаження частота не змінюється — губернатор уже
тримає максимум.

## 6. Куди йти по розгін

Два важелі, з різним профілем ризику:

- **`CM_CLKSEL_MPU[3:0]`** ділить лише ядро, не чіпаючи L3/SDRAM/DSP. Але це
  цілочисельний дільник: якщо зараз /2, наступний крок /1 подвоює частоту.
  Проміжних значень немає — гріх занадто грубий.
- **Множник `CM_CLKSEL1_PLL[21:12]`** дає дрібний крок (кожна одиниця ≈ +1.9 МГц
  на DPLL), але тягне за собою core, L3 і SDRAM, тож потребує перевірки
  таймінгів SDRC.

Перед вибором потрібно **прочитати поточні значення** цих регістрів, щоб знати
фактичний розклад `sys_clk × mult / (div+1) / core_sel / mpu_div`. Читання —
kernel-mode; кандидат на інструмент — драйвер RomPatcher+.

## 7. Інструмент для kernel-mode доступу: `TestPowerAPI`

### RomPatcher+ — шлях виявився дорогим

`dumpsis -x RomPatcherPlus_3.1.sisx` дає три драйвери: `patcher.ldd`,
`patcherShadow.ldd`, `patcherS3.ldd`. Усі стиснуті `KUidCompressionDeflate`
(`0x101F7AFC`), а Symbian-івський deflate **не сумісний із zlib** — власна
реалізація Хаффмана. `System.IO.Compression.DeflateStream` не бере за жодного
зміщення заголовка; `petran`/`elftran` приймають на вхід лише PE/ELF, а не
готовий E32. Щоб піти цим шляхом, довелось би реалізувати Symbian-inflate.

### Кращий кандидат уже в ROM

`d_powerapi.ldd` — зареєстроване ім'я **`TestPowerAPI`**, 2516 байтів,
нестиснений (ROM-образ), у списку завантажених його немає, але він лежить у
`Z:\sys\bin` і вантажиться через `User::LoadLogicalDevice`.

Префікс `d_` у Symbian означає тестовий драйвер — такі навмисно відкривають
ядерні API користувацькому боку.

Імпортує:

| Ціль | Що це |
|---|---|
| `kaomap.dll +0xF0` | **Write32** |
| `kaomap.dll +0xF8` | **Modify32** |
| `power.dll` × 9 | зокрема `0x800AD064` — та сама функція, яку кличе DVFS з id 66 |
| `ekern.exe` × 30 | звичайна ядерна обв'язка |

### Таблиця переходів по ресурсах

Диспетчер (`0x80148FF8`) розгалужується по індексу ресурсу, далі кожен блок
розбирає піддію в `r0`:

| Піддія | Дія |
|---|---|
| 0 | **встановити** рівень; значення приходить від викликача в `r3` |
| 1 | прочитати стан |
| 3 | ще одна операція (`0x80148EAC`) |

Блок ресурсу **66** (`0x80149018`) — це продуктивність CPU, той самий id, який
`dvfs_interface.ldd` зашиває константою:

```asm
cmp r0, #0
mov r2, r3          ; ЗНАЧЕННЯ ВІД ВИКЛИКАЧА
add r1, r4, #88
mov r0, #66         ; ресурс 66
bl <power.dll 0x800AD0A4>
```

Ключове: шлях іде **прямо в power.dll, минаючи `dvfs_hal`**, тож квантування
до 50/100 тут не застосовується. Які межі накладає сама power.dll — невідомо,
перевіряється лише дослідом.

Доступні ресурси, судячи з констант у блоках: 1, 2, 3, 4, 5, 6, 65, 66, 67,
69, 70.

Окремо опкод 12 (`0x80148EFC`) виконує фіксовану послідовність по регістрах
System Control Module (`0x480000CC`, `0x480000D0`, `0x480000D4`, `0x480000D8`,
`0x48000270`) з одним значенням від викликача. Це не PRCM, але доводить
наявність сирого `Write32` із керованими даними.

### Кодування повідомлення (`HandleMsg` @`0x80148FB8`)

Це `DoRequest`, не `DoControl`:

```asm
ldr r0, [r6,#28]     ; a1 = TRequestStatus*
mvn r0, r1           ; r0 = ~iValue = номер запиту = ПІДДІЯ
ldr r1, [r6,#32]     ; r1 = a2 = ІНДЕКС таблиці переходів
cmp r1, #12
addls pc, pc, r1, lsl #2
```

Результат повертається через `Kern::RequestComplete` **у `TRequestStatus`**
(`0x8014928C`: `mov r1, r5 ; b <RequestComplete>`), тож
`DoRequest(піддія, status, індекс)` і далі `status.Int()`.

Таблиця індексів: 0 → `KErrNotSupported`; 1..5 → ресурси 1..5; 6 → 65;
**7 → 66 (продуктивність CPU)**; 8 → 67; 9 → 69; 10 → 70; 11, 12 → інше.

### Виправлення: рівень НЕ приходить від викликача

Спершу я прочитав `mov r2, r3` у блоці ресурсу 66 як «значення від викликача».
Це помилка. `r3` заповнюється раніше з `*(0xC8097150)`, а туди драйвер при
ініціалізації кладе вказівник на власний 8-байтовий об'єкт
(`mov r0,#8 ; bl <alloc> ; str r0,[r5]` @`0x80148D8C`). Тобто це об'єкт
зворотного виклику, і виклик має вигляд
`f(id=66, this+88, callbackObj, 0)` — **звичайне зайняти/звільнити фіксованого
ресурсу, без довільного рівня**.

Отже TestPowerAPI дає доступ до ширшого набору ресурсів, ніж DVFS (65, 67, 69,
70, 1..6), але **примітиву запису довільної адреси не дає**. Єдиний сирий
`Write32` із даними від викликача — це `DoControl(12, a1, a2)`, і він пише за
фіксованими адресами System Control Module, не PRCM.

### Перелік ресурсів: що встигли прочитати

```
LoadLogicalDevice(d_powerapi.ldd) -> 0
DoCreate(TestPowerAPI, v0.0.0)    -> 0
  get(index=0) -> -5     KErrNotSupported, рівно як за кодом
  get(index=1) -> -1     KErrNotFound
  get(index=2) -> -1
  get(index=3) -> -1
  get(index=4) -> -1
  get(index=5) -> -1
  get(index=6) -> запит НЕ ЗАВЕРШУЄТЬСЯ НІКОЛИ (ресурс 65)
```

Індекс 0, що віддав рівно `-5`, підтверджує правильність розшифровки таблиці
переходів. Ресурсів 1..5 на цьому апараті немає.

**Ресурс 65 (індекс 6) вішає запит намертво.** Скасувати нічим: `Cancel`
драйвер не має.

### Наслідок: стан драйвера переживає перезапуск демона

Після зависання на індексі 6 драйвер лишається з нескасовним запитом. Наступна
спроба відкрити канал блокується вже **до** будь-якого запиту — судячи з
поведінки, на м'ютексі, який той запит тримає. Тобто:

- таймаут треба вішати не лише на запити, а й на `LoadLogicalDevice`/`DoCreate`
  — а зробити це штатними засобами не можна, вони синхронні й без таймауту;
- перезапуск демона не допомагає: стан живе в ядрі, чиститься лише
  перезавантаженням апарата;
- однопотоковий демон чекає на вихід процесу, тож зависання проби блокує весь
  канал доставки. Апарат при цьому живий — TCP-рукостискання проходить.

**Висновок по TestPowerAPI: гілка тупикова.** Примітиву запису довільної адреси
він не дає (див. вище), а ціна подальшого промацування — перезавантаження
апарата на кожен невдалий індекс. Іти цим шляхом далі сенсу немає.

### Практичний урок: зависання блокує канал доставки

Перший прогін переліку ресурсів не повернувся: якийсь запит не завершився,
`User::WaitForRequest` став намертво, а демон однопотоковий і чекає на вихід
процесу — тож зависла не лише проба, а весь канал доставки. Апарат при цьому
живий (TCP-рукостискання проходило), лікується перезавантаженням.

Через це в пробнику тепер:

- `TRequestStatus` для драйвера — **статичний**, не на стеку: якщо запит колись
  завершиться після нашого відходу, драйвер напише за живою адресою, а не в
  чужий кадр стека;
- кожен запит обгорнутий `RTimer` із таймаутом (`User::WaitForRequest(s, ts)`),
  повертає `KErrTimedOut`;
- після таймауту канал **не закривається** і подальші запити не шлються —
  скасувати вже висячий запит нічим, `Cancel` драйвер не має;
- уся секція вмикається лише аргументом `power`, щоб звичайний прогін лишався
  таким, після якого апарат гарантовано відповідає.

## 8. Обмеження інструментів

Публічний S60 3rd FP1 SDK **не вміє збирати kernel-side код**: у
`S60_3rd_FP1\Epoc32` немає ні `include\kernel\`, ні `ekern.lib`. Власний LDD
зібрати нічим — потрібен Kernel DevKit, якого немає. Звідси й ставка на
готовий драйвер RomPatcher+.

## 9. Symbian-inflate: розтиснення LDD RomPatcher+ (підтверджено)

`patcher.ldd` та побратими стиснуті `KUidCompressionDeflate` (`0x101F7AFC`) —
власним Хаффман-deflate Symbian, який **не сумісний із zlib**. Реалізовано
дослівний порт декомпресора з відкритих вихідників Symbian (elf2e32:
`huffman.cpp`/`inflate.cpp`) — `tools/syminflate.js` (Node).

Підтверджено на апаратних цілях: `file0/1/2` розтискаються рівно у свій
`iUncompressedSize` — **2688 / 2700 / 2780** байтів. Перші байти
`patcher.ldd` — `E92D4010` (`stmfd sp!,{r4,lr}`), `E3500003` (`cmp r0,#3`):
валідний ARM-пролог, тобто розпаковано правильно, а не «схоже на правду».

Формат стиснутого E32: нестиснена частина = `oh->TotalSize()` == `iCodeOffset`
(поле @0x64), і саме там (для цих LDD — зміщення **156**) починається
deflate-потік. `iUncompressedSize` @0x7C — довжина тіла після розтиснення.
Відновлений образ = нестиснений заголовок + розтиснене тіло; код-секція
(`iCodeSize` = `0x948` = 2376 Б) лягає з `iCodeBase` = `0x8000`.

Артефакти: `out/rp/inflated/patcher.img` (+`Shadow`,`S3`) і
`out/rp/inflated/patcher_code.asm`.

## 10. Примітив запису в `patcher.ldd` (структура і ключові ординали доведені)

Дизасемблер `patcher_code.asm` (код із `iCodeBase = 0x8000`). Імпортує **45**
функцій з `ekern{000a0000}[100041af].exe` (ядро). Доведене **прямо з коду**
(не залежить від версій):

- **Диспетчер `0x8604`**: `sub r1,#0x64; cmp r1,#5; ldrls pc,[pc,r1,lsl#2]` —
  таблиця переходів на функції каналу **100–105** (`0x64…0x69`).
- **Маршрутизація за межами `0x85a4`**: бере об'єкт (імпорт), порівнює цільову
  адресу з `obj[+140]` (base) і `obj[+140]+obj[+244]` (top):
  - `addr ∈ [base, top)` → `0x8530`: підготовка сторінок (`0x8410`) і запис
    32-байтовими шматками — шлях ROM-shadow;
  - `addr ∉ [base, top)` → `0x84f4`: **прямий запис без відхилення**.
- Обидва шляхи роблять сам запис одним імпортом ядра — **ординал 725**, з
  трьома аргументами `(dest, src, len)`, під парою lock/unlock (**ординали
  401/402**). Три аргументи — сигнатура сирого копіювання пам'яті, а не
  `ThreadRawWrite` (той бере 4 аргументи й трактує адресу як user-простір).

**Наслідок:** адреса призначення приходить від клієнта; адреса **поза ROM**
(як наш PRCM `0xC6008540`) іде прямим шляхом і не відкидається. Це і є
примітив запису за довільною адресою ядра, якого бракувало для `CM_CLKSEL1_PLL`
(розділ 4). len для запису регістра = 4.

### Резольв ординалів через реальний `ekern.exe` із дампа (підтверджено з коду)

`ekernu.def` із SymbianSource виявився від пізнішого ядра (ординали зсунуті,
імпорти некогерентні). Замість нього розібрано export directory **реального**
`ekern.exe` із дампа ROM (`../eka2l1/data/drives/z/rm-320/sys/bin/ekern.exe`):
UID1 `1000007A`, `iCodeAddress` = `0x8006A000`, `iExportDirCount` = **808**,
`iExportDir` = `0x8009D9DC`. Export dir — масив 32-бітних адрес; ординал `N`
у записі `[N-1]`. Ординал 725 (`< 808`) — у межах.

| Ординал | Адреса | Функція (виведено з коду) |
|---|---|---|
| **725** | `0x8006F800` | **`memmove(dest, src, len)`**. `cmp r2,#0; bxeq lr`; аналіз перекриття (`subnes r3,r0,r1; cmphi r2,r3`); для `len≤15` — jump-table побайтового копіювання (`sub pc, ip, r2, lsl #3`); для `len>15` — word-loop `0x8006f944` (`pld`/`str`). Повертає `dest` (r0 не чіпається). |
| **401** | `0x80070E60` | acquire блокування планувальника: глобал `[0x8007087c]`, поле `[+304]`, працює з `[+48]/[+52]` |
| **402** | `0x80070EC0` | unlock: декремент лічильника вкладеності `[+48]`, перевірка прапорця решедулу `[+52]`, умовне пробудження |
| 248 | `0x80073A0C` | тривіальний геттер `return *(глобал 0x8007397c)` (поточний обʼєкт/потік) |

Резольв самоузгоджений: 401/402 — суміжні ординали (адреси за 96 байтів) і
утворюють чисту пару lock/unlock; зсув індексації на одиницю цього б не дав.
Це підтверджує коректність декодування export-таблиці на тому ж рівні, що й
«дві незалежні адреси на відомих регістрах» у розділі 4.

**Закрито:** ординал 725 — це `memmove(dest,src,len)`, чистий CPU-store без
MMU-трюків і кеш-барʼєрів. len для запису регістра = 4. Три аргументи й
семантика копіювання підтверджують: це сире копіювання памʼяті, а не
`ThreadRawWrite`. Адреса призначення поза ROM (`0xC6008540`) іде прямим шляхом
`0x84f4` і не відкидається — примітив запису за довільною адресою ядра доведено
від початку (клієнт) до кінця (str у ядрі).

### Повна карта каналу patcher.ldd і два обмеження для нашого випадку

Розібрано всі 6 функцій каналу (диспетчер `0x8604`, `r1-100`, jump-table) і всі
30 import-стубів резольвлено проти export-таблиці реального `ekern.exe`
(стуб→ординал→адреса). Ключові:

| Стуб patcher | Ординал | ekern | Роль |
|---|---|---|---|
| `0x87C4` | **725** | `0x8006F800` | memmove — сам запис |
| `0x883C` | **401** | `0x80070E60` | lock (перед записом у `0x84f4`/`0x8530`) |
| `0x87E4` | **402** | `0x80070EC0` | unlock (після) |
| `0x8854` | 248 | `0x80073A0C` | геттер обʼєкта ROM-регіону (`[+140]`=base, `[+244]`=top) |
| `0x87CC` | 238 | `0x8007828C` | підготовка сторінки (петля в `0x848c`) |
| `0x87D4` | 303 | `0x800765D4` | розмір сторінки |
| `0x8804` | 639 | `0x8006ED0C` | парсер клієнтського дескриптора (a2 = дані, не адреса) |

Функції каналу: 100 — підготовка/перевірка сторінок; 101/102/104 — bulk-запис
через роутер `0x85a4`; **105 — одиничний запис** `write(dest=*a1, src=дані з
дескриптора a2, len=*a2 & 0x0FFFFFFF)`; 103 — фіксований геттер (ord 360),
без аргументів.

Це остаточно підтверджує §10, але виявляє **два обмеження саме для запису в
PRCM** (обидва — прямо з коду, не здогад):

1. **Немає примітиву читання.** Жодна функція каналу не читає довільну адресу:
   105 бере `src` лише з клієнтського дескриптора (через ord 639), 103 — це
   фіксований геттер. memmove симетричний, але канал ніколи не дає підставити
   `src` = довільну адресу ядра. Отже прочитати поточні `CM_CLKSEL1_PLL` /
   `CM_CLKSEL2_PLL` / `CM_CLKSEL_MPU` цим драйвером **не можна**, а без цього
   безпечний read-modify-write бітового поля неможливий (сліпий запис усього
   32-бітного регістра затер би сусідні поля).

2. **Хибний розмір доступу для MMIO.** Для нашого `len=4` memmove іде гілкою
   `len≤15` — це **чотири окремі `strb`**, а не один `str`. Запис регістра PRCM
   чотирма побайтовими зверненнями — недокументований і ризикований доступ:
   частина CM-регістрів OMAP2420 надійно приймає лише 32-бітний доступ, а
   побайтовий дає 3 проміжні стани регістра. memmove створювався для латання
   *байтів коду* в ROM, де це коректно, — не для програмування пристроєвих
   регістрів. Змусити word-шлях (`len>15`) для 4-байтового регістра не можна.

**Наслідок:** `patcher.ldd` дає довільний запис у память ядра, але як інструмент
програмування PRCM він **непридатний** — ні прочитати поточний стан, ні зробити
коректний 32-бітний запис. Гілку не закриваємо як провальну, але для розгону
потрібен примітив із `Read32`/`Write32`/`Modify32` правильної розрядності
(як kaomap `+0xE8/+0xF0/+0xF8`, які імпортує саме `TestPowerAPI`, — але та
гілка тупикова з іншої причини, §7). Питання пошуку такого примітиву — відкрите.

Про мапінг MMIO (початкове питання пункту): роутер `0x85a4` справді шле адресу
поза ROM прямим шляхом `0x84f4` без відхилення, а kernel-mode `str` за kaomap-
мапінгом `фіз+0x7E000000` досягає пристрою (доведено роботою kaomap Write32 для
PRCM). Тобто *мапінг* запис у MMIO дозволяє; блокує саме розрядність memmove
(пункт 2 вище) і відсутність читання (пункт 1).

Апарат не чіпаємо.

Артефакти розбору: `out/asm/ekern.asm` (повний дизасемблер, 56854 рядки),
`out/asm/ekern.bin` (тіло без 120-байтового заголовка).

## 11. Пошук примітиву MMIO по всьому ROM: негативний результат

Просканував усі **2712** модулів дампа ROM на імпорт kaomap-примітивів
(`Read32` `0x800A1C40`, `Write32` `0x800A1C48`, `Modify32` `0x800A1C50` —
опкоди звірено: `ldr r0,[r0]` / `str r1,[r0]` / RMW із забороною переривань).
Імпортують їх **24 модулі**; з них користувацький бік мають лише LDD:
`d_display`, `d_powerapi`, `custom`, `secldd`, `sosadlserver`, `xbus`.

Для кожного LDD класифіковано джерело адреси (`r0`) на кожному call-site
Read32/Write32/Modify32: PC-літерал (фіксована база) чи регістр-аргумент.
Ручна перевірка «підозрілих» (`mov r0,rN`) показала, що `rN` — завжди
внутрішня база драйвера (walking-pointer по блоку регістрів свого периферала),
а не адреса від клієнта:
- `d_display` / `sosadlserver`: `r5 = *літерал` (той самий display-polling
  код, `sub r4,r5,#20; tst r0,#16`);
- `custom`: `r0 = *літерал` (читання ID/ревізії периферала);
- решта — базa+offset із зашитих констант.

**Висновок: жоден драйвер у ROM не віддає юзер-боку запис/читання за довільною
адресою MMIO.** Це очікувано — продакшн-драйвери не експонують сирий MMIO, а
єдині тестові (`d_*`) працюють за зашитими адресами. Артефакти: `out/asm/`
(`d_display.asm`, `custom.asm`, `sosadl.asm`).

## 12. Як прошивка керує частотою в рантаймі (переорієнтація)

> **ВИПРАВЛЕНО 2026-08-07 — див. §17.** Головний висновок цього розділу
> («валідованого рантайм-шляху relock у прошивці немає») **хибний**. Він
> спирався на інвентаризацію лише викликів `kaomap Write32` і лише **повних**
> 32-бітних літералів адрес. Насправді `power.dll` частину PRCM і весь SDRC
> адресує **прямою парою `ldr`/`str` за базою+зсувом, минаючи kaomap**, і саме
> там лежить повна послідовність bypass → полінг IDLEST → relock → relock DLL.
> Текст нижче лишено як є — у своїх межах він коректний, — але читати його
> треба разом із §17.

Розібрано `power.dll` (base `0x800A7C98`, 145 викликів Write32). Ключовий факт
**прямо з коду**:

- Серед усіх 145 Write32 **немає жодного в `CM_CLKSEL1_PLL` (`0xC6008540`)** —
  множник/дільник DPLL. Пишуться дільники доменів/периферії: `0xC6008200/8204/
  8210/8214/821C` (CLKSEL для доменів), `0x8300/8310`, `0x8410`, `0x82A0/82A4`,
  `0x83C8`, плюс безліч `*_FCLKEN/ICLKEN` (`018/028` у блоках `C6018/A/C/E`).
- `CM_CLKSEL1_PLL` у power.dll лише **читається**: геттер `0x800B1544` (§4) і
  функція init `0x800A94xx`, яка перевіряє div-поле (біти [11:8]) і в разі
  чого Modify32 сусіднього `0xC6008530` — тобто валідація boot-конфігу, не
  задавання нової частоти.
- Рантаймові сеттери power.dll беруть **значення з аргументу** й програмують
  саме дільники: напр. `0x800AC698` пише 3-бітове поле в `0xC6008340` зі
  значення 1..4; `0x800AC6CC` — фіксація `PRCM_CLKCFG_CTRL[0]=1`.

**Наслідок (переорієнтація стратегії).** Множник DPLL задається один раз на
буті; рантаймовий DVFS лише масштабує **дільники** вниз від стелі 330 МГц
(§5 — губернатор уже тримає максимум, тобто мінімальний дільник). Звідси два
взаємновиключні шляхи розгону, обидва впираються в те саме:

1. **Зменшити дільник** (`CM_CLKSEL_MPU[3:0]` або core) нижче поточного. Але
   якщо MPU вже на мінімумі — запасу немає; треба **прочитати** поточний
   дільник, а примітиву читання ми не маємо (§10, §11).
2. **Підняти множник DPLL** (`CM_CLKSEL1_PLL`) з relock. ~~Валідованого
   рантаймового шляху для цього в прошивці немає~~ — **хибно, див. §17**:
   шлях bypass→relock у прошивці є (`power.dll @0x800A7F6C`), у ньому немає
   лише самого запису нового множника. Решта абзацу теж застаріла: для цього
   шляху не потрібен kaomap-примітив, бо power.dll там пише в MMIO **прямим
   `str`**, а не через kaomap.

Тобто обидва шляхи заблоковані відсутністю коректного MMIO read/write з
користувацького боку. Це не глухий кут проєкту, а точне формулювання того, що
тепер справді бракує: **не «що писати» (відомо), а робочий канал у ядро з
коректною розрядністю доступу і читанням.** Кандидати далі — розділ у
`state.md`.

Артефакти: `out/asm/power.asm` (11639 рядків), `out/asm/power.bin`.

## 13. Синтез: патчити КОД power.dll, а не MMIO (шлях уперед)

Boot-множник DPLL по всьому дампі не програмується Symbian-кодом: лише power.dll
посилається на `CLKSEL1_PLL(v)`, і тільки читанням; фізичної `0x48008540` немає
ніде (§12). Отже задає його pre-Symbian завантажувач або сирий bootstrap поза
`sys/bin`. «Чистий» патч таблиці частот неможливий — таблиці нема.

Але два блокери (немає читання; memmove пише байтами — §10, §11) знімаються
одним ходом, якщо **патчити не MMIO, а код power.dll**:

- Код power.dll (`0x800A7C98..0x800B3298`) лежить у **ROM-регіоні**, а це саме
  той діапазон `[base, top)`, який patcher обробляє shadow-шляхом `0x8530`
  (§10). Патч коду — це запис у **звичайну память ROM-shadow**, де побайтовий
  memmove коректний (він для цього й створений). Проблема розрядності стосувалась
  лише прямого запису в MMIO — тут її немає.
- Сам доступ до регістрів робить power.dll своїми **коректними** kaomap-
  примітивами (`Read32`/`Write32`/`Modify32`, 32-бітними, Modify32 з забороною
  переривань). Ми лише міняємо, *що* і *куди* вона читає/пише.
- Тригер із юзер-боку вже є: `DoControl(1)` на `dvfs_interface` викликає
  `GetClockFrequency` @`0x800B15DC` (§3), обидві адреси — в патчабельному
  регіоні.

**Два кроки, за зростанням ризику:**

1. **READ (безпечний перший дотик до апарата).** Пропатчити код так, щоб
   юзер-досяжний виклик (напр. `DoControl(1)` або вільний опкод) повернув сире
   значення `CM_CLKSEL1_PLL` / `CM_CLKSEL_MPU` замість похідної частоти. Читання
   MMIO безпечне, частоту не чіпає. Це (а) вперше проганяє весь ланцюг patcher
   end-to-end і (б) закриває брак читання — дає фактичний розклад
   `mult/div/core_sel/mpu_div`, без якого вибір важеля наосліп.
2. **WRITE.** Знаючи поточні значення й ціль, пропатчити код так, щоб
   юзер-досяжний виклик виконав коректний 32-бітний relock DPLL (запис
   `CLKSEL1_PLL` новим множником → `CLKEN_PLL` → фіксація `CLKCFG_CTRL[0]`)
   руками самої power.dll. patcher при цьому чіпає лише байти коду, ніколи MMIO.

**Незакрите, потрібне до першого дотику:**
- Точний формат клієнтського виклику patcher (дескриптор a2 у func 105, §10) —
  щоб реально застосувати патч.
- Чи shadow-шлях patcher коректно готує I-cache/сторінки для виконуваного коду
  power.dll (не лише даних) — інакше пропатчений код не візьметься.
- Вибір місця патча: вписатись у наявні байти чи винести в code-cave і
  зробити перехід.

Це перетворює наявні інструменти на достатні; апарат не чіпаємо, доки крок 1
(READ-патч) не спроєктовано повністю на папері.

## 14. Формат клієнтського виклику patcher.ldd (доведено з коду)

Канал реєструється як **`RomPatcherPlus.Driver`** (фабрика `DPatcherDevice`,
канал `DPatcherChannel`). Диспетчер `0x8604` стоїть у vtable каналу (`0x8908`),
тобто виклик — це `RBusLogicalChannel::DoControl(func, a1, a2)`, `func` 100..105
(`sub r1,#100; cmp #5; ldrls pc,[pc,r1,lsl#2]`). Аргументи `a1/a2` драйвер
розіменовує **прямо** — DoControl синхронний, ядро працює в контексті клієнта,
тож user-вказівники доступні без `kumemget`.

**func 105 — одиничний запис** (`0x8658`), доведено потік аргументів:
- `dest = *a1` (перше слово за `a1` = цільова адреса);
- `src  = a2->Ptr()` (через ord 639 = `TDesC8::Ptr()`, декодує тип дескриптора);
- `len  = a2->Length()` (`*a2 & 0x0FFFFFFF`, довжина із заголовка дескриптора);
- якщо `*a1 == 0` — повертає 0 (no-op).

Тобто **`a1` = вказівник на цільову адресу**, **`a2` = дескриптор із байтами,
які треба записати**. Клієнт (user-side):

```cpp
RBusLogicalChannel ch;                       // відкритий на "RomPatcherPlus.Driver"
TUint32 addr = 0x800B15DC;                    // адреса коду power.dll (ROM)
TBuf8<64> patch;  patch.Copy(bytes, n);       // нові байти (ARM-код патча)
TInt r = ch.DoControl(105, &addr, &patch);    // dest=addr, src=patch, len=n
```

Маршрут за адресою: power.dll (`0x800A7C98..0x800B3298`) — у ROM, тож роутер
шле на **shadow-шлях** `0x8530` (готує сторінки ord 240, пише 32-байтовими
шматками memmove під lock ord 401/402). Це і є коректний шлях патча ROM-коду.

**Незакрите (гіпотеза, перевіряється READ-патчем):**
- Жоден шлях запису не робить явного `Cache::IMB` після memmove. Когерентність
  I-cache для пропатченого коду має забезпечувати remap shadow-сторінки в ord
  240. Якщо ні — пропатчений код не візьметься до флешу кешу. READ-патч це
  й покаже: спрацював → когерентність є.
- Точні значення `base/top` об'єкта (ord 248) невідомі статично; якщо power.dll
  раптом поза `[base,top)`, запис піде прямим шляхом `0x84f4` без shadow і без
  когерентності — теж виявиться на READ-патчі.
- Набір capability для відкриття каналу (з E32-заголовка `patcher.ldd` або
  добором); демон доставки реєструє власну dev-збірку в локальному реєстрі
  хешів (`C:\sys\hash`) — штатний homebrew-механізм цього розблокованого
  апарата, за яким його завантажувач впізнає dev-збірку з її caps.

## 15. READ-патч: проєкт (виведено з коду; НЕ перевірено на апараті)

Мета — отримати сире читання регістрів PRCM з юзер-боку, не маючи read-примітиву,
через патч ядерного коду (стратегія §13) інструментом patcher (§14).

**Ціль патча:** `dvfs_interface.ldd` @ `0x80148410`. Це тіло, яке DoControl(1)
викликає для обчислення відсотка (`GetClockFrequency(1)/3300000`). Єдиний caller —
DoControl(1) @`0x8014843c` (перевірено: grep по `0x80148410` дає один bl).

> **ВИПРАВЛЕНО 2026-08-08.** Далі тут стояло: «патч ізольований: зачіпає лише
> DoControl(1), який у штатній системі ніхто, крім нашого пробника, не кличе».
> **Це хибно, і помилка коштувала двох перезавантажень апарата.** Твердження
> стосувалося викликачів *внутрішнього тіла* всередині `.ldd`, а я поширив його
> на весь канал. Скан ROM показує, що ім'я каналу `dvfs_interface` лежить як
> UTF-16 рядок (форма `_LIT` для `DoCreate`) ще у **двох системних модулях**:
> `mmrmserver.dll` (Multimedia Resource Manager) і `fmradiotunercontrol.dll`.
>
> Наслідок: доки READ-патч накладено, будь-який їхній виклик `DoControl(1, a1)`
> з ненульовим `a1` виконує `ldr r0,[r1]` за цією адресою **в режимі ядра**.
> Обидва спостережені перезавантаження сталися, коли апарат стояв без діла з
> лишеним патчем — саме тоді, коли менеджер ресурсів і опитує стан.
>
> Причинність не доведена остаточно (у DLL звернення до даних ідуть через
> релокації і в сирому дизасемблері не резольвляться), але припущення про
> ізольованість спростоване, і цього досить.
>
> **База для порівняння важлива.** Апарат перепрошито штатною останньою
> прошивкою за кілька днів до цих робіт і до них він був повністю стабільним;
> RomPatcher у флеш нічого не пише. Тобто списати ребути на «старе залізо з
> модифікованою прошивкою» не можна — до наших патчів їх не було.
>
> **Виправлення в коді (доведено на апараті 2026-08-08):** двигун повертає
> оригінальні слова тіла (`ocengine.cpp`, `KDvfsOriginal`) після **кожної**
> операції, а не в кінці сеансу.
>
> Перша спроба відкату писала 6 слів (24 байти) і **мовчки не спрацьовувала** —
> після неї апарат перезавантажився втретє. Причина: 24 байти йдуть гілкою
> `memmove` для `len>15`, а перевірений шлях — рівно 16 байтів, як у самого
> патчу. Слова 5 і 6 тіла патч не чіпає, тож відновлювати їх і не треба.
>
> Відкат тепер **перевіряється функційно**: у штатної `DoControl(1, 0)` відома
> поведінка — вона віддає відсоток від номіналу (§3), тоді як READ-патч на
> `a1=0` повертає рівно 0. На апараті після відкату отримано **100**, тобто в
> ядрі знову оригінальний код. Прочитати відновлені байти напряму неможливо:
> примітив читання це і Є ті байти.

**Патч (16 байтів, перезапис `0x80148410..0x8014841F`):**

| Адреса | Байти (LE) | Інструкція |
|---|---|---|
| `0x80148410` | `00 00 51 E3` | `cmp r1, #0` |
| `0x80148414` | `00 00 91 15` | `ldrne r0, [r1]` |
| `0x80148418` | `00 00 A0 03` | `moveq r0, #0` |
| `0x8014841C` | `1E FF 2F E1` | `bx lr` |

`r1` на вході `0x80148410` = `a1` із DoControl (диспетчер `0x80148438`:
`mov r1,r2`). Захист `a1==0` прибирає NULL-деференс (наявний `PerfPercent()`
кличе `DoControl(1,0)` — після патча він безпечно поверне 0). Слова `0x80148420/
424` лишаються (мертві, недосяжні після `bx lr`). r4 зберігати не треба —
DoControl сам робить `stmdb {r4,lr}`.

**Тригер (user-side):** `RDvfs::DoControl(1, (TAny*)0xC6008540)` → повертає сире
`CM_CLKSEL1_PLL`; аналогічно `0xC6008544` (CLKSEL2_PLL), `0xC6008140`
(CLKSEL_MPU), `0xC6008500` (CLKEN_PLL). Декодувати формулою §4 — і вперше
дізнатись фактичний розклад `mult/div/core_sel/mpu_div`.

**Порядок за зростанням ризику (критично — це перший патч ядерного коду):**

0. **SELF-TEST (нульовий ризик для ядра).** Перед будь-яким патчем ядра —
   перевірити канал patcher і формат func 105 записом у **власний user-буфер**:
   `DoControl(105, &addr, &desc)`, де `addr` = адреса свого буфера. Не-ROM адреса
   йде прямим шляхом `0x84f4` (memmove), ядерний код не чіпається. Доводить:
   patcher вантажиться, канал відкривається (caps/версія), конвенція func 105
   правильна, запис працює. Тільки після успіху — крок 1.
1. **READ-патч** (цей розділ): застосувати 16 байтів, прочитати регістри.
   Заразом підтверджує гіпотези §14 (I-cache-когерентність shadow-remap;
   power.dll/dvfs_interface у `[base,top)` patcher).
2. **WRITE-патч** (пізніше): relock DPLL руками power.dll.

**Передумови доставки (виявлено при проєктуванні):**
- `patcher.ldd` немає в ROM (Z:) — це файл із RomPatcher+ SIS. Для
  `LoadLogicalDevice("patcher.ldd")` треба залити **оригінальний** (стиснений)
  `out/rp/file0` у `E:\sys\bin\patcher.ldd` + зареєструвати його SHA-1 у
  `C:\sys\hash` (той самий механізм, що для ocprobe; завантажувач сам розтисне
  Symbian-deflate). Наш inflated `.img` — лише для аналізу, на апарат не йде.
- Потрібні capability для відкриття каналу — з E32-заголовка `patcher.ldd`.
- `build.cmd` наразі заливає лише ocprobe; для тесту треба додатково залити
  patcher.ldd (+hash) — розширити deploy.

Апарат не чіпаємо, доки крок 0 (self-test) не пройдено.

### Перевірка READ-патчу на апараті — 2026-08-07

Виконано послідовність із §15 на RM-320. Спершу `ocprobe patcher selftest`:
оригінальний стиснений `out/rp/file0` залито як `E:\sys\bin\patcher.ldd` із
SHA-1 у `C:\sys\hash\patcher.ldd`; `LoadLogicalDevice -> 0`,
`DoCreate("RomPatcherPlus.Driver", v0.0.0) -> 0`, а
`DoControl(105, user-buffer, 4 bytes) -> 0` змінив буфер рівно на очікувані
байти. Це підтвердило delivery, capability, формат func 105 і прямий шлях без
зачіпання ROM.

Далі `ocprobe patcher read` повторив self-test і записав 16 байтів за
`0x80148410`; `DoControl(105, READ patch, 16 bytes) -> 0`. Виклик
`dvfs_interface::DoControl(1, addr)` після цього повернув:

| Регістр | Значення |
|---|---|
| `CM_CLKSEL1_PLL` | `0x00056400` |
| `CM_CLKSEL2_PLL` | `0x00000002` |
| `CM_CLKSEL_MPU` | `0x00000002` |
| `CM_CLKEN_PLL` | `0x0000000F` |

Декодування `CM_CLKSEL1_PLL`: `sys_clk=19.2 MHz` (селектор 0), `mult=86`,
`div=4`, тобто DPLL = `19.2 * 86 / (4+1) = 330.24 MHz`. Із кодової формули
power.dll `core = DPLL * CM_CLKSEL2_PLL[1:0]`, а потім
`MPU = core / CM_CLKSEL_MPU[3:0]`, значення `2`/`2` дають MPU = 330.24 MHz.
Це сходиться з незалежним NOP-виміром 322–325 MHz (похибка припущення про
кількість тактів) і зі штатним `DoControl(1) -> 100` до патчу.

**Новий обмежувач.** `mpu_div=2` не є запасом для обережного розгону:
перехід до 1 подвоїв би MPU приблизно до 660 MHz. Отже наступний практичний
кандидат — лише малий крок DPLL, наприклад `mult 86 -> 87` (+1.16%), але не
раніше ніж повністю доведено runtime-послідовність relock, напруга й межі
SDRC. Патч був runtime-only; перезавантаження відновлює ROM, а до нового
експерименту його треба виконати, щоб прибрати READ-патч і стан LDD.

## 16. WRITE-патч: попередня модель була неповною (апарат не чіпати)

Після перезавантаження апарата проаналізовано зовнішнє еталонне джерело:
`arch/arm/mach-omap2/sram242x.S` Linux v3.7 для **OMAP2420**. Це не доказ
поведінки RM-320 сам по собі, але код безпосередньо реалізує PRCM цього SoC і
виправляє небезпечне припущення в попередньому плані §13/§15.

`omap242x_sram_set_prcm` робить повну послідовність:

1. зберігає регістри та preloads власний критичний код в I-cache;
2. переводить `CM_CLKEN_PLL[1:0]` у fast-relock bypass (`2`) і чекає
   `CM_IDLEST_PLL[1:0] == 1`;
3. лише в bypass пише новий `CM_CLKSEL1_PLL` і `PRCM_CLKCFG_CTRL = 1`;
4. переводить DPLL у lock (`3`), чекає `CM_IDLEST_PLL[1:0] == 2`;
5. оновлює SDRC refresh, переводить DLLA/DLLB у lock-mode та витримує не менше
   0x400 L3-тактів на relock DLL.

Окрема функція `omap242x_sram_reprogram_sdrc` також робить memory barrier,
підлаштовує refresh і викликає `voltage_shift` перед підняттям частоти. Отже
попередня скорочена формула «`CLKSEL1_PLL` -> `CLKEN_PLL` -> `CLKCFG_CTRL`»
була хибною за порядком і пропускала SDRC/напругу/SRAM-контекст.

Додаткове зовнішнє підтвердження: `opp2420_data.c` Linux v3.7 задає найшвидшу
офіційну точку як **330 MHz ARM**, `CORE_CLK = 660 MHz`, `SDRC_RFR_CTRL_165MHz`.
Отже `mult=87` не є штатною OPP і не може бути першим дотиком лише тому, що
крок малий.

**Висновок.** READ-патч довів transport, ROM-shadow і читання регістрів, але
не є доказом безпеки DPLL write. Наступна робота — знайти/спроєктувати саме
SRAM-safe виконання, прочитати параметри SDRC та встановити межі живлення;
до цього жодного WRITE-патчу і жодної команди на апараті не додавати.

> **УТОЧНЕНО 2026-08-07 (§17).** Сама вимога послідовності — підтверджена, і
> тепер не лише зовнішнім джерелом: та сама структура (self-refresh → bypass →
> полінг IDLEST → WFI → relock → полінг IDLEST → relock DLL) знайдена **в
> `power.dll` цього апарата**. Але формулювання «знайти/спроєктувати SRAM-safe
> виконання» більше не є єдиним варіантом: готова критична секція вже існує в
> прошивці, і вбудування в неї — дешевший і безпечніший шлях, ніж власна
> послідовність. Параметр SDRC теж більше не невідомий: `SDRC_RFR_CTRL` = 
> `0x0004DA01`. Незміненим лишається головне: **WRITE не робити**, апарат не
> чіпати.

Зовнішні джерела для відтворення: Linux v3.7
`arch/arm/mach-omap2/sram242x.S`, `arch/arm/mach-omap2/opp2420_data.c`; TRM
OMAP2423 (розділ 5.10.15, PRCM частина еквівалентна OMAP2420 в цій лінійці).

## 17. У прошивці Є SRAM-резидентна критична секція PRCM/SDRC (виправляє §12, §16)

Приводом до перевірки був сумнів у походженні висновку §16 (він спирався на
переказ Linux-коду). Перевірка підтвердила зовнішнє джерело, але виявила, що
**наш власний висновок «валідованого рантайм-шляху relock у прошивці немає» —
хибний**.

### Чому це проґавили: дві методичні помилки

1. Інвентаризація §11/§12 рахувала лише виклики `kaomap Read32/Write32/Modify32`.
   Але `power.dll` частину PRCM і **весь** SDRC чіпає **прямими `ldr`/`str`**,
   минаючи kaomap. Приклад — `str r2,[r1,#1280]` у `CM_CLKEN_PLL`.
2. Скан ROM шукав **повні** 32-бітні літерали адрес регістрів. `power.dll`
   адресує ці блоки як **база+зсув**, тож `CM_IDLEST_PLL` (`+0x520`) і всі
   регістри SDRC у скані не з'явилися взагалі.

### Нові бази (доведено збігом зсувів на відомі регістри)

| База | Фізична | Доказ |
|---|---|---|
| **SDRC `0xC6129000`** | `0x68009000` | шість зсувів лягли точно: `+0x60` DLLA_CTRL, `+0x64` DLLA_STATUS, `+0x68` DLLB_CTRL, `+0x70` POWER_REG, `+0xA4` RFR_CTRL_0, `+0xD4` RFR_CTRL_1 |
| CM `0xC6008000` | `0x48008000` | `+0x500` CLKEN_PLL, `+0x520` IDLEST_PLL, `+0x540` CLKSEL1_PLL, `+0x544` CLKSEL2_PLL |
| CONTROL `0xC6014000` | `0x48014000` | `+0x204` ревізія кремнію (пор. §4) |

Зверни увагу: мапінг SDRC — **не** `+0x7E000000` (це дало б `0xE6009000`).
Для цього L3-блока зсув інший. Правило §4 діє для вікна `0x48xxxxxx`, не глобально.

Скан усіх **2868** модулів дампа на літерал `0xC6129000`: **єдиний модуль —
`power.dll`, два входження**. Тобто вся робота ОС із контролером SDRAM — це
рівно дві функції нижче.

### Ланцюг: мапінг SRAM → копіювання коду → виконання з SRAM

Усе доведено прямо з коду.

**1. Конструктор `0x800AB24C`** (єдиний виклик — з `0x800A8560`, тобто
boot-ініціалізація):

```asm
bl  0x800B19C8                  ; аллокація об'єкта
str <0x800B31A8>, [r4]          ; vtable
...
mov r2, #4096                   ; розмір
ldr r1, <0x4029E000>            ; ФІЗИЧНА адреса внутрішньої SRAM OMAP2420
add r0, r4, #12
bl  0x800B1BA0                  ; -> ekern ординал 60 @0x800779E4 (мапінг HW-chunk)
ldr r0, [r4, #12] ; ldr r0,[r0,#36]   ; лінійна адреса відображення
ldr r1, <0x800A7F6C>            ; ДЖЕРЕЛО: код процедури
mov r2, #1024
str r0, [r4, #16]               ; зберегти лінійну адресу SRAM
bl  0x800B1C08                  ; -> ekern ординал 725 @0x8006F800 = memmove
```

Рядок помилки поряд у пулі — `"...for PowerDown"`.

**2. Виклик у рантаймі `0x800AB714`** — селектор глибини сну:

```asm
blx r2                    ; vtable+28 -> глибина сну, у r9
cmp r0, #2
bcc 0x800AB740            ; мілкий idle -> звичайний kernel idle
ldr r0, [r6, #16]         ; лінійна адреса SRAM
bl  0x800A80B0            ; 0x800A80B0 == "bx r0"  -> ВИКОНАННЯ З SRAM
```

**3. Сама процедура `0x800A7F6C..0x800A809C`** (+ пул літералів до `0x800A80AC`,
разом **324 байти**):

```asm
mcr p15,0,r3,c7,c10,4          ; DSB
[SDRC+0x70] |= 0x48            ; SDRC_POWER: self-refresh on idle
ldr r2,[CONTROL+0x204] ; >>28 ; cmp #5 ; bne skip     ; ревізія кремнію
ldr r2,[CM+0x540] ; >>8 ; &0xF ; cmp #8 ; ble skip    ; div з CLKSEL1_PLL
  [CM+0x500] = (v & 0xFC) | 1  ; CLKEN_PLL -> low-power bypass
  poll [CM+0x520] & 3 == 1     ; IDLEST_PLL: bypass активний
skip:
mcr p15,0,r2,c7,c0,4           ; WFI
  [CM+0x500] |= 3              ; relock DPLL
  poll [CM+0x520] & 3 == 2     ; IDLEST_PLL: locked
[SDRC+0x60] = [SDRC+0x68] = 0x770E      ; DLLA/DLLB_CTRL
bic #4 ; записати знову                  ; -> lock mode
delay 1000 ; ldr [SDRC+0x64] & 0xFF00    ; DLLA_STATUS
ldmia sp!, {...,pc}
```

Це **та сама структура, що в `sram242x.S`** (§16), лише без запису нового
множника: `CLKSEL1_PLL` тут тільки читається, щоб вирішити, чи входити в bypass.

**Релокабельність — перевірено:** у діапазоні `0x800A7F6C..0x800A80AC` немає
жодного зовнішнього `bl`, лише PC-relative завантаження літералів і локальні
переходи. Процедура самодостатня. Решта з 1024 скопійованих байтів — запас;
там зовнішні `bl` є (`0x800A80EC` і далі), і входити в них із SRAM не можна.

**Охорони.** На цьому апараті `div=4` (§15), тож `cmp #8; ble` **пропускає весь
блок bypass/relock**. Реально виконуються тільки SDRC_POWER, WFI і relock DLL.
Гілка bypass — мертвий код на RM-320; вона розрахована на ревізію кремнію 5 і
конфігурації з `div > 8`.

### SDRC refresh: значення відоме

`power.dll @0x800A7CAC` пише в `SDRC_RFR_CTRL_0` (`+0xA4`) і `_1` (`+0xD4`)
константу **`0x0004DA01`** → `ARCV = 0x4DA = 1242`, тобто ≈ **165 МГц**.

**Уточнено 2026-08-08 (з апарата).** Значень насправді два, і прошивка
перемикає їх разом із OPP. Обидва є літералами в `power.dll` — `0x0004DA01`
(@`0x800A7F24`) і `0x00032601` (@`0x800A7F28`), — і обидва зчитані з живого
регістра в різні моменти:

| Читання | `CM_CLKSEL2_PLL` | `SDRC_RFR_CTRL_0` | Стан |
|---|---|---|---|
| під навантаженням | 2 | `0x0004DA01` (ARCV 1242) | верхня OPP, L3 165 МГц |
| у спокої | 1 | `0x00032601` (ARCV 806) | нижня OPP |

Два незалежні поля (`core_sel` і `ARCV`) зійшлися в один і той самий висновок,
тож це не артефакт читання. Практичний наслідок для коду: **миттєвий відлік
`CM_CLKSEL2_PLL` брехливий** — спіймавши апарат у спокої, отримаєш 165 МГц CPU
замість 330. `COcEngine::Prepare` тому знімає серію під навантаженням і бере
максимум.

`SDRC_ACTIM_CTRLA_0` (припущений `+0x9C`) теж змінився між читаннями
(`0x8255B485` -> `0xBADDC4C6`). Зсув цього регістра я взяв із даташита по
пам'яті й **не звіряв із кодом**, тож поки що це здогад — на розгін він не
впливає, бо таймінги SDRC ми не пишемо.
Сходиться з `SDRC_RFR_CTRL_165MHz` із `opp2420_data.c` і з нашим читанням
`core_sel=2` (DPLL 330 → L3/CORE 660 → SDRAM 165). Отже апарат стоїть рівно на
штатній верхній OPP **330 / 660 / 165 МГц**, і пункт «прочитати параметри SDRC»
із чотирьох передумов §16 **закрито**.

### Що це змінює

**Підтверджено:** вимога повної послідовності — не Linux-ізм. Та сама
структура є в прошивці цього апарата. Заборона §16 на WRITE лишається чинною.

**Спростовано:** твердження §12/§16, що валідованого рантайм-шляху немає і що
його треба проєктувати з нуля. Він є, разом зі SRAM-мапінгом і relock DLL.

**Новий, точний блокер.** Копіювання в SRAM робиться **один раз на буті**
(єдиний виклик конструктора). Отже ROM-shadow патч, накладений у рантаймі на
`0x800A7F6C`, **не впливає** на код, який реально виконується з SRAM. Наш
перевірений інструмент патча б'є не по тій копії.

### Кандидати далі (ГІПОТЕЗИ, не доведено)

1. Дістати лінійну адресу SRAM-копії й патчити **її**, а не ROM. READ-патч
   (§15) уже дає читання довільної адреси ядра, а patcher func 105 — запис;
   для звичайної памʼяті побайтовий memmove коректний, тож обмеження §10 п.2
   тут **не діє**. Невідоме: де лежить глобальний вказівник на об'єкт
   (`[obj+12]` chunk, `[obj+16]` лінійна адреса). Шукати в даних power.dll.
2. Тригер. Процедура виконується лише на глибокому idle (глибина ≥ 2), який
   ОС обирає сама. Керованого користувацького тригера немає — це окреме
   невирішене питання, і воно робить будь-який WRITE тут погано спостережуваним.
3. Напруга (Menelaus) і межі — як були, не закриті.

**Апарат не чіпаємо.** Ця робота статична, лише за дампом ROM.

## 18. РОЗГІН ДОСЯГНУТО: +5.8% на апараті, підтверджено 2026-08-07

Множник DPLL піднято 86 → 91 у рантаймі на живому RM-320. Підтверджено двома
незалежними приладами, відтворено двічі, повністю оборотно.

```
before   : CLKSEL1=00056400 mult=86  DPLL=330240 kHz   328 MHz (NOP)  17.34 Mitr/s
after    : CLKSEL1=0005b400 mult=91  DPLL=349440 kHz   347 MHz (NOP)  18.35 Mitr/s
restored : CLKSEL1=00056400 mult=86                    328 MHz (NOP)  17.34 Mitr/s
```

| Прилад | До | Після | Зміна |
|---|---|---|---|
| Ланцюг незалежних `add` (абсолютна частота) | 328 МГц | 347 МГц | **+5.7%** |
| ALU-цикл із залежністю по даних | 17.34 Mitr/s | 18.35 Mitr/s | **+5.8%** |
| Обхід 2 МБ повз кеш (смуга L3/SDRAM) | 520 МБ/с | 550 МБ/с | **+5.7%** |
| Розрахунок `19.2*91/5` проти `19.2*86/5` | — | — | +5.81% |

Третій рядок важливий окремо: він доводить, що це **не розгін самого ядра, а
підйом CORE_CLK**, від якого масштабується вся система. Ядро і шина зросли на
той самий відсоток.

Три числа сходяться в межах 0.1 в.п. Витримка під навантаженням: 5 кіл ALU +
перевірка цілісності 1 МБ на кожному колі — **0 хибних слів із 5 МБ**.
Повернення множника дає рівно базові 328 МГц / 17.34 Mitr/s, тобто ефект не
дрейф і не артефакт заміру. `HAL::ECPUSpeed` при цьому, як завжди, показував
незмінні 206438 kHz — ще одне підтвердження, що на нього спиратись не можна.

### Чим це зроблено: три примітиви, зібрані з чужого коду

Жоден із них не потребував ані Kernel DevKit, ані запису у флеш.

1. **Читання довільної адреси ядра.** ROM-shadow патч 16 байтів у тіло
   `dvfs_interface.ldd DoControl(1)` @`0x80148410` → `cmp r1,#0; ldrne r0,[r1];
   moveq r0,#0; bx lr` (§15).
2. **Виконання довільного коду ядра.** Той самий патч, але `bx r1` (4 байти).
   Тіло `DoControl(1)` — це рівно 6 слів `0x80148410..0x80148427`; диспетчер
   починається з `0x80148428` і лишається цілим. Контракт на вході: `r0` = this,
   `r1` = `r2` = `a1`, `r3` затерто диспетчером, `lr` = `0x80148440`. Тобто
   рівно один 32-бітний аргумент.
3. **Плацдарм поза SDRAM.** SRAM-чанк, який `power.dll` мапить на буті
   (§17): фіз. `0x4029E000`, 4 КБ. На цьому апараті лінійна адреса —
   `0xCB202000`; перші 1024 байти займає firmware, ми пишемо зі зсувом
   `+0x800`. Патчер пише туди прямим шляхом (адреса поза ROM), і побайтовий
   memmove тут коректний, бо це звичайна память, а не MMIO — обмеження §10 п.2
   знято.

**Підтверджено по дорозі:** SRAM-чанк доступний на запис, виконуваний і
когерентний за I-cache — блоб `mov r0,#0x5A; bx lr`, записаний туди й
викликаний, повернув `0x5A`. Окремо перевірено виклик заглушки в ROM
(`power.dll @0x800A8264`, `mov r0,#3; bx lr`) — повернув 3.

### Послідовність relock (272 байти, виконується з SRAM)

Порядок — за `omap242x_sram_set_prcm` і за idle-процедурою `power.dll`
@`0x800A7F6C` (§16, §17):

```
IRQ+FIQ off
CM_CLKEN_PLL[1:0] = 2        fast-relock bypass
чекати CM_IDLEST_PLL[1:0]==1
CM_CLKSEL1_PLL = нове        міняються лише біти [21:12]
PRCM_CLKCFG_CTRL = 1         чекати самоочищення
CM_CLKEN_PLL[1:0] = 3        lock
чекати CM_IDLEST_PLL[1:0]==2
SDRC DLLA/DLLB relock        (status&0xFF00)|(ctrl&0xF)|4, потім витримка
IRQ відновити
```

Три деталі, кожна з яких зламала б результат:

- **`EN_DPLL` — це біти [1:0], не [2:0].** Біти [3:2] — це APLL 54 МГц; маска
  `#7` вимкнула б його разом із DPLL. Маску `#3` узято з коду power.dll
  (`and r2,r2,#0xfc`).
- **Жодного зовнішнього `bl` і жодного звернення до SDRAM у критичному вікні.**
  Константи — з власного пулу блоба (`.ltorg` у кінці), тож `ldr [pc,#off]`
  лишається коректним після копіювання. Стек чіпається тільки до і після вікна.
- **Усі три очікування обмежені лічильником** (`0x10000`). Переривання
  вимкнені, тож нескінченний цикл означав би повне зависання з вийманням
  батареї. При таймауті множник не пишеться взагалі, а DPLL примусово
  повертається в lock — тобто відкат.

`SDRC_RFR_CTRL` навмисно **не** чіпаємо: лічильник рахує такти L3, тож на
підвищеній частоті refresh стає лише частішим, а це безпечний напрямок.

### Запас: mult 96 теж стабільний (+11.5%)

| mult | DPLL | MPU (замір) | ALU | Зміна | Пам'ять |
|---|---|---|---|---|---|
| 86 (штат) | 330.2 МГц | 328 МГц | 17.34 Mitr/s | — | — |
| 87 | 334.1 МГц | 331 МГц | 17.53 Mitr/s | +1.15% | 0 помилок |
| **91** | 349.4 МГц | 347 МГц | 18.35 Mitr/s | **+5.8%** | 0 із 5 МБ |
| 96 | 368.6 МГц | 366 МГц | 19.35 Mitr/s | +11.5% | 0 із 5 МБ |

На кожному кроці обидва прилади дали однаковий відсоток, і кожен збігся з
розрахунком `19.2*mult/5`. Відновлення після кожного прогону — точно базові
числа.

**Де зупинились і чому.** Далі йде не межа CPU, а межа SDRAM: `CORE` і `L3`
ростуть разом із DPLL, тож при mult=96 шина вже 184 МГц проти штатних 165
(`SDRC_RFR_CTRL_165MHz` в офіційній таблиці OPP, §16). Відмова там має інший
характер, ніж зависання: не падіння, а **тихе псування даних**, яке може
потрапити у флеш через кеш файлової системи. Перевірка 5 МБ його не виключає —
вона лише не знайшла. Тому подальші кроки (mult 104 ≈ 400 МГц, як штатно в
N810 на тому ж SoC) свідомо не робились: мети досягнуто, а ціна помилки тут —
єдина річ, яку проєкт собі забороняє.

**Робоча рекомендація — mult 91.** Запас до межі SDRAM удвічі більший, ніж
у 96, а мета (≥5%) виконана.

### Дрібне спостереження

`CM_CLKSEL2_PLL` читався то як `2`, то як `1` між прогонами. Отже губернатор
DVFS справді рухає core_sel у рантаймі (пор. §12, де сказано, що масштабуються
дільники). На вимір це не впливає — обидва прилади міряють роботу, а не регістр.

## 19. Чому апарат «перезавантажувався»: I-cache і shadow-сторінка

Чотири «перезавантаження» під час робіт 2026-08-07/08. Розібрано до кінця;
причина виявилась не тією, на яку я думав двічі поспіль.

### Це були НЕ перезавантаження ядра

`User::NTickCount()` рахує тіки нанокернела від старту системи й обнуляється
лише повним ребутом. Замір на апараті після всіх чотирьох подій: **43404 с
≈ 12 год**, і це рівно збігається з часом останнього справжнього
перезавантаження (з логотипом), яке було напередодні.

**Отже ядро не падало жодного разу.** Те, що виглядало як перезавантаження, —
перезапуск оболонки Symbian після загибелі користувацького системного процесу.
Побічне підтвердження: демон доставки після цих подій не піднімався сам, бо
його стартовий запис відпрацьовує на буті, а не при перезапуску оболонки.

**Урок про методику.** Спершу я «доводив» відсутність ребута мережевою
доступністю. Це не доказ: апарат встигає піднятись між перевірками. Прямий
вимір uptime — доказ, і його треба було ставити з самого початку. Пробник
тепер друкує `UPTIME:` першим рядком кожного прогону.

### Справжня причина: перезапис байтів не знімає патч

Патч тіла `DoControl(1)` накладається записом через patcher, і **жоден шлях
патчера не робить `Cache::IMB`** — це було записано як відкрита гіпотеза ще в
§14. Наслідок: пропатчена функція вже виконувалась, її інструкції лежать в
I-cache, а запис *даними* кеш не інвалідовує. Процесор далі виконує стару,
пропатчену копію — «відновлення» відбувається лише в пам'яті.

Спостережено прямо, тим самим тестом на тому ж апараті:

| Спосіб зняття патчу | `DoControl(1,0)` після нього | Що це означає |
|---|---|---|
| перезапис оригінальних байтів | **0** | патч ЖИВИЙ (0 — відповідь патчу на `a1=0`) |
| + `FreeShadowPage` | **50** | штатний код, реальний відсоток від номіналу |

Отже після кожного нашого прогону в системі лишалась **жива** підмінена
функція. Канал `dvfs_interface` відкриває не лише наш код (§15:
`mmrmserver.dll`, `fmradiotunercontrol.dll`), і їхній виклик `DoControl(1, a1)`
з ненульовим `a1` отримував замість відсотка сміття з `ldr r0,[r1]`. Падав
системний процес — оболонка перезапускалась.

### Рішення: у патчера для цього є штатний опкод

Розбір `patcher_code.asm` дав повну картину shadow-механізму:

| Адреса | Ординал ekern | Роль |
|---|---|---|
| `0x8410` | **240** `AllocShadowPage` | виділяє RAM-сторінку під сторінку ROM; кличеться сама на кожному записі в ROM-регіон |
| `0x848c` | **238** `FreeShadowPage` | звільняє її, повертає відображення на ROM |
| **опкод каналу 100** (`0x8694`→`0x8724`) | — | `DoControl(100, &addr, &len)` → `0x848c` по діапазону |

Тобто штатний спосіб прибрати за собою був у патчері весь час. `FreeShadowPage`
викидає RAM-копію і повертає відображення на справжній ROM — разом із коректним
обслуговуванням кешу, чого сам по собі запис не дає.

`COcEngine::EndPatchSession()` тепер робить обидва кроки: спершу перезапис
оригінальних байтів (щоб вміст сторінки був штатним, якщо unshadow колись не
спрацює), потім `UnshadowKernelPage()`. Перевірка результату — **після**
unshadow, а не після запису.

### Бісекція, якою це доведено

Пробник має рівні (`patcher level 0..3`), кожен лишає по собі рівно на одну річ
більше. Після виправлення всі чотири чисті, uptime між ними неперервний:

| Рівень | Що робить | Результат |
|---|---|---|
| 0 | завантажити `patcher.ldd`, відкрити канал | чисто |
| 1 | + запис func 105 у власний буфер | чисто |
| 2 | + READ-патч, читання, повне зняття | чисто, `restore check -> 50` |
| 3 | повний `Prepare` | чисто, `restore check -> 50` |

**Побічний висновок, важливий на майбутнє:** ніщо з цього не писало у флеш і
не пошкодило апарат — усі чотири події лікувались перезапуском оболонки. Модель
безпеки проєкту (все рантаймове) витримала навіть при тому, що конкретна
реалізація була дефектною.

## 20. Розгін із живим дисплеєм: SDRAM у вікні переходу

Безголовий прогін `patcher oc 96` (+11.5%) проходив стабільно, а той самий
двигун із застосунку зависав намертво вже на `mult 88`. Різниця не в множнику,
а в **навантаженні на SDRAM під час вікна переходу**.

Під час bypass CORE дорівнює `sys_clk`, тобто L3 і SDRAM їдуть із 165 МГц до
~5 МГц — і так весь час, поки DPLL захоплюється. Чим більший крок множника, тим
довше захоплення, тобто довше вікно. Безголовий прогін це переживав, бо
контролер дисплея не працював; у застосунку DSS безперервно читає кадровий
буфер із SDRAM, і перехід її ламає.

**Виправлення (обидва — з вендорського коду цього ж SoC):**

1. **SDRAM у self-refresh перед вікном.** `SDRC_POWER |= 0x48` (біт 6
   `SRFRONIDLEREQ`, біт 3 `EXTCLKDIS`) — рівно те й рівно там, де це робить
   idle-процедура `power.dll` @`0x800A7F6C` (§17). Я скопіював послідовність
   PLL, але проґавив її підготовку SDRC — це було упущення, не невідомість.
2. **Апаратний відкат усередині критичної секції.** Якщо DPLL не захопився,
   блоб повертається в bypass, пише **початковий** множник і захоплюється на
   ньому — усе поки переривання ще вимкнені. Без цього DPLL лишався в bypass,
   MPU падав до ~9.6 МГц, і апарат виглядав як намертво зависший, хоча
   формально був живий; лікувалося лише вийманням батареї.

Блоб тепер має **два** слова-заглушки: `0xDEADBEEF` — цільове значення,
`0xFEEDFACE` — початкове. Обидва мусять знайтись при підстановці, інакше блоб
не виконується взагалі. Біти статусу: 1 = таймаут bypass, 2 = таймаут CLKCFG,
4 = таймаут lock (спробувано відкат), 8 = відкат теж не вдався.

### Головна причина зависань у GUI: EXEC-патч був небезпечний для чужих викликів

Гіпотеза «довге вікно bypass» **спростована експериментом**: підйом сходинками
по одному пункту (кожен крок — той самий, що стабільно працює окремо) теж вішав
апарат. Отже справа не в довжині одного вікна, а в **кількості вікон**.

Причина конструктивна. EXEC-патч робив тіло `DoControl(1)` рівним `bx r1` —
стрибок за адресою з аргументу. Але канал `dvfs_interface` відкриваємо не лише
ми (§15): у застосунку з живим інтерфейсом активні `mmrmserver.dll` і віконний
сервер. Будь-який їхній `DoControl(1, a1)`, що потрапив у наше вікно, змушував
ядро стрибнути за **чужою** адресою. Безголово цього не траплялось, бо ці
клієнти не працювали; у GUI траплялось, і сходинковий підйом лише помножив
кількість спроб.

**Виправлення:** патч тепер стрибає **тільки на одну очікувану адресу** (наш
слот у SRAM), а всім іншим повертає 0 — так само безневинно, як READ-патч на
`a1=0`:

```asm
ldr  r0, [pc, #12]     ; дозволена адреса (підставляється зовні)
cmp  r1, r0
bxeq r1                ; стрибок ЛИШЕ якщо адреса та сама
mov  r0, #0
bx   lr
.word <slot>
```

Рівно 6 слів = 24 байти, тобто точний розмір оригінального тіла. Байти патчу
беруться з асемблерного шаблону (`OcExecPatchStart/End`), а не з масиву
констант: кодування інструкцій рахує асемблер, не людина.

**Урок:** підмінюючи функцію ядра, треба виходити з того, що її викличе не лише
твій код. Патч мусить бути безпечним для будь-якого викликача — інакше вікно
експозиції рано чи пізно спрацює як міна. Це та сама помилка, що й у §15, лише
з іншого боку: там я хибно вважав функцію нікому не потрібною, тут — хибно
вважав, що встигну прибрати патч до чужого виклику.

### Заразом виправлено в застосунку

- **Повний екран.** `CAknAppUi::ENoScreenFurniture` прибирає статусну стрічку й
  панель софт-клавіш; rect береться з `ApplicationRect()`, а не `ClientRect()`
  (останній повертає область під furniture, якого вже немає).
- **Поворот екрана.** `HandleResourceChangeL(KEikDynamicLayoutVariantSwitch)`
  переставляє rect. Без цього в ландшафті лишався вертикальний прямокутник —
  саме тому результати читались нормально лише в одній орієнтації.
- **Результати не було видно.** Розкладка вимагала ~360 px при доступних ~268:
  тести працювали, але лог малювався за краєм екрана. Тепер дрібний
  `AnnotationFont` і явне обрізання по `yMax`.

## 21. Дисплей тактується від CORE: карта полів CM_CLKSEL1_CORE

Симетричне спостереження на апараті закрило питання: множник **77 (вниз) вішає
так само**, як 88 (вгору). Отже справа не в "занадто швидко" - ламається
**будь-яка** зміна CORE, і ламається саме відрисовка. Прошивка так не робить:
`dvfs_conf.dll` розсилає сповіщення до і після зміни (§2), а ми цей шлях
обходимо, тож драйвер дисплея не знає, що його частота поїхала.

### Карта полів (виведено з сеттерів power.dll)

`power.dll @0x800AC458..0x800AC598` - сім функцій, кожна валідує значення,
зсуває його і кличе `Modify32(CM_CLKSEL1_CORE, маска, значення)`. Маски й зсуви
читаються прямо з коду:

| Маска / зсув | Біти | Поле | Допустимі значення (з валідації) |
|---|---|---|---|
| `0x1F` / 0 | [4:0] | L3 | **не 0, 3, 5, 9, 18** (виправлено, див. нижче) |
| `0x60` / 5 | [6:5] | L4 | 1, 2 |
| **`0x1F00` / 8** | **[12:8]** | **DSS1** | не 18 |
| `0x2000` / 13 | [13] | DSS2 | 0, 1 |
| `0xF8000` / 15 | [19:15] | VLYNQ | не 5 |
| `0x1F00000` / 20 | [24:20] | SSI | 1,2,3,4,6,8 |
| `0xE000000` / 25 | [27:25] | USB | 1, 2, 4 |

Розклад збігається з заголовками Linux для OMAP2420 (`cm-regbits-24xx.h`) -
два незалежні джерела, як і для мапінгу периферії в §4.

> **ВИПРАВЛЕНО 2026-08-15, і ця помилка коштувала дорого.** Для L3 тут стояло
> «не 18», тобто «дозволено все, крім 18». Насправді валідатор @`0x800AC424`
> читається так:
>
> ```
> 800ac424: cmp   r1, #5
> 800ac42c: beq   reject            ; 5
> 800ac430: bgt   0x800ac444
> 800ac434: cmp   r1, #0
> 800ac438: cmpne r1, #3
> 800ac43c: bne   accept            ; тобто 0 і 3 - reject
> 800ac444: cmp   r1, #9
> 800ac448: cmpne r1, #18
> 800ac44c: bne   accept            ; тобто 9 і 18 - reject
> ```
>
> Відкидаються **0, 3, 5, 9, 18** — той самий за формою перелік, що й у сеттера
> дільника DSP (0, 5, 9, 16, 18). Наслідок помилки: `CompensatedCore()`
> підбирав `l3div=5` на множниках 99..111, апарат такого запису **не бере
> взагалі**, і `CM_CLKSEL1_CORE` лишався незмінним цілком — разом із полем DSS1,
> яке саме по собі було коректним. Тобто компенсація дільників на цих множниках
> **ніколи не працювала**, і виглядало це збоку так, ніби її хтось знімає. Повний
> розбір із замірами — §26.

> **ВИПРАВЛЕНО.** Спершу я виписав допустимі значення SSI як «0,2,3,4,5,7,9».
> Це помилка декодування таблиці переходів: у ARM `pc` читається як адреса
> інструкції **+8**, тож для `addls pc, pc, r1, lsl #2` @`0x800AC520` ціль
> дорівнює `0x800AC528 + r1*4`, а не `0x800AC524 + r1*4`. Правильно:
> **допустимі 1,2,3,4,6,8; відкидаються 0,5,7.** Практичний наслідок нижче -
> SSI не компенсується точно ні на 96, ні на 129.

Наше значення `0x04360644` розкладається так: L3=4, L4=2, **DSS1=6**, DSS2=0,
VLYNQ=6, SSI=3, USB=2. Тобто дисплей тактується `CORE/6` = **110.08 МГц**, і
підіймаючи CORE ми підіймали його разом із нею.

> **ВИПРАВЛЕНО 2026-08-08.** Наведене нижче міркування («панель терпить
> приблизно +1%, і в діапазоні 87..91 компенсувати нічим») **спростоване
> замірами на апараті.** На mult 107 апарат повністю стабільний, а DSS1 там

> дисплея щонайменше +6.6%, а межа 87/88 мала іншу причину: найімовірніше

> Текст лишено як приклад того, як не треба виводити поріг з двох точок.

### Початкове (хибне) міркування про допуск дисплея

Дільник цілочисельний, тож на mult 87..91 він мусить лишатися 6:

|---|---|---|---|
| 87 | 111.36 МГц | +1.2% | працює |
| 88 | 112.64 МГц | +2.3% | вішає |
| 91 | 116.48 МГц | +5.8% | вішає |

Тобто панель терпить приблизно +1%, і компенсувати в цьому діапазоні нічим -
дільника 6.13 не існує. Це не наш дефект, а межа апаратної роздільності.

### Рішення: компенсувати дільники в тій самій фіксації

Блоб тепер пише `CM_CLKSEL1_CORE` **разом** із `CM_CLKSEL1_PLL`, до однієї
фіксації `CLKCFG_CTRL`. Це важливо: одна фіксація латчить і множник, і
дільники, тож L3 та DSS ніколи не бачать нову CORE зі старим дільником.
Шлях відкату так само повертає обидва регістри.

Політика підбору різна для двох доменів, і навмисно:

- **DSS1 - точна компенсація** до найближчого. Дисплею не потрібна вища
  частота, йому потрібна СВОЯ.
- **L3/SDRAM - тримаємо якнайвищою** в межах +15% від штатної. Компенсувати її
  "до найближчого" було б помилкою: на mult 96 це опустило б памʼять **нижче**
  штатної, тоді як замір показав 0 помилок при +11.5%.

Що з цього виходить (перевірено розрахунком, mult 96 - на апараті):

| mult | CPU | L3 (діл.) | DSS1 (діл.) |
|---|---|---|---|
| 86 штат | 330.2 | 165.1 (4) | 110.08 (6) |
| 96 | 368.6 | 184.3 (4) **+11.6%** | 105.3 (7) **-4.3%** |
| 100 | 384.0 | 153.6 (5) -7.0% | 109.7 (7) **-0.3%** |
| **129** | **495.4** | **165.1 (6) 0.0%** | **110.08 (9) 0.0%** |

**mult 129 особливий:** `129/86 = 1.5`, і обидва дільники масштабуються рівно
на 1.5 (4→6, 6→9). Це "чистий розгін процесора": +50% на ядрі, а шина й дисплей
лишаються **точно** на штатних частотах. Чи витримає кремній 495 МГц - окреме
питання (N810 на тому ж SoC штатно 400 МГц), але з боку тактування конфігурація
ідеальна.

Перевірено на апараті (mult 96): `CLKSEL1_CORE 04360644 -> 04360744`,
`status=0`, памʼять +11.0%, 0 хибних слів.

### Незакрите

Процесорні прилади дають стабільно **менший** приріст, ніж розрахунок: на mult
96 це +8.3..8.9% замість +11.6%, тоді як шина масштабується точно (+11.0%).
Два незалежні CPU-інструменти збігаються між собою, тож це не помилка заміру.
Найімовірніша гіпотеза - губернатор DVFS рухає дільник MPU, побачивши вищу
CORE. Перевіряється читанням `CM_CLKSEL_MPU` під навантаженням.

Інтерфейс телефона й емуляція «працюють значно швидше» (спостереження

Рядок **mult 129** тут вирішальний: L3 і DSS1 виставлені **точно** на штатні

> **УТОЧНЕНО 2026-08-08 (з апарата).** Нижче стояло «mult 107 для щоденного

щоденним використанням. **mult 107** — якщо потрібен запас: +24.4%, шина в межах
0.5% від штатної, теж повністю перевірений.

Для **чужих** апаратів у публічній збірці за замовчуванням лишити 107: там немає
ні тривалої перевірки, ні гарантії тих самих умов охолодження.

Усе рантаймове: перезавантаження повертає апарат у штатний стан, у флеш не
пишеться нічого.

## 23. Домен DSP: як прошивка рахує частоту C55x (виведено з ROM)

Приводом стало завдання від сусіднього проєкту `../TMS320C55x test` —
`docs/TASK_DSP_CLOCK.md`. Там зміряно ~50 MMAC/s і висунуто гіпотезу, що C55x
тактується вдвічі нижче за номінал. Нижче — тільки те, що випливає з коду ROM;
на апараті це ще **не** перевірялось.

**`CM_CLKSEL_DSP` = `0x48008840` (вірт. `0xC6008840`).** Адреса не з даташита:
її вантажить сама `power.dll` із літерала `@0x800B16F4`, і другим джерелом —
сеттери в `ehwaomap.pdd`, які роблять `str r1,[r0,#0x840]` від бази PRCM.

**Прошивка рахує «частоту DSP» як `CORE / CM_CLKSEL_DSP[3:0]`.** Ординал 60
`power.dll` @`0x800B1620`:

```
bl   0x800b15b0      ; CORE, кГц
cmp  r5, #1          ; аргумент != 1 -> 0
ldr  r0, [pc,#176]   ; 0xc6008840
bl   0x800b1c60      ; read32
ands r1, r0, #15     ; МАСКА 0xF, тобто [3:0]
bl   0x800b1c18      ; CORE / поле
mul  r4, #1000, r0
```

Одиниці зійшлися до числа: `0x800B1544` повертає DPLL у **МГц** (sys_clk із
`[25:23]` в одиницях 0.1 МГц: 0→192, 2→130, інше→120; далі `×mult`,
`/(div+1)`, `/10`) = 330; `0x800B15B0` множить на `CM_CLKSEL2_PLL[1:0]` і на
1000 → CORE = 660000 кГц; `ord60(1)` при полі 6 дає 660000/6·1000, а
`ehwaomap.pdd` ділить на 1000 і кладе в `_BRIDGEINIT_DSP_FREQ` → **110000**.
Це рівно те бімодальне значення (110000/220000), яке спостерігав замовник.

**Наслідок — знято неоднозначність полів.** З самих сеттерів PDD не видно, яке
поле тактує C55x: вони чіпають `[7]`, `[6:5]`, `[12:8]` і `[13]`, а низького
поля не чіпають узагалі. Але прошивка рахує частоту DSP саме з низького поля,
тож дільник C55x — воно. Те, що сеттери його не чіпають, означає лише, що в
рантаймі прошивка його не змінює (виставляється на буті).

**Спростована гіпотеза (моя, не замовникова).** Я припустив, що `ord60` може
віддавати інтерфейсний клок `[6:5]`, і тоді ядро сиділо б на 220, а 110 було б
артефактом звіту. Код це виключає: `[6:5]` у формулу не входить взагалі.

**Дрібниця з наслідком.** `ord60` маскує `0xF`, хоч даташит дає полю 5 бітів
`[4:0]`. При дільнику ≥16 штатний репортер брехав би — а `_BRIDGEINIT_DSP_FREQ`
для замовника і є основним індикатором. Для значень 3 і 6 нерелевантно.

**Запис у `CM_CLKSEL_DSP` не потребує латча `PRCM_CLKCFG_CTRL`:** сеттер у PDD
@`0x801AE900` — звичайний `ldr`/`bic`/`orr`/`str`, коміту не робить.

**Варіант WRITE-патча `strne r2,[r1]` із завдання неможливий** — доведено з
диспетчера `dvfs_interface` @`0x80148428`:

```
cmp  r1, #1
mov  r3, #0        ; a2 приходить у r3 і знищується ТУТ
stmdb sp!, {r4,lr}
bne  0x80148444
mov  r1, r2        ; r1 = a1
bl   0x80148410    ; тіло: r1 == r2 == a1
```

У пропатчене тіло `a2` не доїжджає ніколи, а `r2` дорівнює `r1`, тож такий
патч записав би адресу саму в себе. Якщо доходитиме до запису — робити його
наявним EXEC-шляхом (блоб у SRAM + EXEC-патч, стрибок дозволено рівно на одну
адресу), а не новою формою патча: WRITE-патч повернув би небезпеку для чужих
клієнтів `dvfs_interface` у гіршому вигляді, ніж READ.

## 24. Домен DSP на апараті: дільник уже штатний, і чому «110 МГц» — міраж

Прогін `patcher dsp` на RM-320 (2026-08-11, апарат у простої):

```
CM_FCLKEN_DSP @c6008800 = 00000401
CM_ICLKEN_DSP @c6008810 = 00000002
CM_IDLEST_DSP @c6008820 = 00000000
CM_CLKSEL_DSP @c6008840 = 000023c3
fields: DSP[3:0]=3 [4:0]=3  IF[6:5]=2  bit7=1  IVA[12:8]=3  bit13=1
```

12 знімків за 3 с — **жодної зміни**, одне-єдине значення `0x23C3`.

**Дільник DSP = 3, тобто C55x на 220.16 МГц — на номіналі.** Гіпотеза сусіднього
проєкту «DSP сидить на половині частоти» **спростована на апараті**.

### 24.1. Звідки бралися «110 000» — і чому це не про DSP

Ланцюг замикається без жодного припущення:

1. `ord60(1)` рахує `CORE / CM_CLKSEL_DSP[3:0]` (§23);
2. `CORE = DPLL × CM_CLKSEL2_PLL[1:0]`;
3. а `CM_CLKSEL2_PLL[1:0]` **сам ходить між 1 і 2** — це вже задокументовано в
   цьому проєкті (§12, §18) і закодовано в `Prepare()`, який саме тому знімає
   серію під навантаженням і бере максимум, а не вірить миттєвому відліку.

Отже при `sel2 = 2` виходить `660480/3 = 220160`, при `sel2 = 1` —
`330240/3 = 110080`. Рівно ті дві групи, що їх бачив замовник, з тим самим
відношенням. Дільник DSP при цьому не змінювався **жодного разу**.

Це збігається і з їхнім власним контрольним спостереженням (`DSP_GUIDE.md`
§14.3): пропускна здатність між «110» і «220» прогонами **не мінялась**. Їхній
же висновок у §14.3 був правильний, а пізніший §15.4 («C55x майже завжди на
110 МГц») — ні; §15.4 треба вважати спростованим.

**Наслідок для їхніх чисел:** MAC/такт рахувалися при 220 МГц, і це припущення
підтвердилось. Перерахунок не потрібен.

### 24.2. Прошивка цей регістр не змінює взагалі

Літерал `0xC6008840` зустрічається в усьому образі ROM (60 МБ) **рівно двічі**,
обидва рази в `power.dll`: у пулі констант сеттерів і в пулі `ord60`. Адреси
обох сеттерів (`0x800AC59C` у power.dll, `0x801AE900` у ehwaomap.pdd) в образі
**не зустрічаються жодного разу** — ні як ціль `BL`, ні в таблицях експорту.
Тобто обидві функції — мертвий код. Тому знятий на старті дільник можна брати
за опорний: сам собою він не «попливе».

### 24.3. Робочий шлях зміни: кликати штатний сеттер, а не писати регістр

Реалізовано в `COcEngine::ApplyDspDiv`. Трамплін у SRAM-слоті ставить `r1 =
дільник` і робить `blx` на `0x800AC59C` **прямо в ROM** (не копіюючи: усі власні
`bl` функції лишаються коректними). EXEC-патч, як і завжди, дозволяє стрибок
рівно на одну адресу.

`Modify32` (@`0x800A1C50`) розібрано й визнано безпечним для виклику з нашого
контексту — це leaf-функція без блокувань:

```
mrs ip,cpsr / orr r3,ip,#0xC0 / msr cpsr   ; IRQ+FIQ off
ldr r3,[r0] / bic r3,r3,r1 / orr r3,r3,r2 / str r3,[r0]
mcr p15,0,r3,c7,c10,5                      ; DMB
msr cpsr,ip / bx lr
```

тобто `Modify32(addr, clearMask, setBits)`.

**Поручні беремо в прошивки.** Сеттер відкидає значення 0, 5, 9, 16, 18
(повертає `-6`); решту 1..31 приймає. Ми додатково відсікаємо >31: сеттер їх
пропускає, а `Modify32` маскує `0x1F`, тож 32 записало б у поле 0 і зупинило
клок DSP.

### 24.4. ГОЛОВНЕ: запису в регістр НЕ ДОСИТЬ, потрібна фіксація

Перевірено прямо на апараті. Перша версія трампліна робила тільки виклик
сеттера:

```
ApplyDspDiv(2) -> r=0, firmware setter rc=0
after:  div=3      <-- регістр НЕ змінився
MISMATCH: register did not take the value
```

Сеттер відзвітував успіхом, а поле лишилось старим. Нове значення латчиться
лише записом `1` у `PRCM_CLKCFG_CTRL` (`+0x80`) — тим самим латчем, яким
relock-блоб цього проєкту фіксує `CLKSEL1_CORE` і `CLKSEL_MPU` (§21). Штатний
сеттер цього не робить — і це, найпевніше, і є причина, чому він ніде не
викликається: у наявному вигляді він просто не працює.

Після додавання фіксації (під вимкненими перериваннями, бо губернатор DVFS
користується тим самим латчем для `CM_CLKSEL2_PLL`):

```
before: div=3 -> DSP 220160 kHz
ApplyDspDiv(2) -> r=0, firmware setter rc=0
after:  div=2 -> DSP 330240 kHz
register confirmed by read-back
after 3 s: div=2 (system alive)
```

**Дільник DSP змінюється в рантаймі: 3 → 2, тобто 220.16 → 330.24 МГц (+50%).**
Ні CORE, ні SDRAM, ні дисплей, ні USB не зачіпаються. Відкат на виході
підтверджено окремим прогоном: `0x23C3` на місці.

### 24.5. Дільник 2 не можна ЛИШАТИ: два перезавантаження з двох

Хронологія, у порядку виконання:

| # | що робилось | результат |
|---|---|---|
| 1 | `sweep.ps1 -Runs 3`, дільник 3 (штатний) | min 1 136 260 мкс, розкид 5%, **ok=3/3** |
| 2 | `patcher dsphold 2` — дільник 2 **лишено** в системі | застосовано, підтверджено читанням |
| 3 | той самий `sweep.ps1 -Runs 3` при дільнику 2 | **апарат втрачено, ребут** |
| 4 | `patcher dspset 2 120` — дільник 2 **всередині процесу**, 120 с | 24 семпли по 5 с, `div=2` весь час, **апарат живий**, відкат на виході |
| 5 | `patcher dsphold 2` — дільник 2 знову **лишено** | застосовано, процес вийшов чисто |
| 6 | нічого не робилось, апарат у простої | **ребут сам собою** |

**Вузол DSP ні до чого.** Крок 6 — це те саме падіння, що й крок 3, але без
жодного DSP-навантаження: базовий образ не вантажився, задача не створювалась,
бенчмарк не запускався. Отже гіпотези §24.5 у попередній редакції — «C55x не
тримає 330 МГц» і «DSP/BIOS з чужими таймінгами» — обидві **не пояснюють крок
6**, бо на DSP там не виконувалось нічого.

Продовження, з розрізняльними прогонами:

| # | що робилось | результат |
|---|---|---|
| 7 | `dspset 2 240 quiet` — один сон на 240 с, **жодних прокидань**, система вільна піти в глибокий retention | **чисто**, `div=2` на виході |
| 8 | `dspset 2 180 child` — дільник тримає наш процес, усередині вікна запущено `dsptest baseonlydcdopnobench` (завантаження базового образу DSP, без вузла й бенчмарку) | **апарат помер**; лог на `E:` обірвався рівно на `child: started` |

### 24.6. ВИПРАВЛЕННЯ ВЛАСНОГО ВИСНОВКУ: справа не у «володінні процесом»

Вище (редакція від 2026-08-11) я записав, що живі й мертві прогони розрізняє
час життя дільника відносно нашого процесу, і що причина — idle/retention.
**Обидва твердження хибні, і крок 8 їх спростовує:** дільник тримав наш живий
процес, і апарат усе одно помер. Крок 7 окремо спростовує підозру на retention —
240 секунд глибокого простою на дільнику 2 пройшли без наслідків.

Правильне узагальнення всіх шести точок одне й просте:

> **Домен DSP на 330 МГц живий, поки на C55x нічого не виконується, і падає, щойно
> DSP піднімають.**

- кроки 4 і 7 (120 с семплювання і 240 с глибокого простою) — DSP **простоює**,
  жодного коду на ньому не виконується: чисто;
- крок 8 — завантаження базового образу, тобто **старт DSP/BIOS на C55x**: смерть;
- крок 3 — те саме плюс вузол: смерть;
- крок 6 — дільник лишили в системі, апарат «у простої»: смерть настала не
  одразу. Це та сама причина: рано чи пізно домен DSP піднімає щось штатне
  (аудіо, сповіщення, радіо), і в цю мить усе повторюється. «Ребут сам собою»
  був не спонтанним, а відкладеним.

Тобто ребут спричиняє не нештатний дільник як запис у регістр, а **виконання
коду на C55x при CORE/2**.

### 24.7. Наслідок: дільником DSP розігнати не можна, а множником — уже розігнано

Дільник цілочисловий, тож зі штатних 3 єдиний крок угору по частоті — це 2,
тобто одразу **+50%**. Проміжних значень не існує. А 330 МГц C55x не тримає.
Отже **важіль дільника для розгону непридатний** — надто грубий.

Але DSP тактується від CORE, і множник DPLL його вже піднімає. При робочому
`mult 111` виходить `852480/3 = 284.16 МГц`, тобто **+29% до DSP** — і цей режим
апарат тримає щодня, включно з аудіо (§22). Тобто:

| частота C55x | звідки | стан |
|---|---|---|
| 220.16 МГц | штат, `mult 86`, дільник 3 | — |
| **284.16 МГц** | `mult 111`, дільник 3 | **працює щодня, перевірено** |
| 330.24 МГц | `mult 86`, дільник 2 | **валить апарат при роботі DSP** |

Межа C55x при штатній напрузі лежить між 284 і 330 МГц. Тобто розгін DSP на
цьому апараті вже досягнутий — як побічний ефект розгону ядра, і рівно в тому
обсязі, який кремній витримує.

**Що дільник лишається вартим:** рух у ІНШИЙ бік (4, 6, 8 — тобто 165, 110, 82
МГц) безпечний за побудовою і дає економію живлення, коли DSP не потрібен.

**Правило проєкту спрацювало як слід:** нічого у флеш не писалось, патч ядра
знімався до кінця кожного прогону, і перезавантаження щоразу повертало апарат у
штатний стан. Лог із `Flush` на кожен рядок пережив падіння й показав саме ту
секунду, на якій усе сталось, — без нього крок 8 був би ще однією здогадкою.

## 25. Чому бенчмарк C55x нижчий за очікуваний: що додає цей проєкт

Сусідній проєкт (`CHARACTERIZATION.md` §8) міряє 45–67 мільйонів машинних
операцій за секунду **незалежно від типу коду** і робить із цього висновок:
«реальна робоча частота близько 60 МГц, а не номінальні 220». Гіпотеза причини —
`ivapolicyserver.exe` тримає DSP у низькому режимі, бо його ніхто не запитав.

Дані цього проєкту дозволяють викреслити одне й додати два.

### 25.1. Викреслюється: «низький режим» через дільник

Хоч би що робив `ivapolicyserver`, **через `CM_CLKSEL_DSP` він цього не робить**:
поле стабільне (§24), а обидва штатні сеттери цього регістра в усьому ROM
мертві — не викликаються й не експортуються (§24.2). Дільника, який «хтось
опустив», не існує. Шукати треба або в напрузі, або в стелі.

### 25.2. «60 МГц» і «220 МГц із рівномірним стопором» — це той самий вимір

Висновок §8 спирається на те, що всі навантаження дають ту саму кількість
операцій за секунду. Але рівномірний стопор дає **точно такий самий підпис**, як
учетверо нижчий такт: якщо кожна вибірка інструкції коштує зайвих тактів, це
однаково гальмує і Q15, і fp32, і ділення.

Контрольне ядро `dsp_reg_mac` цього не розрізняє. Воно прибирає звернення до
**даних**, але код при цьому вибирається звідти ж, звідки й раніше. Тобто
перевірено «дані не є вузьким місцем», а не «пам'ять не є вузьким місцем».

**А ось такт тепер відомий прямо з заліза:** `CM_CLKSEL_DSP[3:0] = 3`, тобто
`CORE/3` = 220.16 МГц (або 110.08 на нижчій OPP, див. далі). Ніяких 60 МГц у
регістрі немає. Отже пояснення «низький такт» на апаратному боці **закрите**, і
залишковий розрив мусить пояснюватись стопорами — найпершим кандидатом лишається
вибірка інструкцій вузла.

### 25.3. Додається: частота DSP заручник ARM-губернатора

`DSP = CORE / 3`, а `CORE = DPLL × CM_CLKSEL2_PLL[1:0]`, і це поле **само ходить
між 1 і 2** під губернатором DVFS (§12, §18). Тобто DSP іде то на 220.16, то на
110.08 МГц — і не тому, що хтось керує DSP, а тому, що керують ARM.

Під час DSP-бенчмарку ARM **заблокований в очікуванні** результату, тобто з боку
губернатора виглядає як простій. Найприродніший наслідок: OPP опускається, CORE
падає вдвічі, і DSP разом із ним.

Це пояснює й ту особливість їхніх даних, яку вони приписали витісненню
аудіо-стеком: оцінки **монотонно спадають** зі зростанням обсягу роботи
(88.1 → 68.2 → 55.6 MMAC/s). Що довше DSP рахує на самоті, то більшу частку
часу губернатор тримає низьку OPP, то нижча гранична швидкість. Витіснення
аудіо такої монотонності не передбачає, а цей механізм — передбачає.

Це ж пояснює й бімодальні `_BRIDGEINIT_DSP_FREQ` (§24.1): той самий механізм,
той самий множник 2.

### 25.4. Два дешеві досліди, які це перевіряють

1. **Зайняти ARM під час DSP-роботи** (окремий потік у циклі). Якщо частина
   розриву від губернатора, числа мусять піти вгору, до ×2. Робиться цілком на
   їхньому боці, апарат не ризикує нічим.
2. ~~Прогнати той самий бенчмарк при `mult 111`.~~ **ЗРОБЛЕНО, див. §25.5.**

### 25.5. Дослід поставлено: робота C55x строго тактозалежна

Той самий вузол, той самий `dsptest`, ті самі бінарники (`-SkipBuild`), 3 прогони
на точку, підсумок — мінімум серії:

| CORE | частота DSP | час, мкс | розкид |
|---|---|---|---|
| `mult 86` (штат) | 220.16 МГц | **1 136 260** | 5% |
| `mult 111` | 284.16 МГц | **882 995** | 15% |

Прискорення **28.7%**. Чисте масштабування за тактом передбачає
`284.16/220.16 − 1 = 29.1%`. Збіг у межах чверті відсотка.

**Що з цього випливає:**

1. **Час бенчмарку майже цілком визначається виконанням на DSP.** Якби вагому
   частку становили фіксовані накладні (створення вузла, обмін повідомленнями,
   ARM-бік), приріст був би помітно меншим за тактовий.
2. **Прихованого «режиму продуктивності», який тримає DSP, немає.** Машина
   відгукується рівно на ту частоту, яку ми виставили в `CM_CLKSEL_DSP`/DPLL.
   Гіпотеза «`ivapolicyserver` тримає DSP унизу, там схований резерв ×3–4»
   (`CHARACTERIZATION.md` §8) цим **не підтверджується**: політика, яку ніхто не
   запитав, не масштабувалася б лінійно з CORE.
3. **Отже дефіцит — не в частоті, а в тактах на операцію.** ~67 M оп/с при
   220 МГц — це ~0.3 операції за такт, і ця величина стала. Шукати треба
   рівномірний стопор: найпершим кандидатом лишається вибірка інструкцій вузла
   (§25.2), який їхнє контрольне ядро `dsp_reg_mac` не перевіряє, бо прибирає
   звернення до даних, а не до коду.
4. **Побічно — готовий виграш для замовника:** при `mult 111` DSP іде на
   284.16 МГц, і бенчмарк це бачить як −22% часу. Ніяких змін у їхньому коді не
   потрібно.

Розкид на 111 більший (15% проти 5%) — очікувано, бо на вищій CORE губернатор
рухає OPP тими самими кроками, але від вищої бази.

## 26. Дільник MPU і повна розкладка клоків: інструмент є, замір ще не зроблено

Завдання — `docs/TASK_MPU_DIVIDER.md` від сусіднього проєкту `../PS1Emulator`.
Йому потрібна конфігурація, у якій змінилась частота ядра, а частота шини — ні:
без такої пари відношення часу кадру не розділяє «впирається в ЦП» і
«впирається в пам'ять», бо множник DPLL рухає обидва домени на одні й ті самі
відсотки.

Зроблено 2026-08-15. Три прогони на апараті відповіли на питання §5 завдання і
заразом знайшли справжню причину того, що замовник описав як «дільники не
тримаються». Причина виявилась зовсім інша, ніж припускали обидва проєкти.

### 26.0. Головне: недійсний дільник відкидає ВЕСЬ запис у CM_CLKSEL1_CORE

Компенсація дільників не «жила секунди» — вона **не записувалась узагалі**.
Читання назад робиться в тій самій операції, що й запис, тож ніякого вікна, у
якому щось могло б її зняти, тут немає.

Чотири заміри. Кожен — знімок до, одразу після запису, далі раз на 10 с, і
повернення штатного стану на виході.

| прогін | mult | l3 | dss | записалось |
|---|---|---|---|---|
| 2 | 86 | 6 | 6 | **так** |
| 3 | 107 | 5 | 7 | ні |
| 5 | 107 | 6 | 7 | ні |
| 6 | 107 | 6 | 6 | **так** |

Прогони 5 і 6 різняться **лише полем DSS1** — той самий множник, той самий
дільник L3, та сама рампа перед ними. Отже недійсне значення тут `dssdiv=7`.

І важливіше за саме значення: у прогоні 5 не записалось **нічого**, хоча
`l3div=6` завідомо дійсний (прогони 2 і 6 його взяли). Тобто недійсне значення в
одному полі відкидає весь запис у регістр, а не лише своє поле.

> **ВИПРАВЛЕНО в цьому ж тексті.** Спершу я записав сюди висновок «винен
> `l3div=5`»: він спирався на прогін 3 (де було і `l3=5`, і `dss=7`) та на
> валідатор L3 у ROM, який 5 справді відкидає. Контрольний прогін 5 його
> спростував — з дійсним `l3=6` і тим самим `dss=7` запис так само не пройшов.
> Це саме та помилка, від якої застерігає §5 CLAUDE.md: дві змінні в одному
> замірі й правдоподібне пояснення для однієї з них.

Валідатор L3 @`0x800AC424` усе ж прочитано правильно, і §21 виправлено: він
відкидає **0, 3, 5, 9, 18**, а не саме лише 18. Але з цієї історії випливає
ширший урок: **таблиці валідації прошивки недостатньо**. Валідатор DSS1
@`0x800AC49C` відкидає лише 18, тобто `dssdiv=7` для нього дійсний — а апарат
його не бере. Апаратний набір дільників вужчий за той, що валідує прошивка.

Виправлено відповідно, і у два рівні. Автоматичний підбір (`CompensatedCore`)
працює тепер на завідомо вузькому наборі `KAutoDivAllowed` = 1, 2, 4, 6, 8, 12,
16 — це класичний для OMAP2 набір, він містить обидва значення, якими
користується сама прошивка (4 для L3, 6 для DSS1), і обидва, які записались у
наших замірах. Ручний режим лишається ширшим, з валідації прошивки плюс
виміряне виключення `dss=7`, і спирається на читання назад: рядок `MISMATCH`
ловить відмову апарата негайно.

Чому це важливо не лише для точності компенсації: якщо запис не проходить, CORE
змінюється зі **старими** дільниками. Саме ця ситуація ламала відрисовку (§21),
і саме її компенсація мала виключити.

### 26.1. §5 завдання: розкладка тримається, утримувати нічого не треба

Обидві половини питання закрито, і обидві дали «тримається».

`CM_CLKSEL_MPU = 4` протримався всі 40 с під навантаженням, **без резидентного
патча** (між знімками патч у ядрі не живе взагалі) і через перехід OPP —
`CM_CLKSEL2_PLL` за цей час сходив 2 → 1 → 2, а дільник MPU не поворухнувся.
Губернатор цього регістра не чіпає.

`CM_CLKSEL1_CORE` із нештатним `l3div=6` протримався так само, 0 зсувів. Плюс
непряме, але сильне свідчення: апарат зустрів перший прогін зі словом
`04360544` (`dssdiv=5`), яке лишив там прогін замовника **13.6 години тому** —
рядок `NOT STOCK AT START` це й показав. Нештатне слово живе годинами.

Отже гіпотеза «губернатор переписує дільники» **спростована**, а разом із нею й
потреба в утриманні: блоб `ReassertDividers` і ключ `hold=1` лишаються, але
для цієї задачі не потрібні.

### 26.1a. Виправлено ще один хибний висновок: refresh SDRAM

У `PickDivider` стояло обґрунтування, що за рівної похибки краще взяти нижчу
частоту шини, бо «refresh рахується в тактах L3, тож повільніша шина означає
частіший refresh, а не рідший». Це **навпаки**.

`SDRC_RFR_CTRL0 = 0x0004DA01`, тобто `ARCV = 0x4DA = 1242` такти L3. При
165.12 МГц це 7.52 мкс — рівно вікно авторефрешу для 8192 рядків за 64 мс.
Лічильник рахує такти шини, тож **повільніша шина розтягує інтервал у реальному
часі**: при 82.56 МГц це вже 15 мкс, при 41.28 — 30 мкс, і рядки встигають
втратити заряд.

Числа конкретні. `ARCV = 0x4DA = 1242` такти шини; при штатних 165.12 МГц це
7.52 мкс — рівно 64 мс / 8192 рядки, тобто впритул до специфікації. При `l3div=8`
шина 82.56 МГц дає 15.0 мкс (майже вдвічі понад спеку), а на нижчій OPP
губернатора 41.28 МГц — 30.1 мкс, тобто вчетверо.

Чи компенсує прошивка свій власний нижчий OPP, **невідомо**: `SDRC_RFR_CTRL0` ми
досі читали лише між прогонами, коли `sel2=2`, і завжди бачили те саме
`0x0004DA01`. Якщо вона ARCV не рухає, то штатний апарат на нижчій OPP уже
працює вдвічі понад спеку — і тоді справжній запас утримання щонайменше
двократний, а ламається десь між ним і чотирикратним. Це дослід, а не здогад:
регістр тепер знімається в тому ж пакеті, що й дільники, і друкується разом з
інтервалом у наносекундах.

Хай там як, про НАШ дільник прошивка не знає напевно. Отже опускання шини нижче
штатної — це ризик, а не запобіжник, і політику підбору L3 змінено відповідно:
беремо найвищу шину, яка не перевищує **виміряну** стелю 213.12 МГц. Ця стеля не з
голови — це та частота, на якій апарат фактично працює щодня при `mult 111`, з
нулем помилок цілісності SDRAM у кожному лозі.

Практичний наслідок для замовника: його конфігурація C (`l3=4` при `mult 43`,
тобто шина 82.56 МГц, а на нижчій OPP 41.28) **не є безризиковою**, попри те що
це зниження частоти. Конфігурації A, B і D цього не стосуються — там шина або
штатна, або незмінна.

### 26.2. Прилад заразом відкалібровано

Обидва заміри дають те, чого не давав жоден попередній: рух **одного** домену.

| конфігурація | ядро | шина | NOP | MEM |
|---|---|---|---|---|
| `mpu=4`: ядро вдвічі нижче, шина штатна | 325 → 161 МГц | 165.12 незмінна | **−50.4%** | **−20.8%** |
| `l3=6`: шина нижча, ядро штатне | 324 → 323 МГц | 165.12 → 110.08 | **+0.3%** | **−30.2%** |

Тобто власний `BestMem` цього проєкту — **не чистий вимір шини**: половинна
частота ядра коштує йому 20.8% навіть при незмінній шині. Це варто знати,
перечитуючи всі попередні «RESULT MEM» у логах: там ядро й шина завжди їхали
разом, тож розділити внески з них не можна було в принципі.

### 26.3. Наслідок, який стосується робочої конфігурації проєкту

Стара `CompensatedCore(107)` підбирала `dss=7`, а `CompensatedCore(111)` —
`l3div=5`. Обидва значення апарат не бере, тож **компенсація на робочих
множниках ніколи не застосовувалась**, і `hold 111` весь час лишав штатне слово
`04360644`: шина йшла 852480/4 = 213.12 МГц (+29%), а дисплей 852480/6 =
142.08 МГц (+29%) — а не 170.50 і 110.08, як було записано в `state.md`.

Для множника 107 це виміряно прямо: у прогонах 3 і 5 регістр лишився штатним, і
рядок `after` показав `BUS=205440 DSS1=136960`. Для 111 це той самий код і той
самий механізм, але сама пара чисел з апарата ще не знята.

Практично це радше добра новина: апарат тиждень тримає +29% не лише по ядру, а
й по шині та дисплею, з нулем помилок цілісності SDRAM у кожному лозі. Саме
тому нова політика підбору L3 (§26.1a) цілиться в те, що фактично працює, а не в
теоретичну «компенсацію»: після виправлення `CompensatedCore(107)` дає `l3=4`
(шина 205.44, як і було) і `dss=8` (дисплей 102.72), а `CompensatedCore(111)` —
`l3=4` (213.12) і `dss=8` (106.56).

Обидві розкладки перевірено на апараті — записуються, читаються назад, тримають
вікно витримки:

```
mult=107 l3=4 dss=8 -> CORE=04360844  BUS 205440  DSS1 102720   CPU +20.3% MEM +20.8%
mult=111 l3=4 dss=8 -> CORE=04360844  BUS 213120  DSS1 106560   CPU +24.6% MEM +24.7%
```

Тобто після виправлення щоденний `mult 111` лишає шину там, де вона фактично й
була весь час (213.12 МГц), а дисплей уперше справді компенсується: 106.56 МГц
замість непередбачених 142.08.

### 26.4. Виправлено: опорна точка компенсації тепер стала

`Prepare()` раніше знімав `iStockCore`, `iStockMpu` і `iStockClocks` з **живих**
регістрів, тобто опорною ставала та розкладка, у якій процес застав апарат.
Поки апарат штатний, різниці немає. Щойно він розігнаний — точка з'їжджає, а
`CompensatedCore()` цілиться в `iStockClocks.Dss1Khz()`, тобто в уже зсунуту
частоту дисплея.

Наслідок відтворено в логах замовника повністю: `hold 107` лишив апарат із
`dssdiv=6` при CORE 821.76, тобто з піксельним клоком 136.96 МГц; наступний
`hold 86` прочитав це як штатне і сумлінно зберіг, зменшивши дільник до 5, а в
рядку `vs stock: DSS1 -3.5%` відзвітував, що дисплей майже не зачеплено —
хоча насправді зафіксував його на 132.1 МГц замість 110.08. Кожен цикл
«підняти — опустити» зсував дільник ще на крок і не повертав.

Опорна точка винесена в константи `ocengine.h`, знята з апарата після холодного
завантаження:

```
KStockClkSel1Core = 0x04360644   l3div=4 dssdiv=6  ->  BUS 165.12, DSS1 110.08
KStockClkSelMpu   = 0x00000002   mpu_div=2         ->  MPU 330.24
KStockMult        = 86           DPLL 330.24       ->  CORE 660.48
```

Живий стан на старті лишився доступним окремо (`BootMult()`, `BootCore()`,
`BootMpu()`) і друкується рядком `NOT STOCK AT START`, коли не збігається зі
штатним. Раніше цей випадок мовчки ставав новою нормою.

Заразом виправлено `RestoreStock()`. Він робив саму лише рампу множника, а вона
не пише **нічого**, коли множник уже штатний, — тож розкладка виду «mult 86,
mpu_div 4» лишалася б у залізі. Тепер після рампи йде один явний запис штатної
розкладки.

### 26.5. «Дільники живуть, поки живе патч» — це не так

Замовник пояснив зникнення компенсації тим, що дільники тримає релок-блоб, і
щойно патч знято, штатний сеттер їх переписує (`TASK_MPU_DIVIDER.md` §2).
Механізм названо неправильно, і це видно прямо з нашого коду.

Патч тіла `DoControl(1)` — це **транспорт**, а не засувка. Блоб виконується один
раз, пише регістри, повертає керування, і на цьому все; далі патч знімається, і
жодного нашого коду в системі не лишається. Резидентність патча ніяк не
пов'язана з тим, що стоїть у `CM_CLKSEL1_CORE`. Тобто якщо регістр повернувся до
штатного слова, це зробив хтось інший, і зробив би так само за живого патча.

Хто саме — не встановлено. Найімовірніший кандидат: губернатор DVFS. Що він
активний, у проєкті вже виміряно (`CM_CLKSEL2_PLL[1:0]` ходить між 1 і 2, §12 і
§18), а повернене значення — рівно штатне слово, тобто виглядає як запис із
таблиці OPP. Це **гіпотеза**, дизасемблювання шляху переходу OPP не робилось.

Практичний наслідок протилежний до того, який вивів замовник: якщо це
губернатор, то тримати патч резидентним марно, і дочірнього процесу самого по
собі теж не досить. Треба або переконатись, що конкретне поле губернатор не
чіпає (для `CM_CLKSEL_MPU` це відкрите питання, §5 завдання), або переписувати
дільники в тому ж вікні.

### 26.6. Що саме показують логи замовника, а що ні

`HoldOverclock` **не перечитував** `CM_CLKSEL1_CORE` після запису. Рядок
`CLKSEL1_CORE 04360644 -> 04360745` друкує `LogCompensation()` **до**
застосування, тобто це намір, а не факт. Отже з тих логів не випливає навіть те,
що компенсований дільник колись стояв у регістрі: він міг не записатись зовсім,
а міг записатись і за секунди зникнути. Ці два випадки лог не розрізняє.

Тепер відомо, який саме: **не записалось зовсім** (§26.0). Але дорогою варто
відзначити аргумент, який спокушав і виявився хибним. У тому ж прогоні
`hold 107` пропускна здатність пам'яті зросла на 20.5% при намірі лишити шину
незмінною, і це виглядало як доказ, що компенсація не діяла. Доказом воно не
було: замір §26.2 показав, що `BestMem` втрачає 20.8% від самої лише половинної
частоти ядра, при абсолютно незмінній шині. Тобто цей прилад відповідає на обидва
домени, і в конфігураціях, де ядро й шина їдуть разом, він не розділяє нічого.

Питання закрило читання регістра назад одразу після запису — воно тепер є і в
`patcher clocks`, і в `patcher hold`.

### 26.7. Команда `patcher clocks`

```
ocprobe.exe patcher clocks mult=86 mpu=4 l3=4 dss=6 sec=300 [sample=10]
                           [child=ps1|dsp] [hold=1] [args:<аргументи дитини>]
```

Ключі за замовчуванням дають рівно штатну розкладку, тобто команда без
аргументів нічого не змінює, лише міряє й наглядає.

Порядок кроків усередині не довільний. **Застосування у два кроки**: наївна
рампа з кінцевими дільниками на кожній сходинці вбила б апарат, бо конфігурація
«mult 43, mpu_div 1» на проміжному множнику 86 дала б ядру 660 МГц, а шині 330 —
удвічі більше за штатну і вдвічі більше за встановлену цим проєктом межу 426 МГц.
Тому спершу йде звичайна рампа з автоматичною компенсацією (перевірений шлях; на
кожній сходинці частоти лишаються біля штатних), і лише на кінцевому множнику
робиться один явний запис потрібної розкладки — там вона коректна за побудовою.

Приємний збіг: автоматична компенсація на `mult 43` сама дає `l3div=2` і
`dssdiv=3`, тобто рівно те, що потрібно конфігураціям B і C. Явний крок міняє
там лише дільник MPU.

Далі: читання всіх чотирьох регістрів назад із явним рядком `MISMATCH`; замір
NOP і пропускної здатності до й після; вікно витримки з періодичним знімком
розкладки; читання після дитини; явне повернення штатного стану з читанням назад.

Аргументи дитини йдуть **останніми**, після маркера `args:`, і все після нього
відрізається від нашого власного розбору командного рядка — інакше чуже слово
(скажімо, `power`) ловилося б нашим `Find` і запускало чужу гілку. Буфер
командного рядка піднято з `TBuf<64>` до `TBuf<256>`: рядок замовника
`gui play nosnd frames6100 dsa light blend imggt.pbp` — це 50 символів, і в
попередньому буфері команда мовчки обрізалась би посередині. 256 — стільки ж,
скільки приймає демон розгортання (`tester_exec.cpp`).

### 26.8. `ReassertDividers`: переписати дільники, не зупиняючи DPLL

На випадок, якщо розкладка таки не тримається, доданий окремий блоб: запис
`CM_CLKSEL1_CORE` і `CM_CLKSEL_MPU` плюс фіксація `PRCM_CLKCFG_CTRL`, під
вимкненими перериваннями, **без bypass DPLL**.

Чому не використати наявний relock: він заради тієї самої пари регістрів щоразу
заганяє DPLL у bypass, а це те саме вікно, яке при активному дисплеї вішає
апарат (§20, §21). Тут CORE не змінюється взагалі — змінюються лише похідні від
неї дільники. Це не новий клас операції для цього SoC: рівно це робить сам
губернатор при кожному переході OPP.

**Не виконувався на апараті жодного разу.** Увімкнення — лише явним ключем
`hold=1`, і команда пише про це в лог окремим рядком.

Заразом виправлено застарілий коментар при `ApplyDspDiv`: там ще стояло, що латч
`PRCM_CLKCFG_CTRL` не потрібен. Це було спростовано на апараті ще в §24 — сеттер
повертав 0, а регістр не мінявся, — але коментар лишився старий.

### 26.9. Що лишається зміряти

| Питання | Стан |
|---|---|
| Чи тримається `CM_CLKSEL_MPU` без резидентного патча | **закрито: тримається**, 40 с під навантаженням, через перехід OPP |
| Чи тримається нештатний `CM_CLKSEL1_CORE` | **закрито: тримається**, і живе годинами між прогонами |
| Чому компенсація не діяла | **закрито**: недійсний дільник відкидає весь запис (§26.0) |
| Чи бере апарат `dss=8` | **закрито: бере**, перевірено на 107 і на 111 |
| Нова компенсація на робочих множниках | **закрито**: 107 і 111 записуються й тримаються |
| Які саме дільники апарат бере | частково: 2, 4, 6, 8 записуються, 7 ні; решта не перевірялась |
| Чи працює `ReassertDividers` | відкрито; для цієї задачі більше не потрібен |
| Пари A/D і B/C замовника | відкрито, потребує їхнього `ps1stage1.exe` на апараті |

Дільники тепер валідуються і в `patcher clocks` — недійсне значення відхиляється
з поясненням ще до того, як щось буде записано. А головний запобіжник у тому, що
кожен запис читається назад: саме рядок `MISMATCH` і зловив усю цю історію.

### 26.10. Рампа ВНИЗ до множника 43 валить апарат (двічі з двох)

Прогін `mult=43 mpu=2 l3=2 dss=3 sec=15` — перевірка `dss=3`, потрібного
конфігураціям B і C замовника, — **не завершився двічі поспіль**. Обидва рази
апарат переставав відповідати, і обидва рази піднімався сам (усе рантаймове).

Лог із апарата локалізує момент точно. Він обривається одразу після заміру
«до», а рядка про рампу немає взагалі:

```
--- CLOCKS: mult=43 mpu=2 l3=2 dss=3 sec=15 child=0 hold=0 ---
  target: CORE=04360342 MPU=00000002 -> CORE=330240 MPU=165120 BUS=165120 DSS1=110080 kHz
  before: m=86 mpudiv=2 l3div=4 dssdiv=6 sel2=2 -> ...
  BEFORE: 324 MHz (NOP), 512 MB/s (MEM)
<кінець файлу>
```

Тобто апарат помирає **всередині рампи**, а не на кінцевій розкладці. Сама
кінцева точка тут цілком безневинна: шина 165.12 і дисплей 110.08 — рівно
штатні, ядро вдвічі нижче. Небезпечна саме дорога.

Спуск нижче 86 у цьому проєкті ніколи не пробувався: усі рампи були 86 ↔ 111.
Що саме вбиває — не встановлено, є три кандидати, і жоден не перевірений:

- **удвічі більше вікон bypass**: 43 сходинки проти 25 у щоденному 86 → 111,
  кожна з живим дисплеєм (§20);
- **дисплей на проміжних множниках**: автопідбір без дільника 3 дає DSS1
  89.6 МГц (−19%) біля множника 70 і 82.6 МГц (−25%) на 43. Дільник 3 дав би
  рівно штатні 110.08, але для L3 він недійсний, а для DSS1 не перевірений;
- **нижча OPP губернатора**: він у будь-яку мить може поставити `sel2=1` і
  поділити CORE ще навпіл. На множнику 43 це CORE 165.12, MPU 82.56, шина 82.56
  і дисплей 55.04 — область, де апарат ніколи не працював.

Щоб наступна спроба хоч щось локалізувала, рампа в `patcher clocks` тепер
розписана покроково: кожна сходинка пише в лог свій множник, слово дільників і
похідні частоти, з flush. Порожнеча після рядка `BEFORE`, як вище, більше не
повториться.

### 26.11. Конфігурація C замовника доступна без зміни множника

Найкорисніший наслідок §26.10: до множника 43 більшість потрібного не вимагає
йти взагалі.

Замовникові потрібні три точки: опорна, «вдвічі повільніше ядро при незмінній
шині» і «те саме ядро при вдвічі повільнішій шині». Третю він планував як
`mult=43 mpu=1 l3=4 dss=3`, тобто через рампу. Але ту саму пару частот дає
дільник L3 при **штатному множнику**:

| точка | замовник | те саме без DPLL | ядро | шина | дисплей |
|---|---|---|---|---|---|
| A | `mult=86 mpu=2 l3=4 dss=6` | те саме | 330.24 | 165.12 | 110.08 |
| D | `mult=86 mpu=4 l3=4 dss=6` | те саме | 165.12 | 165.12 | 110.08 |
| C | `mult=43 mpu=1 l3=4 dss=3` | **`mult=86 mpu=2 l3=8 dss=6`** | 330.24 | **82.56** | 110.08 |

`CORE/8 = 82.56` — та сама вдвічі повільніша шина, ядро й дисплей штатні, і
жодного relock понад один крок. Тобто всі три точки, які власне й розділяють
процесорну частку бюджету від пам'яттєвої, беруться без рампи взагалі.

Рампи потребує лише конфігурація B (`CORE` удвічі нижча при незмінних ядрі й
шині) — вона відповідає на інше питання, про CORE як внутрішню стелю, і поки
лишається недосяжною.

### 26.12. C прогнано: число отримано, апарат помер одразу після вікна

`mult=86 mpu=2 l3=8 dss=6 sec=20` записався з першого разу, читання назад
підтвердило `CORE=04360648`, розкладка протримала все вікно без жодного зсуву. І
дала те число, заради якого замір і потрібен:

```
BEFORE: 324 MHz (NOP), 513 MB/s (MEM)
AFTER : 322 MHz (NOP), 282 MB/s (MEM)
RESULT: CPU 0.6%  MEM -45.0%
```

Але лог обривається на рядку `drift samples: 0`, тобто апарат помер **на
поверненні штатного стану або одразу перед ним**, після двадцяти секунд роботи
на зниженій шині. Останній знімок показує `sel2=1`, тобто губернатор саме стояв
на нижній OPP: шина 41.28 МГц, дисплей 55.04.

Це **узгоджується з §26.1a і є найкращим свідченням на її користь**, хоч і не
доказом. 41.28 МГц проти штатних 165.12 — це вчетверо розтягнутий інтервал
авторефрешу: 30 мкс замість 7.5, тобто повний цикл по 8192 рядках за 256 мс
замість 64. Це поза будь-якою специфікацією утримання заряду, і двадцяти секунд
цілком досить, щоб памʼять зіпсувалась.

### 26.14. Гіпотезу про refresh СПРОСТОВАНО, і підпис відмови став точнішим

Здогад із §26.12 виявився хибним, і його спростував той самий дослід, який мав
підтвердити. У знімок додано `SDRC_RFR_CTRL0` і перевірку **утримання** заряду
(буфер заповнюється один раз, звіряється на кожній вибірці, тож між записом і
звіркою проходить увесь інтервал, а не частки мілісекунди, як у
`MemoryIntegrity()`). Повторний прогін `l3=8`:

```
sel2=2:  RFR=0004da01  arcv=1242 -> 15043 ns
sel2=1:  RFR=00032601  arcv= 806 -> 19525 ns
SDRAM retention over 5 s: 0 bad words in 1 MB   (три вибірки з трьох)
```

Два висновки, обидва виміряні.

**Прошивка ARCV таки рухає.** При переході на нижчу OPP вона переписує
`SDRC_RFR_CTRL0` з 1242 на 806. Ми цього не бачили раніше лише тому, що читали
цей регістр між прогонами, коли губернатор стоїть на верхній OPP. Тобто
припущення §26.1a про те, що прошивка компенсує свій власний OPP, підтвердилось,
а от про наш дільник вона справді не знає: 806 тактів при 41.28 МГц дають
19.5 мкс замість 9.8, які вона мала на увазі.

**Але пам'ять цього не помічає.** Нуль зіпсованих слів на мегабайті за три
п'ятисекундні витримки при 2.6× від штатного інтервалу. Отже втрата заряду —
**не** причина смерті апарата, і рекомендація «C можна зміряти, але не тримати»
спиралась на хибне обґрунтування. Сама рекомендація лишається чинною, але з
іншої причини, і причина тепер відома точніше.

**Апарат помирає на ПОВЕРНЕННІ штатного стану.** Обидва прогони `l3=8`
завершили вікно витримки повністю (`drift samples: 0`) і обидва обірвались на
наступному кроці — `RestoreStock`. Зміна `l3div` 4 → 8 пройшла чисто двічі,
зворотна 8 → 4 двічі вбила.

Асиметрія і вказує на причину. Обидва напрямки роблять той самий повний relock,
і різняться лише станом **перед** вікном bypass: у ньому CORE падає до `sys_clk`
19.2 МГц, тож при `l3div=4` шина отримує 4.8 МГц, а при `l3div=8` — 2.4 МГц. Це
здогад, але єдиний, який пояснює асиметрію.

Виправлення, що з цього випливало: коли множник уже штатний, повертати дільники
повним relock нема потреби. `RestoreStock()` тепер спершу пробує
`ReassertDividers()` — запис плюс латч `PRCM_CLKCFG_CTRL`, без bypass, — читає
результат назад і лише в разі невдачі падає на relock.

**Не допомогло.** Прогін із цим виправленням помер на тому самому місці, з тим
самим підписом: вікно витримки цілком, `drift samples: 0`, і обрив. Тобто
падають ОБИДВА шляхи повернення — і повний relock, і легкий запис із латчем.

Це, у свою чергу, послаблює здогад про вікно bypass: легкий шлях його не має
взагалі. Лишається щось спільне для обох, і кандидатів принаймні два.

Перший: `ReassertDividers` міняє частоту шини **не захистивши SDRAM**. Relock-блоб
перед своїм вікном заганяє памʼять у self-refresh (запис `0x48` у `SDRC+0x70`,
findings §20), а легкий блоб цього не робить взагалі — він писався для домену
DSP, де памʼять ні до чого. Повернення `l3div` 8 → 4 при `sel2=1` подвоює частоту
шини наживо, з активною SDRAM.

Другий: сам напрямок. Обидва шляхи піднімають частоту шини вдвічі, а прямий хід
(4 → 8) її знижував — і проходив чисто. Можливо, річ саме в підйомі при
незмінних таймінгах `SDRC_ACTIM`, а не в способі його зробити.

### 26.15. Смерть локалізовано: вона всередині самого запису дільників

Щоб не гадати, який із викликів у послідовності повернення обриває роботу, кожен
крок дістав власний рядок у лозі, і прогін повторено (`out/ocprobe_diag.log`).
Лог закінчується так:

```
  restore: step 1, read live layout
  restore-before: PLL=00056400 SEL2=00000001 MPU=00000002 CORE=04360648 RFR=00032601
  restore-before: m=86 mpudiv=2 l3div=8 dssdiv=6 sel2=1 -> CORE=330240 MPU=165120 BUS=41280 kHz
  restore: step 2 skipped, multiplier already stock
  restore: step 3, ReassertDividers (no DPLL bypass)
```

Рядка `restore: reassert -> r=… rc=…`, який пишеться одразу після повернення з
виклику, немає. Отже апарат гине **всередині** `ReassertDividers`, а не на
читанні регістрів перед ним і не на запасному relock після нього. Запасний шлях
у цьому прогоні взагалі не виконувався, тож §26.14 треба уточнити: там сказано
«падають обидва шляхи», і це лишається правдою для двох різних прогонів, але в
цьому конкретному до relock справа не дійшла.

Це прибирає останні сумніви щодо вікна bypass: у легкому блобі його немає, а
апарат усе одно гине. Лишається те, що блоб робить: запис `CM_CLKSEL1_CORE`,
запис `CM_CLKSEL_MPU`, латч `PRCM_CLKCFG_CTRL` і очікування його звільнення.

Знімок перед смертю додає ще одну деталь, якої раніше не було видно. На момент
повернення губернатор стоїть на **нижній** OPP (`SEL2=1`, CORE 330.24 МГц), тобто
шина йде з 41.28 МГц, а не з 82.56. Повернення `l3div` на 4 множить її **вчетверо
відносно того, що памʼять бачила щойно**, і робить це наживо, без self-refresh —
той захист є лише у великому relock-блобі (§20). Із двох кандидатів §26.14 це
підсилює перший і майже знімає другий: справа не в напрямку як такому, а в тому,
що частоту SDRAM міняють, не зупинивши до неї звертань.

Звідси й наступний крок, коли до нього дійдуть руки: додати в `OcDivBlob` ту саму
пару «self-refresh перед зміною, вихід після», що вже є в relock-блобі. Поки
цього немає, повертатися зі зниженої шини нема чим, і єдиний надійний спосіб —
перезавантаження, яке й так повертає апарат у штатний стан.

Розрізнити їх можна лише замірoм, і поки що з логу не видно навіть того, який
саме виклик усередині повернення обриває прогін: `RestoreStock()` мовчазний. Тому
в `patcher clocks` повернення тепер розписане покроково — читання, рампа,
reassert, читання назад, запасний relock, — і кожен крок пише про себе **до**
того, як його зробити. Наступний прогін покаже місце точно.

**Три смерті апарата на одній операції, тож далі без окремого рішення не йдемо.**

Практичний висновок для замовника: **точка C дає число, але прогін закінчується
смертю апарата**. Чому саме — з'ясувалось наступним дослідом, §26.14, і причина
не та, на яку тут вказано.

### 26.13. Прилад розкладено на два внески

Три заміри, у кожному рухається рівно один домен, дають повну картину того, що
насправді міряє `BestMem` цього проєкту:

| що рухали | ядро | шина | NOP | MEM |
|---|---|---|---|---|
| `mpu=4` | 325 → 161 МГц | незмінна | −50.4% | −20.8% |
| `l3=6` | незмінне | −33.3% | +0.3% | −30.2% |
| `l3=8` | незмінне | −50.0% | +0.6% | −45.0% |

Два останні рядки лягають майже на пряму: `BestMem` віддає близько 0.9 від зміни
частоти шини. Перший рядок дає другий внесок: близько 0.42 від зміни частоти
ядра. Тобто це **не вимір шини**, а суміш, і в конфігураціях, де ядро й шина
їдуть разом, він не розділяє нічого — усі попередні «RESULT MEM» у логах проєкту
саме такі.

Заразом це готовий ключ для замовника: стаття його профілю, яка поводиться як
перший рядок, обмежена ядром; як третій — пам'яттю; проміжна розкладається за
цими двома коефіцієнтами.

## 27. E90 не має DVFS узагалі: узагальнення впирається не в адреси

Виміряно 2026-08-31. Апарат Nokia E90 доступний по Bluetooth (`deploy_net.ps1
-Com COM9`), демон відповідає, `INFO` дає `screen 800x352`, `ramfree 77619200`,
`boot 1 by t`. Доступ до захищених каталогів на ньому тепер повний: `LS
C:\sys\bin\` віддає 272 файли, серед них `patcher.ldd` (1568 байтів),
`patcherS3.ldd` і `patcherShadow.ldd`. Тобто передумова для нашого двигуна —
драйвер RomPatcher+ — на місці.

Прошивку апарата зчитано з нього самого, `Z:\resource\versions\sw.txt`:

```
400.34.93
21-04-2009
RA-6
(c)Nokia
```

Це рівно та версія, чий MCU-образ уже лежить у
`firmware/e90-ra-6-400.34.93/ra6_400.34.93_prd.c00`, тож звіряти є з чим.

### Що знайшлося в образі, а що ні

Імена модулів у каталозі ROM зберігаються як UTF-16 і в образі FPSX лежать
відкрито — це перевірено на обох апаратах. У RM-320 знаходяться
`power.dll`, `dvfs_interface.ldd` і `ehwaomap.pdd`. У RA-6 знаходиться
`power.dll`, а `dvfs_interface.ldd` і `ehwaomap.pdd` — ні.

Пошук зроблено ширше, ніж за трьома іменами, бо назви могли відрізнятися:
підрядки `dvfs`, `DVFS`, `Dvfs`, `ehwa`, `EHWA` в образі E90 не трапляються
жодного разу, тоді як `omap` трапляється. У RM-320 усі вони на місці. Для
повноти: у розпакованому `z:` від RM-320 підсистема DVFS складається з
`dvfs_conf.dll`, `dvfs_engine.dll`, `dvfs_hal.dll`, `dvfs_interface.ldd` і
`dvfs_monitor.dll`.

### Чому це важливо

Примітив читання пам'яті в цьому проєкті будується на патчі тіла
`dvfs_interface` `DoControl(1)` (розділ 19). Якщо в прошивці немає самого
драйвера, переносити нема чого: питання не в тому, за якою адресою лежить
функція, а в тому, що функції немає.

Отже узагальнення на E90 — не задача пошуку зсувів, як планувалося в
`ROADMAP.md` §2, а задача пошуку **іншої точки входу**. Це рівно те, заради
чого E90 і брався за тест узагальнення: невдача тут коштує вечора, а не
випущеного релізу.

### Межі цього твердження

Це пошук по сирому образу FPSX, а не розбір ROM. Якби каталог імен був
стиснений, відсутність рядка нічого не доводила б. Але `power.dll` і `omap` у
тому самому образі знаходяться, причому в тій самій кодировці й на близьких
зсувах, тож область із іменами читається відкрито. Тому це сильне свідчення, а
не остаточний доказ; остаточним воно стане після нормального розбору
каталогу ROM.


### Виправлення того самого дня: механізм розгону на E90 Є, бракує лише читача

Висновок вище («узагальнення впирається в пошук іншої точки входу») правильний,
але його легко прочитати надто песимістично, і глибший пошук це прочитання
спростовує. Розгін на E90 не впирається у відсутність механізму — механізм на
місці.

Спершу звірка списку драйверів апарата (`LS Z:\sys\bin\`, 2590 файлів) зі
списком RM-320. У E90 справді немає всієї підсистеми DVFS (`dvfs_interface.ldd`,
`dvfs_engine`, `dvfs_hal`, `dvfs_conf`, `dvfs_monitor`), і немає ще двох речей,
на які ми могли б спертися: `d_powerapi.ldd` і `memoryaccess.ldd`. Але
`power.dll`, `ehwa.ldd`, `ehwaomap.pdd` і `patcher.ldd` — на місці.

Ключове — не імена, а самі регістри. Пошук у образі E90 за мапованими адресами
PRCM (фізична адреса плюс `0x7E000000`) знаходить рівно ті регістри, якими
керує наш двигун:

```
CM_CLKSEL1_PLL  0xc6008540  (множник DPLL - головний регістр розгону)  x3
CM_CLKSEL2_PLL  0xc6008544                                             x4
CM_CLKSEL_MPU   0xc6008140                                             x2
CM_CLKEN_PLL    0xc6008500                                             x1
CM_CLKSEL1_CORE 0xc6008240  (дільники шини й DSS)                       x4
power-down глоб 0xc80030c8                                             x1
```

І вони не розкидані — у E90 на зсуві `0x618028..0x61804c` лежить літеральний
пул одразу за `str r0,[r1,#4]` / `bx lr`, у якому підряд ідуть `CLKSEL2_PLL`,
`CLKEN_PLL`, `CLKSEL1_PLL`, `CLKSEL_MPU`. Це хвіст функції в `power.dll`, яка
читає й пише блок регістрів тактування — той самий код, що на N95 сидить біля
`0x646fxx`. Зсув відображення `+0x7E000000` тут справджується тик-у-тик, як і на
RM-320.

Отже на E90 присутні і карта регістрів, і код, який їх пише, і драйвер
RomPatcher+, яким ми цей код патчимо. Відсутня одна ланка — **читач**:
`DoControl(1)` драйвера `dvfs_interface`, з якого ми знімали частоту для
перевірки. Тобто задача звужується з «чи взагалі можливо» до «чим на цьому
апараті читати назад результат», а це вже інша, значно вужча задача. Кандидати,
які лишились на E90: власний канал RomPatcher+ (розділ 10 показав, що читання
він дає обмежене) або прямий замір роботою, як у пробнику `ocprobe`.

Межа твердження та сама, що й вище: це аналіз сирого образу, не розбір ROM.
Але знайти чотири адреси PRCM, упаковані в один літеральний пул за епілогом
функції, набагато важче списати на випадковість, ніж поодинокий рядок імені.

### Практичне застереження: чинну збірку на E90 запускати НЕ МОЖНА

Записано 2026-08-31 перед тим, як цього НЕ зробити. `ocgui` встановлено на E90
(`C:\sys\bin\ocgui.exe`, 39752 байти, реєстрація на місці), але сам запуск
небезпечний. `COcEngine::Prepare()` викликається одразу з `ConstructL` і серед
іншого робить `PokeWords(KDvfsBody, KReadPatch, 4)` — пише 4 слова в `0x80148410`.
Ця адреса вірна лише для RM-320; на E90 за нею інший код ядра. Слідом
`ReopenDvfs()` провалюється (драйвера немає) і `Prepare` виходить з помилкою
**НЕ знявши патч** (`EndPatchSession()` не досягається на цій гілці). Тобто на
E90 лишилась би підмінена чужа функція ядра, і перший її виклик з ненульовим r1
розіменував би довільну адресу в режимі ядра — перезавантаження в кращому разі.

Висновок для E90-збірки: адреси (`KDvfsBody`, `KRomSramRoutine`, `KDspSetter`,
`KPwrDownGlobal`) мають стати параметрами, а не константами, і `Prepare` мусить
знімати вже накладений READ-патч навіть на аварійній гілці, до будь-якого
дальшого кроку.

### Код тактування E90 локалізовано в образі (offline, без апарата)

Дизасемблер по образу E90 (`objdump -b binary -m arm`, вікно перед пулом PRCM
`@0x618028`) показав саму рутину запису клоків у `power.dll`:

```
618014: ldr r1,[pc,#64]   ; адреса CM-регістра з пулу
618018: mov r0,#0
61801c: str r0,[r1]
618020: str r0,[r1,#4]
618024: bx  lr
618028: .word 0xc6008544   ; CM_CLKSEL2_PLL      <- пул
        .word 0xc6008500   ; CM_CLKEN_PLL
        .word 0xc6008540   ; CM_CLKSEL1_PLL (множник DPLL)
        .word 0xc6008140   ; CM_CLKSEL_MPU
```

Поряд — читач регістра через helper (`ldr r0,[pc,#..]; bl 0x618564; ands r1,r0,#0xf`),
тобто в E90 є і читання, і запис клоків, лише не через DVFS. Це підтверджує
§27: на E90 присутній повний механізм, і майбутня E90-збірка може або патчити
цю рутину, або кликати її helper'и. Точні vaddr дасть встановлення образу в
EKA2L1; файлові зсуви вже є.

## 28. Метод «з файлу, без апарата» перевірено на 51 прошивці: що він може і де його межа

Виміряно 2026-08-31. Питання стояло практичне: чи можна для апаратів, яких нема
в руках, дізнатися з самого файла прошивки і потрібні модулі, і адреси. Коротка
відповідь: наявність машинерії — так, надійно; точну адресу — лише сигнатурою
тіла там, де вона ловиться, інакше потрібен дизасемблер.

### Інструмент і чому він працює

`tools/romscan.js` шукає в сирому MCU-образі (FPSX) три речі, не встановлюючи
його нікуди. Це можливо, бо ядровий бік ROM (`ekern`, `power.dll`, `*.ldd`,
`*.pdd`) лежить у XIP CORE **нестисненим** — код виконується прямо з флешу, тож
його інструкції та імена присутні в образі як є. Стиснені секції ROFS
(переважно user-side) сюди не потрапляють, і це навмисна межа.

Скрипт звітує:
- **драйвер dvfs_interface за іменем** — надійний тест наявності READ-примітиву;
- **тіло `DoControl(1)` за сигнатурою** — точний патч-сайт, шість слів, два
  адресозалежні звіряються за маскою;
- **літеральні пули PRCM** — регістри тактування поряд, тобто механізм ЗАПИСу.

### Перевірка на істині

На нашому RM-320 `31.0.015` скрипт знаходить тіло рівно за `0x8c0222` — це і є
`KDvfsBody` (vaddr `0x80148410`), який патчить `ocengine.cpp`. Тобто метод
відтворює з файла ту саму адресу, яку ми здобули роботою на апараті. На E90
тіла немає, і драйвера немає ні за іменем, ні на живому апараті (`LS
Z:\sys\bin\`) — два незалежні джерела збіглися.

### Асиметрія, яку не можна ігнорувати

Сигнатура тіла — **позитивний** детектор: збіг завжди справжній (звірено), а
ось **промах не доводить відсутності**. `DoControl(1)` компілюється між версіями
по-різному, і на RM-320 `20.0.016` тіло сигнатурою не ловиться, хоча драйвер там
є — ім'я `dvfs_interface` в образі присутнє. Тому present/absent беремо за
іменем, а сигнатуру тіла — лише як «патч-сайт знайдено одразу / доведеться
дизасемблити».

Так само й відсутність за іменем — сильний натяг, не вирок: у стисненому ROFS
імені не видно. Але для ядрового `dvfs_interface`, чиє ім'я лежить у XIP, це
свідчення міцне, і на E90 його підтвердив апарат.

### Що показав прогін по 51 образу (`firmware/_romscan.md`)

Драйвер DVFS присутній у 25 образах із 51, і присутність не суцільна навіть у
межах однієї моделі — вона з'являється з певної версії прошивки:

- **RM-320** (наш N95 8GB): є в усіх сімох версіях, від `10.0.021`.
- **RM-159** (звичайний N95): у ранніх `10.x`–`12.x` немає навіть підрядка
  `dvfs`, з'являється з `13.0.003` і далі є завжди.
- **RM-160** (N95 NAM): з'являється з `20.2.011`.
- **RM-245** (китайський N95, без 3G/WiFi): немає в жодній із семи версій.
- **N82 RM-313**: є в усіх.
- **E90, N93, N93i**: немає ніде.

Натомість пули PRCM — тобто сам код запису клоків у `power.dll` — присутні майже
скрізь, включно з усіма E90 (крім однієї версії) і рештою, де DVFS немає. Це
означає, що **механізм розгону (запис множника DPLL) на цих апаратах є, бракує
лише штатного читача частоти**. Виняток по пулах — `RM-245`, `RM-159 30.0.015`
та кілька інших, де пул не склався у ≥3 літерали поспіль; це не доказ
відсутності коду, а лише те, що літерали розкидані, і їх треба шукати інакше.

### Практичний висновок для узагальнення

1. Для **RM-320 будь-якої версії** метод переноситься майже як є: драйвер
   скрізь, у чотирьох версіях патч-сайт знаходиться одразу, у трьох — потрібен
   точковий дизасемблер тіла `DoControl(1)`.
2. Для **E90, N93, N93i і ранніх/китайських N95** READ-примітив через DVFS
   недосяжний. Там або інший читач (канал RomPatcher+, прямий замір як в
   `ocprobe`), або запис «наосліп» через `power.dll` з перевіркою роботою.
3. Точну числову адресу з сирого файла окремим відніманням бази взяти не можна:
   XIP не лягає одним пласким зсувом (перевірено — на очікуваній базі N95 замість
   заголовка ROM лежить таблиця вказівників). Надійний шлях до адрес і повного
   переліку файлів той самий, що дав нам `rm-320/`: встановити образ у EKA2L1,
   дістати `z:`, і читати `romtool.ps1`. Апарат для цього не потрібен, але й
   headless-підагент цього кроку не зробить — інсталяція в емулятор ручна.


## 29. Метод адаптації під невідомий апарат: що саме треба з ROM і як його взяти

Записано 2026-09-01. Мета розділу — зробити перенесення розгону на апарат, якого
нема в руках, повторюваною процедурою, а не щоразовим реверсом. Нижче — рівно те,
що доводиться дістати з прошивки, звідки, і чим це перевіряється.

### Головне уточнення методу (виправляє наївне припущення)

Єдиної лінійної відповідності «зсув у файлі → віртуальна адреса» на весь образ
НЕМАЄ. Перевірено: якір `dvfs` дає дельту `0x7f8881ee`, але код `power.dll` за нею
не читається — у RM-320 пул PRCM за цією дельтою ліг би на `0x80130B00`, а реальні
клок-функції power.dll — коло `0x800B15xx`. Причина: FPSX зберігає ROM блоками, і
кожен модуль має власне розміщення. Тому справжню адресу можна взяти лише з
`TRomImageHeader.iCodeAddress` конкретного модуля, тобто через нормальне
розпакування ROM. Власний розпакувальник FPSX не пишемо (помилка в адресі коштує
апарата) — використовуємо перевірений: встановлення образу в EKA2L1 дає `z:`, далі
`romtool.ps1` читає `iCodeAddress` (зсув 20 у 120-байтовому заголовку) і
дизасемблює з правильною адресою. Це «без апарата», хоч і не «без EKA2L1».

### Еталон RM-320 (з чим звіряти)

`romtool.ps1 -Module power.dll -Disasm` на RM-320: `codeAddr=0x800A7C98`,
`codeSize=46592`. Ключове знайдено в `out/asm/power.dll.asm`:

```
800b1560: ldr r0,[pc,#388]  ; 0x800b16ec -> літерал 0xc6008540 (CM_CLKSEL1_PLL)
800b1564: bl  0x800b1c60     ; helper ЧИТАННЯ регістра: r0=адреса -> вертає значення
800b1568..90: витягання поля множника й множення (це і є DPLL = sysclk*mult/(div+1))
```

Тобто в power.dll є: (1) helper читання мапованого регістра, (2) сам множник
`0xc6008540` у пулі, (3) далі — helper запису (пара `str r0,[r1]; str r0,[r1,#4]`
з findings §22 / розд.27). Регістри — мапована адреса = фізична `0x48008xxx` +
`0x7E000000` = `0xc6008xxx`, однакова на всьому OMAP2420.

### Що дістати на КОЖЕН апарат (чек-лист адаптації)

1. **Мапований базовий регістр множника** — очікувано `0xc6008540` (звірити, що
   присутній у пулі power.dll; на E90 присутній — розд.27).
2. **Helper читання регістра** у power.dll (vaddr) — щоб читати клоки БЕЗ dvfs.
3. **Helper запису регістра** у power.dll (vaddr) — або писати напряму зі stub'а.
4. **Чи є dvfs_interface** (romscan за іменем): якщо є — доступний старий READ-шлях
   через `DoControl(1)`, і треба зсув його тіла; якщо нема (E90, ранні/кит. N95) —
   читати через helper power.dll або взагалі не читати регістр, а МІРЯТИ роботу.
5. **SRAM-рутина relock DPLL** (`KRomSramRoutine`) і **power-down глобал**
   (`KPwrDownGlobal`) — для безпечної зміни множника з обходом DPLL; беруться з
   power.dll тим самим дизасемблером.
6. **Сеттер дільника DSP** (`KDspSetter`) — опційно, для домену DSP.

### Наслідок для стратегій читання

Метод розпадається на дві гілки за пунктом 4:
- **dvfs є** (усі RM-320, N82, пізні RM-159/RM-160): переносимо як є, лише інші
  адреси.
- **dvfs нема** (E90, N93/N93i, ранні/кит. N95): READ-примітив інший. Найнадійніше
  — не читати регістр узагалі, а міряти реальну частоту роботою (як `ocprobe`
  `BestMem`): це і сильніший доказ (міряємо роботу, не напис — §5), і не залежить
  від жодної адреси читання. Запис множника лишається через power.dll/relock.

Тобто «адаптація під чужий апарат» = заповнити профіль із пп.1–6 з розпакованого
`z:`, а де читача нема — покластися на вимір роботи. Числа беруться офлайн; апарат
потрібен лише наприкінці, щоб підтвердити, що вгадали.

## 30. XIP витягується прямо з FPSX без GUI EKA2L1: `tools/fpsx_extract.js`

§29 спирався на розпакований `z:`, а його давав інсталятор прошивок EKA2L1
через File → Install → Device. Цей інсталятор вилітає на E90 і N82 (окремий
потік фронтенду, крашу в лог не пише), а командного рядка для встановлення
прошивки збірка не має взагалі — у бінарнику є лише `--run`, `--listapp`,
`--device`, `--kbp`, а саме встановлення прив'язане до GUI-діалогу з
інтерактивним вибором варіанта. Тобто масово чи headless поставити прошивки в
EKA2L1 не можна.

Тому XIP тепер дістається прямо з образу прошивки, минаючи емулятор. Формат
FPSX/BB5 відкритий у вихідниках EKA2L1 (`src/emu/loader/{include,src}` та
`src/tools/fpsxdump`), і `tools/fpsx_extract.js` — його точний порт на Node.
Це видобуток, а не здогад: усі адреси беруться з заголовків самого ROM після
пересобирання, тож ризику для апарата в ньому немає.

Три речі, на яких трималося, і які довелося виправити проти коду EKA2L1 master:

- **Блоки впритул, без вирівнювання до 512.** Код master робить
  `seek(align(data_size,512))` між блоками; на цих образах наступний блок стоїть
  рівно за `data_offset_in_stream_ + data_size_`. Перевірено на ланцюжку
  RM-320: `0x281+0xa0=0x321`, `0x334+0x240=0x574` — точні збіги. Усі
  багатобайтові поля FPSX — big-endian.
- **CORE-корінь визначати за вмістом, не за назвою.** У N95/N82 нестиснутий XIP
  лежить у корені з описом `SOS+CORE`, у E90/N93/N93i — у `SOS+UPDAPP`, а
  тамтешній `SOS*CORE` (зірочка!) стиснутий і дає високу ентропію. Селектор
  тепер шукає корінь, чиї байти починаються таблицею векторів ARM
  (`byte[3]==0xEA`, далі гілки `EA`/`EB`), і тримає передній бутстрап до неї
  (у N95 це 0xC00, у E90 — 0).
- **Розкол ОС на резидентну й пейджовану частини.** N95/N82 тримають увесь ОС
  нестиснутим (`SOS+CORE`, ~43 МБ). N93/N93i/E90 тримають нестиснутим лише
  малий резидентний XIP (`SOS+UPDAPP`, 1–1.8 МБ), решту стискають. Код тактування
  (power.dll) в усіх випадках у нестиснутій частині, тож для розгону цього
  досить; демандпейджовані застосунки нам не потрібні.

**Перевірка на істині.** Витягнутий з `RM-320_31.0.015_PR.C0R` образ у зоні коду
байт-у-байт збігається з `SYM.ROM`, який EKA2L1 колись розпакував сам, а головне
— поле множника `0xc6008540` стоїть точно за `vaddr 0x800b16ec`, як і в §29, і
пролог DPLL-функції `0xe92d4010` — за `0x800b1544`. Відображення
`file_offset = vaddr − 0x80000000` тримається. (Повний `SYM.ROM` EKA2L1 більший:
у нього дописано хвіст до розміру CORE-розділу й перезаписано кілька слів у
заголовку ROM — контрольні суми й час; на зону коду це не впливає.)

**Прогін по всіх шести апаратах OMAP2420** (`out/roms/*.rom`) — кожен дав
валідний XIP (`v0=0xea00007e`) з регістром множника всередині:

| апарат | XIP-корінь | розмір | множник `0xc6008540` на vaddr |
|---|---|---|---|
| N95 RM-320 | SOS+CORE | 0x2959200 | 0x800b16ec |
| N95 RM-159 | SOS+CORE | 0x28e9200 | 0x800b16ec (та сама база коду) |
| N82 RM-313 | SOS+CORE | 0x29eb200 | 0x800b16fc |
| N93 RM-55 | SOS+UPDAPP | 0x115000 | 0x80045314, 0x800832e8 |
| N93i RM-156 | SOS+UPDAPP | 0x13e000 | 0x8003fdbc … 0x80097658 |
| E90 RA-6 | SOS+UPDAPP | 0x1b0000 | 0x800580e0, 0x8005eba8, 0x800b76dc |

E90 навколо свого пулу `0x800b76dc` дизасемблюється у зв'язний ARM-код роботи з
регістрами PRCM — підтверджено `objdump`. Отже адреси E90 з §29 тепер можна
виводити офлайн, без встановлення прошивки в емулятор і без апарата.

Виклик: `node tools/fpsx_extract.js <образ .C0R/.c00/.fpsx> [out.rom]`;
`--root=N` примусово бере конкретний корінь (діагностика).

## 31. Адреси тактування по всій лінійці; і де впирається офлайн-адаптація E90

Маючи офлайн-XIP усіх шести апаратів (§30), можна було вивести адреси
тактування з коду й звірити їх. Три кодові якорі — функція-читач множника,
SRAM relock-рутина (`iRomSramRoutine`), DSP divider setter (`iDspSetter`) —
знайдено за підписом (не за адресою) і **незалежно перевірено байтовим тестом**
у RM-320, RM-159, N82, N93, N93i; для E90 підтверджено SRAM-рутину й setter.
Розбір чотирьох апаратів вели паралельно підагенти `agy`, E90 й еталон —
оркестратор. Зведена таблиця — `out/analysis/_summary.md`, покрокові докази —
`out/analysis/<dev>.md`.

Ключові числа: RM-159 збігається з RM-320 байт-у-байт (та сама база коду N95).
N93 має пролог SRAM-рутини `{r1-r6,lr}` замість `{r1-r7,lr}` — r7 не вживається,
логіка relock та сама. E90 setter має маску `0x1f`, як RM-320 (сусідній близнюк
із маскою `0x1f00` — інше поле, не наш setter):

| апарат | читач | пул 0xc6008540 | iRomSramRoutine | iDspSetter |
|---|---|---|---|---|
| RM-320 / RM-159 | 0x800b1544 | 0x800b16ec | 0x800a7f6c | 0x800ac59c |
| N82 | 0x800b1554 | 0x800b16fc | 0x800a7f7c | 0x800ac5ac |
| N93 | 0x800451e4 | 0x80045314 | 0x8003e6d0 | 0x80040c80 |
| N93i | 0x80046248 | 0x80046408 | 0x8003eb3c | 0x80041630 |
| E90 | (пейджовано) | 0x800b76dc | 0x80056874 | 0x80059aa4 |

### Де офлайн E90 впирається (і чому це не помилка інструмента)

Профіль двигуна має чотири залежні від прошивки поля. Для E90 два з них
(`iRomSramRoutine`, `iDspSetter`) виведено офлайн вище. Решта два — ні, і причина
структурна:

- **`iDvfsBody = 0`.** Штатний READ-примітив RM-320 — патч тіла
  `dvfs_interface DoControl(1)`. Рядки «dvfs» у резидентному XIP E90 є, але всі
  стосуються DVFS **дисплея** («DvfsDisplay», «Driver_Tv_for_DVFS»), а не
  процесорного `dvfs_interface`. Це підтверджує §27: процесорного dvfs на E90
  немає. (Перевірено повторно на витягнутому XIP — висновок §27 правильний.)
- **`iPwrDownGlobal = 0xc8004194` — знайдено (виправлення).** Спершу здавалося, що
  цей глобал офлайн не вивести. Насправді виводиться: у power-зоні E90 є чиста пара
  геттер/сеттер — `str r0,[0xc8004194,#4]` (0x8005ebec) кладе `obj` у `global+4`,
  `ldr r0,[0xc8004194,#4]` (0x8005ebf8) його повертає. Це точний аналог того, що
  читає двигун (`[iPwrDownGlobal+4] -> obj -> [obj+16] -> sram`). init-конструктор
  ставить `[obj+16]` на 0x800587d0, байт-у-байт як RM-320 0x800ab2c0. Отже три з
  чотирьох полів профілю E90 (`iRomSramRoutine`, `iDspSetter`, `iPwrDownGlobal`)
  виведено офлайн.
- **Лишається примітив ЧИТАННЯ для резолвінгу SRAM у рантаймі.** Сам ланцюг відомий,
  але прочитати `[obj+16]` на апараті нема чим: dvfs немає, а придатного
  користувацьки-доступного резидентного драйвера, тіло якого можна пропатчити як
  читач, у нестиснутому XIP E90 не видно.

**Висновок.** Примітив ЗАПИСУ (`patcher.ldd`, shadow-сторінки) на E90 доступний і
від dvfs не залежить. Примітив ЧИТАННЯ — ні. За рішенням користувача обрано
бутстрап читання через запис: на апараті пропатчити крихітний kernel-стаб, що
пройде вже відомий ланцюг `0xc8004194+4 -> obj -> obj+16` і поверне адресу SRAM;
далі повний WRITE-шлях E90 працює як на RM-320. Лишилося знайти користувацьки-
доступну функцію E90, тіло якої безпечно тимчасово пропатчити як виконавця стаба
(аналог ролі dvfs DoControl на RM-320). Уся решта E90 вже виведена офлайн; апарат
потрібен лише для цього кроку — як і планувалося.

## 32. Read/exec-примітив E90: хост знайдено — DLddUsbcChannel::DoControl

Останнє поле для WRITE-шляху E90 — примітив читання/виклику в режимі ядра (на
RM-320 його дає dvfs, якого на E90 немає, §27). Обрано (рішення Павла) бутстрап
через запис: записом RomPatcher+ пропатчити тіло користувацьки-відкривного
XIP-драйвера. **Носій — стандартний драйвер USB-клієнта `DLddUsbcChannel`
(LDD-ім'я «Usbc»).**

Чому саме він. Хост мусить бути (1) резидентним XIP (фіксована адреса; драйвер
із ROFS лягає в динамічну RAM ядра, адресу не зашити), (2) користувацьки
відкривним, (3) тихим у наше вікно. Usbc задовольняє всі три: код у базовому
порту OMAP (XIP), відкривається `RBusLogicalChannel::DoCreate(«Usbc»)` з
CommDD, і без кабелю USB-канал не обслуговується — тобто в наше коротке вікно
патча його `DoControl` ніхто не смикає.

Як знайдено (без здогадів). Диспетчери `HandleMsg` усіх message-based LDD у XIP
перелічено сигнатурою `ldr rX,[r1,#24]; cmp rX,#0x80000000` (читання
`iValue` й перевірка на закриття). Диспетчер Usbc на E90 — `0x80095be8`, на
RM-320 — `0x8010ce3c`; вони **байт-у-байт однакові за структурою**, а на RM-320
його щільно оточують рядки «Usbc*» — отже це той самий `DLddUsbcChannel`. Гілка
DoControl диспетчера (opcode ≥ 0):

```
ldr r2, [r4, #28]      ; a1  (msg->iArg[0])
ldr r3, [r4, #32]      ; a2
mov r1, r5             ; aFunction
mov r0, r7             ; this
bl  <DoControl>        ; RM-320 0x8010bd04, E90 0x80094ac4
```

тобто у `DoControl(this, aFunction, a1, a2)` **a1 (адреса) — у r2**. Пролог
обох `DoControl` теж байт-у-байт (`e92d4ff0 e24dd044 e1a04000 e1a06002 …`,
`mov r6,r2` зберігає a1), тож патч-сайт і регістр однакові на обох апаратах.

Патчі (варіант r2, на відміну від r1-версій dvfs §14):

| призначення | слова | асемблер |
|---|---|---|
| READ | `e3520000 15920000 03a00000 e12fff1e` | `cmp r2,#0; ldrne r0,[r2]; moveq r0,#0; bx lr` |
| EXEC | `e12fff12` (+ решта прологу лишити) | `bx r2` |
| RESTORE (4 слова) | `e92d4ff0 e24dd044 e1a04000 e1a06002` | штатний пролог |

READ-стаб не чіпає sp (штатний `stmdb/sub` не виконується), `bx lr` повертає
r0 через `HandleMsg` у результат `DoControl` користувача. Знімати патч —
запис оригіналу + `FreeShadowPage` (§19), як на RM-320.

Адреси хоста й перевірки:

| апарат | DoControl | пул множника (тест READ) | очікуване `[пул]` |
|---|---|---|---|
| RM-320 | 0x8010bd04 | 0x800b16ec | 0xc6008540 |
| E90 | 0x80094ac4 | 0x800b76dc | 0xc6008540 |

Валідація (спершу прилад, §дисципліна): на RM-320 є незалежний оракул dvfs.
Пробник `usbcboot` відкриває Usbc, ставить READ-стаб, читає `[пул]` через
`RDevUsbcClient::DoControl(0, пул)` і звіряє з `dvfs.ReadOrCall(пул)` та з
відомим `0xc6008540`; тоді відкат і перевірка відкату. Лише після збігу на
RM-320 той самий механізм іде на E90, де перевіркою слугує вже сам відомий
`0xc6008540`.

**Перевірено на RM-320 (2026-09-03).** `ocprobe usbcboot` (демон, WiFi):
Usbc-канал відкрився (`DoCreate v0.0.0 -> 0`), READ-стаб ліг у `0x8010bd04`,
і всі три відомі слова прочиталися через хост правильно —
`[0x80000000]=0xea00007e`, `[0x800b16ec]=0xc6008540`, `[0x800a7f6c]=0xe92d40fe`
(3/3), тоді відкат і `FreeShadowPage` обидва `-> 0`, апарат не перезавантажився
(uptime цілий). Механізм доведено на приладі з незалежним оракулом. E90 має
байт-у-байт той самий пролог `DoControl` і диспетчер, хост `0x80094ac4`.

## 33. Штатне тактування E90: бутстрап дає 266 МГц, а не 330; читач множника таки в XIP

Виведено з `out/roms/e90.rom` (резидентний XIP, база `0x80000000`) і **звірено
власним `objdump`**, не лише звітом підагента. Приводом був борг «заповнити
штатну розкладку E90 в `KProfileE90`»: перед тим, як покласти в профіль числа,
треба було знати, звідки вони й наскільки їм можна вірити.

**Послідовність холодного старту знайдено в bootstrap-коді** (`0x80001910`–
`0x800019ac`). База CM береться з пулу `[0x80001e30]`, далі прямі записи в її
регістри (зсуви — від фізичної `0x48008000`):

```
80001924: ldr r1,[pc,#1316]  ; = 0x08301044 (пул 0x80001e50)
80001928: str r1,[r0,#0x240] ; CM_CLKSEL1_CORE <- 0x08301044
8000192c: mov r1,#2
80001930: str r1,[r0,#0x140] ; CM_CLKSEL_MPU   <- 2
80001920: str r1,[r0,#0x544] ; CM_CLKSEL2_PLL  <- 2 (CORE = DPLL*2)
80001940: str r1,[r0,#0x840] ; CM_CLKSEL_DSP   <- 0x000023c3
80001968: mov r1,#97 / mov r2,#6 / ... / str r7,[r0,#0x540] ; CM_CLKSEL1_PLL
```

Множник обирається за детекцією sysclk (біти [25:23] `CM_CLKSEL1_PLL`): гілки
дають `mult=133/div=5`, `mult=41/div=1` і — типова — `mult=97, div=6`. Останнє
при кварці 19.2 МГц це **DPLL ≈ 266 МГц**, тобто холодний старт E90 стоїть на
266, а не на 330. `CM_CLKSEL1_CORE = 0x08301044` тут теж СВОЄ (L3=4, L4=2,
DSS1=16, SSI=3, USB=4) і не дорівнює штатному рантайм-значенню RM-320
`0x04360644`.

**Але це значення bootstrap, а не рантайм-штат ОС.** Той самий OMAP2420 на
RM-320 стартує так само рано, а на 330 МГц (`mult 86`) його виводить уже
менеджер живлення пізніше — саме той механізм, який цей проєкт і перехоплює.
Перехід E90 на робочу частоту (і чи це взагалі 330) лежить у **стиснутій
частині ROFS**, якої в резидентному XIP немає: вичерпний скан XIP на вторинний
запис `CM_CLKSEL1_PLL` нічого не дав. Тому:

- `iStockClkSel1Core` і `iStockClkSelMpu` для E90 лишаються **не заповненими з
  ROM** — рантайм-розкладку читаємо з апарата, коли підніметься примітив Usbc.
  Значення bootstrap у профіль класти НЕ можна: воно опис ранньої фази, а не
  того, де апарат працює.
- `iStockMult=86` у `KProfileE90` — лише робочий здогад для 330-МГц апарата;
  bootstrap показує 97/266, тож перед будь-яким розгоном множник треба
  підтвердити читанням поля [21:12] `CM_CLKSEL1_PLL` на живому E90. До того
  `Prepare()` для E90 однаково відмовляє (§27, `EOcStepUnsupported`).

**Виправлення попереднього висновку.** У `out/analysis/_summary.md` стояло, що
функція-читач множника E90 лежить у пейджованій частині. Це хибно: у резидентному
XIP вона **є**, за `0x8005ea00`, з прологом `e92d4010 stmdb sp!,{r4,lr}` —
структурно тотожним читачеві RM-320 `0x800b1544`, — і вантажить той самий пул
`0xc6008540` (`0x8005eba8`), викликаючи венір-читач `0x8005f0c4`. Практичний
наслідок: на E90 є штатний резидентний спосіб ПРОЧИТАТИ множник; бракує лише
носія, здатного викликати довільний код ядра, і ним лишається бутстрап Usbc.

## 34. XIP читається з user mode; офлайнова розкладка E90 спростована апаратом

Розділ виправляє §31 і §33 у частині адрес E90 і знімає гейт, який тримав усю
гілку E90: примітив читання ROM більше не потрібен, бо ROM читається просто так.

**Що виміряно.** `ocprobe usbcboot e90` з адресами, виведеними офлайн, тричі
поспіль повертав рівно `0x00000000` замість очікуваних слів, не перезавантажуючи
апарат. Три проби розділили можливі причини.

Перша — стаб-підпис `mov r0,#0x5a; bx lr`, який нічого не розіменовує. Він
повернув 0, тобто записане в `0x80094ac4` не виконувалось узагалі; отже справа
не в припущенні про регістр `r2`.

Друга — канарок у пам'яті власного процесу: `WriteBytes(&canary, 0xdeadbeef)`
ліг і прочитався назад (`WRITE PATH OK`). Отже шлях запису `patcher.ldd` на E90
живий, і підозра з ординалів експорту `ekern` знята.

Третя — пряме читання XIP з користувацького режиму (`ocprobe romread`). Воно
не тільки не впало, а й дало відповідь: `[0x80000000] = 0xea00007e` збігається,
а `[0x800b76dc]` і `[0x80056874]` дають зовсім інший, але цілком осмислений ARM-код
(`ldr r0,[r4,#52]`, `mov r0,#1`). База `0x80000000` правильна, а от розкладка — ні.

**Причина.** Адреси E90 у §31 і §33 виведені з `out/roms/e90.rom` за припущенням
`vaddr = 0x80000000 + зсув у файлі`. Для RM-320 цю лінійність колись звірили з
розпакованим `SYM.ROM`, для E90 — ніколи, а §29 сам же попереджав, що FPSX
зберігає ROM блоками. `HAL EMemoryROM` на апараті віддає **19776 КБ**, тоді як
витягнутий образ має 1.7 МБ, тож офлайн ми бачили меншу частину й не в тій
розкладці. Патч через це лягав у чужу сторінку: запис проходив, виконуватись не
було чому, і ніщо не падало — рівно та картина, що спостерігалась.

**Наслідок, важливіший за саму помилку.** XIP читається з user mode, отже
залежні від прошивки адреси знаходяться НА АПАРАТІ сигнатурним сканом, без
ядерного примітиву читання. Це знімає циклічну залежність, у яку впиралася вся
офлайнова гілка («щоб просканувати ROM, потрібен примітив читання, а щоб його
дістати — треба вже знати першу адресу»).

Додано в пробник три режими, усі лише для читання:

```
ocprobe romread            три контрольні слова, перевірка бази
ocprobe romscan            суцільний скан живого XIP за сигнатурами
ocprobe romdump <a> <len>  вивантаження вікна ROM у E:\romdump.bin
```

**Результат скану живого E90** (увесь 19.3-мегабайтний XIP, без падінь):

| адреса | що це |
|---|---|
| `0x8005a610`, `0x800610d8`, `0x800e640c` | пул із `CM_CLKSEL1_PLL` (`0xc6008540`) |
| `0x8005c338`, `0x800610dc` | пул із `CM_CLKSEL_MPU` (`0xc6008140`) |
| `0x800bf874` | пролог `DLddUsbcChannel::DoControl` |
| `0x800c09a4` | диспетчер `HandleMsg` того ж драйвера |

Вивантажені вікна дизасембльовано власним `objdump`. Код навколо `0x8005a404`
вантажить `CM_CLKSEL1_PLL` у `r9` і працює через helper'и `0x800615f4` (читання),
`0x80061604` і `0x80061614` (запис) — структурно те саме, що на RM-320, лише за
іншими адресами. Диспетчер за `0x800c09a4` збігається з офлайновим до інструкції:
`cmp r5,#69` пропускає наш опкод повз перевірку готовності USB, а `ldr r2,[r4,#28]`
кладе адресу в `r2` перед `bl 0x800bf874`.

**Примітив на E90 доведено (2026-09-09).** З виміряним хостом `0x800bf874`
`ocprobe usbcboot e90` дав підпис `0x5a` (стаб виконується) і **3/3** контрольних
слова: `[0x80000000]=0xea00007e`, `[0x8005a610]=0xc6008540`,
`[0x800c09a4]=0xe5915018`. Відкат і `FreeShadowPage` обидва `0`, `startTick`
незмінний за весь сеанс — апарат не перезавантажувався жодного разу.

**Що з цього випливає для §31 і §33.** Усі числа тих розділів, отримані з
`out/roms/e90.rom` через лінійну мапу, треба вважати недійсними, доки не
переміряні на апараті. Це стосується `iRomSramRoutine`, `iDspSetter`,
`iPwrDownGlobal` (у коді обнулені) і висновку §33 про бутстрап із `mult=97`.
Метод §30 (витяг XIP із FPSX) сам по собі не спростований — спростована лінійна
мапа зсув→vaddr поверх нього, і саме для E90, де XIP розколотий.

### 34.1. Штатне тактування E90, виміряне на апараті

Тим самим примітивом, лише читанням, знято регістровий файл PRCM живого E90
(2026-09-09, Bluetooth):

```
CM_CLKSEL1_PLL  = 0x00056400   mult=86  div=4  sys_clk_sel=0 (19.2 МГц)
CM_CLKSEL2_PLL  = 0x00000002   core_mult=2
CM_CLKSEL_MPU   = 0x00000002   mpudiv=2
CM_CLKSEL1_CORE = 0x04360626
CM_CLKEN_PLL    = 0x0000000f   DPLL у lock
```

За формулою §4: `19.2 × 86 / (4+1) = 330.24 МГц` на DPLL, `× 2` на CORE і `/ 2`
на MPU, тобто **E90 штатно працює на тих самих 330.24 МГц, що й RM-320**.
Робочий здогад `iStockMult = 86` підтвердився — але тепер це вимір, а не здогад,
і в профілі він стоїть як вимір.

Розкладку `CM_CLKSEL1_CORE = 0x04360626`, якої офлайн не було видно взагалі
(код ініціалізації лежить у стиснутій частині), отримано цілком. `KProfileE90`
заповнено цими трьома числами.

Застереження: це знімок одного моменту. Процесорного DVFS на E90 немає (§27),
тож розкладка має бути сталою, але перед WRITE-прогоном її треба перечитати —
правило «не вірити напису без заміру» стосується і власних попередніх замірів.

Числа `mult=97` / 266 МГц із §33 до робочого штату ОС не стосуються, а самі
адреси §33 виведені з розкладки, яку апарат спростував (§34).

## 35. Носій примітиву став профільним; ребут E90, куплений одним пропущеним рядком

Щоб розгін працював не лише на RM-320, носій READ/EXEC-примітиву винесено в
профіль (`TOcHost`): на RM-320 це `dvfs_interface` з `DoControl(1, a1)` і
адресою в `r1`, на E90 — `Usbc` з `DoControl(69, a1)` і адресою в `r2`. Механіка
патча спільна; різняться назва каналу, опкод, регістр аргументу, слова відкату
й спосіб перевірки відкату. Дублювати послідовність relock не можна — дві копії,
що розійшлись, означали б зависання, — тож саме параметризація, а не другий двигун.

**Ребут E90, і чому він стався.** Перший прогін нового шляху поклав апарат
миттєво. Причина — рівно один пропущений рядок: `KReadPatch` (r1-варіант)
підставлявся за профілем у `ApplyReadPatch()`, але в `Prepare()` є ДРУГИЙ виклик
накладання того самого патча, і він лишився зі старою константою. На носії Usbc
диспетчер кладе в `r1` опкод, тобто 69, а стаб робить `ldrne r0,[r1]` — читання
за адресою 69 у режимі ядра. Апарат перезавантажився й піднявся сам.

Урок вужчий і корисніший за «будь уважним»: **коли константа стає профільною,
шукати треба ВСІ її входження, а не те, яке трапилось першим**. Тут допоміг би
навіть тривіальний `grep` по імені константи після правки — його й треба робити
правилом.

**Три запобіжники, дописані після цього.**

Перший — `Prepare()` відмовляє, коли в профілі нуль не лише в `iDvfsBody`, а й у
`iRomSramRoutine` чи `iPwrDownGlobal`. Нуль означає «ще не виміряно», і патчити
за нульовою адресою або звіряти SRAM проти нуля — гарантований спосіб покласти
апарат.

Другий — перевірка, що патч ЖИВИЙ, до того як йому вірити. На носії Usbc нуль від
штатного `DoControl(69)` не відрізнити від нуля, прочитаного примітивом, і саме
на цьому колись згубився бутстрап (§34). Тепер `PrepareProbe()` спершу читає
вектор скидання й вимагає `0xea00007e`.

Третій — перевірка відкату більше не кличе ядро. Для `dvfs` вона спиралась на те,
що `DoControl(1,0)` віддає відсоток від номіналу; для `Usbc` такого оракула немає,
а кликати штатний `DoControl(69)` з ненульовим `a1` небезпечно — це реальна
функція драйвера, і що вона зробить із чужим покажчиком, невідомо. Натомість
шість слів тіла звіряються прямим читанням з user mode, бо XIP на цьому апараті
читається (§34). Це сильніший доказ за будь-який непрямий: ми дивимось на самі
байти.

**Регресія на еталоні (2026-09-09, N95 RM-320 по WiFi).** Обидва шляхи цілі.
`patcher dsp` — `engine ready: SRAM @cb202000, stock mult 86`, `CM_CLKSEL_DSP =
0x000023c3`, `restore check -> 50`. `patcher oc 107` — повний записний цикл:
328 → 408 МГц (`RESULT NOP 24.3%`, `ALU 24.4%`, `MEM 24.4%`), пʼять раундів
витримки з нулем зіпсованих слів, повернення на множник 86 зі `status=0`.
Uptime 722 хвилини, апарат не перезавантажувався.

**Стан E90.** Профіль заповнено виміряними адресами (`iDvfsBody = 0x800bf874`,
`iRomSramRoutine = 0x80058da4`, `iPwrDownGlobal = 0xc8003068`, штатна розкладка
з §34.1), код виправлено, але перевірити на апараті не вийшло: після ребуту на
E90 вимкнулись патчі `Open4all`, а без них запис у `E:\sys\bin` віддає `-46`.
Увімкнути їх можна лише руками на самому апараті. Наступний крок, щойно це
зроблено, — `ocprobe patcher dsp e90`: він проганяє весь новий шлях, не пишучи
в PRCM жодного біта.

### 35.1. Штатна шина E90 вдвічі повільніша, і чому це міняє план розгону

Розкодована штатна розкладка двох апаратів при однаковій частоті ядра:

| апарат | CM_CLKSEL1_CORE | l3div | dss1div | CORE | шина L3 | DSS1 |
|---|---|---|---|---|---|---|
| RM-320 | `0x04360644` | 4 | 6 | 660.48 | **165.12** | 110.08 |
| E90 | `0x04360626` | 6 | 6 | 660.48 | **110.08** | 110.08 |

Тобто E90 має те саме ядро на 330.24 МГц, але шину памʼяті на третину нижчу.
Це не дрібниця: компенсатор дільників цілиться в стелю `kL3Max = 213120`, а це
число ВИМІРЯНЕ на RM-320 і означає рівно ту шину, на якій RM-320 працює щодня.
На E90 та сама стеля дозволила б `l3div = 4`, тобто 205 МГц при штатних 110 —
майже вдвічі вище, без жодного заміру. Це майже напевно поклало б апарат.

Виправлено відносною межею замість абсолютної: **дільник L3 ніколи не
опускається нижче штатного для цього апарата**. Наслідків три, і всі бажані.
Шина піднімається рівно в тій самій пропорції, що й ядро, — режим, який на
RM-320 доведений щоденною роботою. Повернення не чіпає дільника L3 взагалі, тож
ми обходимо саме ту операцію, яка на RM-320 тричі валила апарат (§26.12, §26.14,
§26.15). А на самому RM-320 не міняється нічого: там стеля й так дає штатний 4,
що підтверджено повторним прогоном `patcher oc 107` — ті самі `l3div=4 dssdiv=8`
і ті самі 328 → 408 МГц.

Для E90 це означає обережний перший крок: при множнику 107 шина стане 136.96 МГц,
тобто нижчою, ніж RM-320 має ШТАТНО, а дільник лишиться незмінним на 6.

### 35.2. Записний шлях E90: що вже звірено офлайн, а що лишається на апарат

Перед першим прогоном розгону на E90 звірено все, що можна звірити без апарата,
бо кожне неперевірене припущення тут коштує перезавантаження.

Блоб `OcRelockBlob` несе зашитими дві бази регістрів. Обидві підтверджені пулом
самої relock-рутини E90 (`0x80058ed8..0x80058ee4`): `SDRC = 0xC6129000`,
`CM = 0xC6008000`, а поряд `CONTROL = 0xC6014000` і константа DLL `0x770E` —
рівно той самий набір, що й на RM-320. Тобто відображення периферії на E90 те
саме, і правило `+0x7E000000` для вікна `0x48xxxxxx` тут теж діє.

Плацдарм у SRAM: конструктор E90 мапить чанк `mov r2,#4096` і копіює в нього
`mov r2,#1024` байтів процедури — обидва числа ті самі, що на RM-320. Отже
`KSramSlot = 0x800` лягає всередину чанка й не накриває скопійовану прошивкою
процедуру, як і задумано.

Що лишається неперевіреним і перевіряється лише на апараті: сама лінійна адреса
SRAM (резолвиться в рантаймі через `iPwrDownGlobal`), збіг першого слова копії з
ROM (двигун звіряє сам і відмовляє при розбіжності) і, головне, чи витримає
кремній E90 підняття множника. Порядок прогонів — спершу `patcher dsp e90` (жодного запису в PRCM), потім
`patcher oc 95` як перший запис. Саме 95, а не 107: на новому апараті перший
крок має бути найменшим із тих, що взагалі щось доводять. При 95 шина стане
121.6 МГц, тобто на десяту вище штатних 110, а рампа однаково йде по одній
сходинці й зупиняється на першій же відмові. Якщо 95 чистий - далі 107.

## 36. РОЗГІН E90 ДОСЯГНУТО: +29% на другому апараті, перенесення доведене

Nokia E90 (RA-6, 400.34.93) розігнано в рантаймі тим самим двигуном, що й
RM-320. Це перший апарат, доданий до проєкту не переписуванням коду, а
заповненням профілю, і саме тому результат важливіший за самі мегагерци: він
доводить, що метод переносний.

| множник | MPU | шина L3 | вимір | стан |
|---|---|---|---|---|
| 86 штат | 330.24 | 110.08 | 328 МГц, 17.34 Mitr/s, 344 MB/s | — |
| 95 | 364.80 | 121.60 | 362 МГц (+10.3%) | чисто |
| 107 | 410.88 | 136.96 | 408 МГц (+24.3%) | чисто |
| **111** | **426.24** | **142.08** | **423 МГц (+28.9%)** | **чисто** |

Кожен прогін — рампа по одній сходинці, `status=0` на всіх, пʼять раундів
витримки з нулем зіпсованих слів памʼяті, повернення на штатний множник і
контрольний замір, який щоразу давав рівно вихідні 328 МГц. Апарат за всі три
прогони не перезавантажувався: `startTick` лишився тим самим, що й до них.

Три числа масштабуються разом і в одній пропорції — 28.9% на NOP, 29.1% на ALU,
29.3% на памʼяті, — тобто це справжня зміна тактової частоти, а не зсув
показника. Прилад тут той самий, що й на RM-320, і сумніватися в ньому підстав
немає.

**Чого це коштувало, окрім самого множника.** Профіль E90 не має жодного числа,
взятого з голови: хост `0x800bf874`, relock-рутина `0x80058da4` і глобал
power-down `0xc8003068` виміряні сигнатурним сканом живого ROM (§34), а штатна
розкладка прочитана з регістрів (§34.1). Носій примітиву став полем профілю
(§35), а дільник L3 більше не опускається нижче штатного для апарата (§35.1) —
без цієї межі E90 отримав би шину 205 МГц при штатних 110.

**Побічне спостереження про саме залізо.** E90 має те саме ядро на 330.24 МГц,
але штатну шину 110.08 МГц проти 165.12 у RM-320, і це видно в замірі: 344 MB/s
проти 519 на штаті. При цьому стеля розгону ядра в обох однакова — 111 бере
чисто, і в обох випадках упирається не шина, а сам ARM1136. Тобто вужча шина E90
обмежує пропускну здатність, але не заважає ядру йти на ті самі +29%.

Що НЕ перевірено: тривала щоденна робота на 111 (на RM-320 це тиждень
спостережень) і поведінка вище 111. Стелю E90 не шукали свідомо — потреби не
було, а кожна спроба вище коштує перезавантаження.

## 37. Автовибір профілю за апаратом; GUI працює на обох

Застосунок не має командного рядка, тож спосіб, яким пробник обирав профіль
(слово `e90` в аргументах), для нього не годиться. А профіль — це чотири адреси,
які патчаться в ядро: узяти чужий означає покласти апарат.

Профіль тепер добирається за `HAL EMachineUid`:

| апарат | EMachineUid |
|---|---|
| N95 8GB (RM-320) | `0x20002D84` |
| Nokia E90 (RA-6) | `0x20002496` |

Обидва зняті з апаратів, не з документації. Запасного варіанту «не впізнали —
беремо еталонний» свідомо НЕМАЄ: невідомий апарат отримує чесну відмову ще до
будь-якого дотику до ядра. Це не теоретична обережність — перша ж перевірка
спрацювала саме так, бо я помилився, переводячи десяткові значення в
шістнадцяткові, і апарат не впізнався. Замість патча чужих адрес вийшов рядок
у лозі.

Автовибір став типовим і в пробнику. Раніше `patcher oc 111`, запущений на E90
без слова `e90`, узяв би адреси RM-320 — окрема міна, яку цим прибрано; слово
лишилось явним перевизначенням для перевірок.

**Потрібна capability `CommDD`.** На E90 носієм примітиву є драйвер USB-клієнта,
і його `DoCreate` без `CommDD` віддає `-46`. У пробника вона була, у застосунку
ні, тож перша спроба дала `NOT READY (-46)` на цілком справному коді. Додано в
`ocgui.mmp`. Пастка тут не в самій capability, а в тому, що ABLD не перезбирає
ціль після правки `.mmp` — заголовок E32 треба звіряти (`elftran -dump h`), а не
припускати.

**Перевірено на обох апаратах.** E90: `stock m86 CPU 330 BUS 110 DSS 110`,
`CLKSEL1_CORE 04360626`, `BUSDIV /6`, `DSPDIV /3 DSP 220`, двигун готовий.
N95: `stock m86 CPU 330 BUS 165 DSS 110`, `CLKSEL1_CORE 04360644`, `BUSDIV /4`.
Тобто кожен апарат бачить свою розкладку, і жоден — чужу.

Відоме косметичне обмеження: розмітку інтерфейсу зроблено під екран 320 точок
завширшки, тож на 800x352 в E90 вона займає вузьку колонку зліва. Читається, але
місце використано погано.

### 37.1. Латентна вада в `.gitattributes`: `.pkg` віддавався з LF

Знайдено при збірці пакета, а не в роботі: `.gitattributes` описував `*.pkg` як
`text eol=lf`, тобто і в індексі, і **в робочій копії при викачуванні**. А
`makesis` файл із LF мовчки псує — про це прямо сказано в коментарі всередині
самого `ocgui.pkg` і в шапці `tools/build_sis.cmd`.

На цій машині це не спливло лише тому, що робочу копію жодного разу не
перевикачували після появи `.gitattributes`. Свіжий клон отримав би несправний
пакет, і симптом був би саме таким, який найважче звʼязати з причиною: збірка
проходить, підпис ставиться, а пакет поводиться не так.

Виправлено на `*.pkg text eol=crlf`. Перевірено не міркуванням, а дією: файл
видалено, викачано наново з git і перелічено байти — 42 CRLF, жодного самотнього
LF, жодного байта поза ASCII; після цього пакет перезібрано з цієї самої копії.

## 38. Дільники CORE, найпевніше, не записуються; висновок §22 через це втрачає опору

Розділ виправляє §22 і послаблює §26. Джерело — досліди Павла на обох апаратах
(2026-09-09), зроблені вбудованим у GUI бенчмарком пропускної здатності памʼяті.

**Спостереження.** Зміна дільника системної шини не дає жодної зміни швидкості
памʼяті — ні на N95, ні на E90. Дільник дисплея так само не впливає на поведінку
зовнішнього екрана E90: після певного порогу частоти той просто стає чорним, а
нижче порога блимає чорним раз на кілька секунд, і рух `DSS1` цього не змінює.
Внутрішній екран стабільний у всіх режимах.

**Чому це руйнує §22.** Там межу приписано кремнію ядра на підставі
конфігурації з множником 129, у якій «і шина, і дисплей виставлені ТОЧНО на
штатні частоти». Це твердження спиралося на НАМІР запису, а не на читання назад.
Якщо запис відкидався, шина при множнику 129 їхала разом із CORE на
`990.72/4 = 247.68` МГц замість штатних 165.12, і миттєвий ребут пояснюється
шиною, а не ARM1136. Отже висновок «межа — сам кремній MPU» більше не
підтверджений; він не спростований, але й доказу під ним немає.

**Незалежне підтвердження з другого апарата.** E90 бере множник 129 (495 МГц)
без проблем. У E90 штатний `l3div=6`, тож при 129 його шина дає
`990.72/6 = 165.12` МГц — рівно ту частоту, яка в N95 є ШТАТНОЮ. Тобто на одному
й тому самому множнику апарати різняться саме шиною: 165 проти 248 МГц. Це
пряме свідчення на користь того, що обмежує шина, а не ядро, і воно узгоджується
з тим, що E90 з нижчою базовою шиною йде далі.

**Суперечність, яку не замовчуємо.** §26.12 зафіксував прогін `l3=8` при
штатному множнику з результатом `MEM -45.0%`, тобто там дільник ПОДІЯВ. Разом із
спостереженнями вище це означає, що правильне формулювання не «дільники не
працюють ніколи», а «запис у `CM_CLKSEL1_CORE` відкидається мовчки й частіше,
ніж ми думали». Апаратура відкидає ВЕСЬ запис, якщо хоч одне поле недійсне (§26),
а набір, який приймає залізо, вужчий за той, що валідує прошивка. Конфігурація
§22 містила `dss=9` — цілком імовірний кандидат на відмову.

**Вада інструменту, через яку це прожило місяць.** Двигун ніколи не читав
`CM_CLKSEL1_CORE` назад після застосування. Усі логи звітували про те, що ми
збиралися записати, і жоден — про те, що опинилось у залізі. Виправлено: додано
`COcEngine::LiveCore()`, і тепер кожен прогін пробника й кожне `CONFIRM` у
застосунку друкують живий регістр поруч із наміром і вердикт
`DIVIDERS APPLIED` / `DIVIDERS REJECTED`.

**Правило методу (від Павла, прийняте).** Працездатність дільника перевіряється
ВИМІРОМ — вбудованим бенчмарком пропускної здатності памʼяті, — а не рядком у
лозі. Читання регістра назад це доповнює, але не заміняє: регістр може прийняти
значення, а частота — не змінитись. Обидва свідчення мають сходитись.

**Що з цього випливає для планів.** Питання «де межа RM-320» відкривається
наново, і найдешевший дослід тепер інший: не шукати стелю множника, а перевірити,
чи тримає N95 високий множник при шині, приведеній до 165 МГц більшим дільником.
Але виконувати його можна лише після того, як читання назад підтвердить, що
дільник узагалі записується.

### 38.1. Причина знайдена: застосунок не писав розкладку, якщо множник не змінювався

Уточнення Павла звузило пошук вирішально: його спостереження стосуються ШЛЯХУ
ГРАФІЧНОЇ ОБОЛОНКИ, тоді як `MEM -45%` у §26.12 отримано пробником. Отже
суперечності не було — різними були самі шляхи запису.

Застосунок застосовує розкладку єдиним викликом `ApplyRampWithCore()`, а весь
запис у тому методі стоїть усередині циклу

```
while (cur != aTarget) { ... ApplyMultAndCore(cur, ...) ... }
```

Коли користувач міняє САМІ дільники, не чіпаючи множника — а це основний спосіб
ними користуватись, — `cur` уже дорівнює `aTarget`, цикл не виконується жодного
разу, і в залізо не йде НІЧОГО. Зовні це виглядає точно як «дільники не
працюють»: ні шина, ні дисплей не реагують, бо запису не було.

Пробник цього не показував, бо `patcher clocks` після рампи робив ОКРЕМИЙ явний
запис кінцевої розкладки (крок 2) і навіть звіряв його читанням назад. Тобто два
шляхи розійшлися, і саме розбіжність сховала помилку.

Виправлено двома змінами, і друга важливіша за першу.

По-перше, `ApplyRampWithCore()` тепер після циклу робить явний фінальний запис,
коли дільники задані. Запис ідемпотентний: якщо рампа була, остання сходинка вже
поставила ті самі значення.

По-друге, `patcher clocks` більше не має власного шляху запису — він кличе той
самий `ApplyRampWithCore()`, що й застосунок. Тепер прогін пробника є справжньою
перевіркою того, що робить GUI, а не сусідньої реалізації. Дублювання тут і було
справжньою вадою: одна гілка працювала, друга ні, і жоден лог їх не розрізняв.

**Що це означає для попередніх висновків.** Усі спостереження Павла про дільники
пояснюються цією помилкою, і §38 треба читати з поправкою: питання «чи приймає
залізо ці значення» лишається ВІДКРИТИМ, бо через GUI воно жодного разу й не
ставилося. Висновок §22 від цього не відновлюється — там запис теж ніхто не
звіряв читанням назад, — але й не спростовується остаточно.

**Не перевірено на апараті.** На момент правки E90 віддавав `-46` (вимкнені
патчі `Open4all`), а демон N95 не слухав у своїй підмережі, тож вимір
відкладено. Перший прогін після відновлення звʼязку: `patcher clocks mult=86
l3=<стоковий> dss=8` — міняє лише дільник дисплея, для SDRAM безпечний, і
читання назад одразу скаже, чи запис тепер відбувається.

### 38.2. Дільник шини працює на обох апаратах; повертати шину назад — смертельно

Після виправлення §38.1 дільник шини нарешті виміряно тим приладом, який
Павло й назвав єдиним чесним, — інтегрованим бенчмарком пропускної здатності
памʼяті. Обидва апарати дали однозначний результат: дільник **працює**.

```
E90   l3div 6 -> 8:  CPU  0.0%   MEM -21.0%   layout confirmed by read-back
N95   l3div 4 -> 8:  CPU +0.6%   MEM -44.9%   layout confirmed by read-back
```

Розділення доменів тут повне: частота ядра не змінилась ані на E90, ані на N95
(0.6% — це шум вимірювання NOP), тоді як памʼять просіла рівно так, як велить
дільник. Це водночас закриває питання §38 і підтверджує метод: логи про намір
запису нічого не доводили, а два числа поруч доводять.

Розкладка тримається під навантаженням: десять секунд спостереження, нуль
зіпсованих слів у мегабайті SDRAM на обох апаратах, дрейфу немає. Тобто саме
пониження шини — операція чиста.

> ВИПРАВЛЕНО 2026-09-11 (§39): загальний висновок цього абзацу — «підняти шину
> не можна» — неправильний. На E90 шину піднято зі штатної вище штатної, апарат
> вижив і дав +41% у 3D. Правдою лишається сам факт чотирьох смертей і те, що всі
> вони сталися на ПОВЕРНЕННІ шини з уже зниженої.

**Зворотна операція вбиває апарат.** Повернення `l3div` до штатного значення
дало чотири смерті з чотирьох: тричі на RM-320 (§26.12, §26.14, §26.15) і раз
на E90 сьогодні, причому обома шляхами — і повним relock, і легким
`ReassertDividers` без bypass DPLL. Лог щоразу обривається рівно на цьому
записі.

Сьогоднішня смерть E90 заразом **спростувала пояснення §26.15**. Там причину
шукали в губернаторі DVFS, який нібито втручається у вікно bypass. На E90
губернатора немає взагалі, `sel2` весь час дорівнював 2, шина стояла рівно на
82.56 МГц, а підйом був лише в 1.33 раза проти 2 на N95 — і апарат усе одно
загинув. Отже, справа не в губернаторі й не у величині стрибка, а в самій
асиметрії операції: понизити шину можна, підняти — ні.

Практичний висновок простий і його вже втілено в коді. `RestoreStock`
відмовляється піднімати `l3div` назад, ставить прапорець `RestoreNeedsReboot()`
і лишає апарат на зниженій шині — цей стан виміряно як безпечний. Користувачеві
проба й GUI кажуть перезавантажитись, і ребут повертає штатне тактування
гарантовано, бо у флеш не пишеться нічого. Запобіжник живе в рушії, а не в
застосунку: проба раніше ходила повз нього і кликала `ReassertDividers`
напряму зі сталими RM-320, що на E90 було вдвічі неправильно.

Перевірено на апараті: N95 пройшов повний цикл `patcher clocks l3=8 sec=10` до
кінця й **лишився живим** — уперше на цій операції. У логу видно рядок
`BUS LEFT LOWERED ON PURPOSE`, після нього штатний фінальний читанням стану й
`restore check: stock DoControl(1,0) -> 50`, тобто код ядра повернено на місце.

Побічне спостереження з того ж прогону: під час десятисекундної витримки
губернатор N95 перевів `sel2` з 2 на 1, тобто вдвічі понизив CORE (330 МГц
замість 660) і разом з ним шину до 41 МГц. Апарат це пережив. На E90 такого не
буває, що ще раз підтверджує §35.1.

### 38.3. Запобіжник шини стоїть у точці запису, а не лише у відновленні

Відмова піднімати шину в `RestoreStock` закривала тільки один шлях. Той самий
фатальний запис легко зробити й звичайним застосуванням: досить у GUI понизити
шину, а потім повернути дільник назад — це вже не «відновлення», а рядове
`APPLY`, і воно пішло б у залізо без жодного застереження.

Тому запобіжник перенесено в `ApplyMultAndCore` — єдину точку, крізь яку
проходить будь-який запис розкладки. Він не відмовляє в записі: відмова
заблокувала б розгін після будь-якої зміни шини. Він **затискає** поле `l3`
живим значенням, тобто множник міняється як просили, а шина лишається зниженою.

```
E90, живий l3div=8, замовлено l3=6:
  bus clamp: l3 6 -> 8 (raising the bus is 4/4 fatal; reboot for stock)
  layout confirmed by read-back
```

Заразом довелося виправити самі прилади. Проба й GUI звіряли живий регістр із
тим, що ЗАМОВЛЯЛИ, тож свідомий затиск вони показали б як «апаратура відкинула
запис» — прилад брехав би про власну роботу. Тепер обидва порівнюють із
`LastCoreWritten()`, тобто з тим, що двигун справді віддав у залізо, і окремим
рядком кажуть, що затиск стався.

Дільник дисплея на E90 при цьому теж виміряно: `dssdiv` 6 → 8 бере
(`DSS1 110080 → 82560 kHz`, читання назад збігається), і зворотна зміна 8 → 6
теж бере. Тобто цей дільник, як і шинний, працює — питання про мигання
зовнішнього екрана стосується не запису регістра, а поведінки самої панелі.

### 38.4. N95 бере 491 МГц, коли шину тримати нижче штатної

Гіпотеза Павла — що N95 упирався не в кремній, а у власну штатну шину 165 МГц
проти 110 у E90 — підтвердилась першим же прогоном.

При зниженому дільнику (`l3div=8`) апарат пройшов рампу 86 → 129 по одному
кроку без жодного ненульового статусу й витримав 15 секунд навантаження:

```
AFTER : 491 MHz (NOP), 432 MB/s (MEM)
RESULT: CPU 50.1%  MEM 50.5%
SDRAM retention over 10 s: 0 bad words in 1 MB
drift samples: 0
```

Доти стелею N95 було 111 (426 МГц). Тепер це 129 — рівно той множник, який на
E90 працює зі штатними дільниками, і та сама частота 495 МГц.

Числа сходяться, якщо врахувати губернатора. Знімки, зняті в простої, показують
`sel2=1`, звідки формула дає CORE 495 МГц і MPU 248 МГц. Але NOP міряє 491 МГц,
а памʼять дає +50%, і обидва числа збігаються з `sel2=2`, тобто CORE 990.72 МГц,
MPU 495.36 МГц, шина 123.84 МГц. Це та сама розбіжність між знімком і виміром,
про яку йдеться в §12 і §18: під навантаженням губернатор піднімає OPP, а знімок
ловить нижчу. Прилад тут не суперечить сам собі — він міряє два різні моменти.

Тобто робоча шина під час прогону була 123.84 МГц, нижча за штатні 165.12, а
множник — на 18 пунктів вищий за колишню стелю. Обмежувачем була шина.

**Чого ще не зроблено.** Поріг не звужено: невідомо, чи візьме N95 множник 129
при `l3div=6`, тобто при шині рівно 165 МГц, як у E90. Цей дослід потребує
ребуту (піднімати шину в рантаймі заборонено запобіжником), і його варто
зробити першим наступним кроком.

### 38.5. Чому «дільники не працюють»: запобіжник затискає мовчки, а інтерфейс показував намір

Павло повідомив 2026-09-10, що на обох апаратах примусова зміна дільника
памʼяті нічого не дає, а N95 понад множник близько 111 ще й сам піднімає
дільник, не показуючи цього в інтерфейсі. Обидва спостереження правильні, і в
них одна причина — наша власна, свідомо додана поведінка, яку не було видно.

Перше — запобіжник §38.3. `ApplyMultAndCore` затискає поле `l3` живим
значенням, щойно замовлений дільник МЕНШИЙ за той, що стоїть у залізі, бо
менший дільник означає підйом шини, а він убив апарат чотири рази з чотирьох.
Обидва апарати після дослідів §38.2 лишились на `l3div=8` і з того часу не
перезавантажувались, тож будь-яка спроба опустити дільник (тобто підняти шину)
мовчки замінювалась на 8. Ззовні це виглядає рівно як «дільник не працює».
Знімається лише ребутом: після нього шина штатна, і дільник знову керований
униз — до першого підйому в межах сеансу.

Друге — стеля шини в `CompensatedCore`. Дільник підбирається так, щоб шина не
перевищила 213120 кГц, тож на RM-320 при переході з множника 111 на 112
підбір сам переходить `l3div` 4 → 6: `990720/4 = 247680` вже понад стелю. У
режимі auto рядок `BUSDIV` це значення показував, але коли дільник заданий
вручну, показувалось задане, а в залізо йшло затиснуте.

Виправлено в 1.7.0 показом, а не зміною поведінки: рядок `BUSDIV` друкує
`BUSDIV /4 CLAMPED /8` разом із частотою, яку справді дасть
затиснутий дільник; рядок `armed` окремо каже `bus stays /8 clamped`; після
CONFIRM лишається старе порівняння з `LastCoreWritten()`. Сам запобіжник не
чіпали — він тримається на чотирьох смертях і знімається ребутом, а не кодом.

### 38.6. Дільник DSS1 на E90 усунув проблему з зовнішнім екраном

Павло підтвердив 2026-09-10, що зміна дільника дисплея на E90 допомогла. Це
закриває сумнів §38.3: там було виміряно лише те, що запис у поле DSS1 береться
в обидва боки, і лишалось відкритим, чи дає він потрібний ефект на панелі.
Тепер відомо, що дає.

### 38.7. Стелю повзунка піднято 129 → 255

Межа 129 була нашою, а не апаратною: поле множника `CM_CLKSEL1_PLL[21:12]` має
десять біт, крок — 3.84 МГц. 129 обрано колись як рівно +50% від штатних 86,
значення зручне тим, що 129/86 = 1.5 і всі супутні дільники масштабуються
цілим числом.

Піднято на прохання Павла до 255, бо колишня стеля N95 у 111 виявилась шиною, а
не ядром (§38.4), тобто справжня межа кремнію невідома. Вище 129 не перевірено
нічого, і GUI з пробником кажуть про це вголос окремим рядком. Що саме там
може зупинити: захоплення DPLL (безпечно — блоб віддає ненульовий статус і
відкочується сам), кремній при штатній напрузі, шина (вище 129 підбір може
опускати її лише грубими кроками 8 → 12 → 16) і вікно авторефрешу SDRAM, яке
ми лише читаємо й ніколи не компенсуємо: при `l3div=8` воно вже розтягнуте з
7520 нс до 13016–19525 нс.

### 38.8. Запобіжник шини став перемикачем: `BUS GUARD`

Павло повідомив 2026-09-11, що пониження дільника до 4 на E90 усе одно не
працює, а на N95 дільник памʼяті після множника 111 усе одно скидається. Обидва
спостереження правильні, і §38.5 пояснив причину, але не змінив нічого по суті:
показ затиску — це не керування ним. Заборона лишалась абсолютною, а
користувачеві потрібна саме можливість спробувати на власному апараті.

Тому запобіжник зроблено перемикачем, типово ввімкненим. У GUI це окремий рядок
`BUS GUARD: ON / OFF  raising bus died 4 of 4` одразу під `BUSDIV`; у пробнику —
ключ `guard=0` до `patcher clocks`. Вимкнення знімає і затиск у
`ApplyMultAndCore`, і відмову в `RestoreStock`. Це рівно та сама схема, що й
решта небезпечних шляхів проєкту: небезпечне доступне, але лише за явним
вибором, і ніколи за замовчуванням.

Що при цьому лишається правдою і чого перемикач не міняє: підйом шини досі
чотири смерті з чотирьох (§38.2), на двох апаратах і обома шляхами, і жодного
разу шину не було піднято успішно — навіть вище штатної не пробувано взагалі.
Ціна невдачі відома й обмежена: у флеш не пишеться нічого, найгірше — миттєвий
ребут.

Окремо варто тримати в голові, що корисна ціль на N95 при множнику 129 — це
`l3div=6`, тобто рівно штатні 165.12 МГц шини, а не `l3div=4`: четвірка при
CORE 990.72 МГц дала б 247.68 МГц, тобто півтора штатних, чого не пробував
ніхто.

### 38.9. Межа ARM1136 без підйому напруги — близько 500 МГц

Павло назвав цю цифру 2026-09-11 як відому властивість цього процесора. Вона
узгоджується з нашим власним заміром: N95 стабільно тримав 491 МГц при множнику
129 (§38.4), і це фактично впритул до неї. Отже підняття стелі повзунка до 255
(§38.7) саме по собі частоти не дасть — без керування напругою вище 500 МГц
чекати нема на що, і практичний сенс має радше шина, ніж множник.

## 39. ПІДЙОМ ШИНИ ПРАЦЮЄ: E90 на +50% памʼяті дає +41% у 3D

Павло 2026-09-11 вимкнув `BUS GUARD` (§38.8) і підняв частоту памʼяті на E90 на
50%. Апарат вижив, і приріст виявився найбільшим з усього, що цей проєкт міряв:

```
E90, великий екран
  штатно            16.33 fps   пам'ять 339 МБ/с
  шина +50%         23.00 fps   пам'ять 463 МБ/с
  розгін шиною      24.55 fps   пам'ять 509 МБ/с
```

Арифметика сходиться точно й підтверджує, яким саме шляхом це зроблено. Штатна
шина E90 — 110.08 МГц при `l3div=6` і CORE 660.48 МГц (§35.1); `l3div=4` дає
рівно 165.12 МГц, тобто ті самі +50%. Отже піднято дільником, тим самим полем
`L3` у `CM_CLKSEL1_CORE`, і в тому самому напрямку, який досі вважався
смертельним.

**Це виправляє §38.2.** Там записано, що підняти шину не можна взагалі, і
висновок сформульовано як асиметрію самої операції: «понизити шину можна,
підняти — ні». Тепер відомо, що це неправда в загальному вигляді. Що лишається
правдою — усі чотири смерті сталися на ПОВЕРНЕННІ шини з уже зниженої, а не на
підйомі зі штатної; жодна з них не була підйомом вище штату. Тобто вбиває не
напрямок як такий, а щось у переході саме з пониженого стану, і що саме — поки
невідомо. Це здогад, не висновок.

**Головне з результату — не частота, а те, куди впирається апарат.** Приріст
41% у 3D від самої лише памʼяті, при незмінному ядрі, означає, що ARM1136 у 3D
майже повністю обмежений памʼяттю. Це узгоджується з вимірами §38.2, де зміна
дільника шини рухала `MEM` на 21–45%, а `CPU` не рухала взагалі. І це ставить
під сумнів пріоритети проєкту: множник упирається в кремній близько 500 МГц
(§38.9), а шина щойно дала більше, ніж будь-який розгін ядра до неї.

### 39.1. Шкала E90: пропускна здатність іде за шиною майже точно, 3D — слідом

Уточнення від Павла 2026-09-11: 509 МБ/с — це чистий розгін шиною на 50%, без
множника; 463 МБ/с — той самий стан у іншому прогоні. Плюс іще одна точка,
шина +50% разом із множником 105.

```
E90, великий екран        шина       CORE     MPU     МБ/с    fps
  штатно                 110.08     660.48  330.24     339   16.33
  l3div 6 -> 4           165.12     660.48  330.24     463   23.00
  l3div 6 -> 4 (повтор)  165.12     660.48  330.24     509   24.55
  l3div=4 + mult 105     201.60     806.40  403.20     569   28.20
```

**Два середні рядки — це один і той самий стан, зміряний двічі.** Звідси
головне число цієї таблиці, і воно не про частоту: розкид повторних прогонів
однакової конфігурації становить 10% по памʼяті і 6.7% по fps. Причина не
виміряна. Найімовірніший кандидат — контролер дисплея, який ділить ту саму
шину, тож частка, яку він відбирає, залежить і від дільника DSS1, і від того,
що на екрані; це здогад, і перевіряється він окремим прогоном.

Практичний наслідок стосується всього, що ми міряємо далі: одна точка не
розрізняє нічого меншого за 10%, тож будь-яке відхилення такого порядку
потребує повторів, а не пояснення.

Кращий із двох прогонів лягає на пряму точно: шина 1.500x, пропускна здатність
509/339 = 1.501x. Тобто в цьому режимі памʼять — буквально єдине, що міряє
бенчмарк, і жодного іншого обмежувача поруч немає.

**ВИПРАВЛЕНО тут-таки.** У першій редакції цього параграфа я записав, що крок
до 201.6 МГц відстає від прямої на 8% (569 МБ/с замість очікуваних 621) і
пояснив це затримками SDRAM. Це було передчасно: 8% лежить усередині щойно
показаного 10-відсоткового розкиду, тобто відхилення від прямої не доведене
взагалі. Правильне формулювання таке: пропускна здатність іде за шиною лінійно
в межах точності вимірювання, а щоб побачити відхилення, потрібні повтори.

3D іде слідом за памʼяттю майже один до одного: +50% шини дали +50% fps
(16.33 -> 24.55). Наступний крок додав ще 15% fps (до 28.20), але там разом із
шиною росло й ядро (множник 86 -> 105, MPU 330 -> 403 МГц), тож розділити внески
на цій точці не можна: змінено дві речі одразу.

Загальний підсумок по E90 — 16.33 -> 28.20 fps, тобто +73%, і головна частина
цього приросту прийшла від шини, а не від ядра.


## 40. C5-00.2 як вимірювальний прилад; тест кеша міряє не кеш

Перші заміри на C5-00.2 (ARM11 600 МГц з FPU, не OMAP 2420, розгін до нього не
стосується — §38 і вище):

```
C5-00.2   пам'ять 256 МБ/с   ALU 38.2 Mitr/s   кеш 90 МБ/с
```

Павло звернув увагу на те, що кеш виходить повільнішим за памʼять, і що так
виходить на всіх апаратах. Це неможливо фізично, отже помилка в приладі — і вона
знайшлася в самому тесті.

Два тести рахують МБ/с несумісно між собою:

```cpp
// TestMemBandwidth: один дотик на рядок кеша, 64 байти в залік
for (TInt i = 0; i < aWords; i += 16)
    acc += aBuf[i];

// TestCache: два LCG-множення, запис, читання і порівняння на КОЖНІ 4 байти
x = x * KLcgA + KLcgC;
aBuf[i] = x;
...
if (aBuf[i] != x) ++bad;
```

Тобто тест памʼяті на кожні 64 байти виконує одне додавання й один промах у
DRAM — він справді впирається в шину. Тест кеша на ті самі 64 байти виконує
шістнадцять множень у послідовному ланцюжку залежностей плюс шістнадцять
записів, читань і порівнянь. Робочий набір у 4 КБ при цьому лежить у L1 і
коштує майже нічого, тож обмежувачем стає ALU, а не кеш.

Арифметика це підтверджує кількісно. У тесті кеша на одну ітерацію LCG
припадає рівно 4 байти заліку, тож при вимірянних 38.2 Mitr/s стеля цього
циклу — 152.8 МБ/с. Виміряно 90 МБ/с, тобто 23.4 Mitr/s, або 61% від чистої
швидкості ALU; решта припадає на запис, читання й порівняння, яких у тесті ALU
немає. Отже число «кеш 90 МБ/с» повністю пояснюється швидкістю ALU і про кеш не
говорить нічого.

Висновок для методу: порівнювати між собою можна лише ті два тести, які роблять
однакову роботу на байт. Щоб тест кеша справді міряв кеш, його цикл має бути
таким самим, як у тесті смуги памʼяті, і відрізнятись ЛИШЕ розміром робочого
набору — меншим за L1 замість більшого за нього. Поки цього не зроблено, рядок
`CACHE` у застосунку слід читати як другий тест ALU.

Побічне спостереження, поки без пояснення: памʼять C5 (256 МБ/с) повільніша за
штатну памʼять E90 (339 МБ/с), хоча ядро в C5 удвічі швидше. Що це — вужча
шина, інший тип памʼяті чи інші затримки — не міряно.

### 40.1. E90 на 503 МГц дає 37 Mitr/s — рівень C5 при на 100 МГц нижчій частоті

Павло 2026-09-11: на E90 досягнуто 37 Mitr/s в ALU при частоті ядра 503 МГц,
памʼять при цьому 534 МБ/с.

Множник виводиться з частоти однозначно. На E90 `sel2` завжди 2, дільник MPU
штатно 2 (§35.1), тож частота MPU дорівнює множнику, помноженому на 3.84 МГц:
`503 / 3.84 = 131.0`. Отже множник 131, тобто на два кроки вище за стару стелю
повзунка 129 — піднята до 255 межа (§38.7) знадобилась відразу і на практиці, а
не лише на папері.

Памʼять 534 МБ/с узгоджується з `l3div=6` при CORE 1006.08 МГц, тобто шиною
167.68 МГц: лінійна шкала від штатних 339 МБ/с при 110.08 МГц дає 516 МБ/с, а
різниця в 3% лежить усередині виміряного розкиду повторних прогонів (§39.1).
Це узгодження, а не встановлена конфігурація: сам рядок розкладки з того
прогону не записаний.

**Порівняння з C5 цікавіше за саму цифру.** C5-00.2 дає 38.2 Mitr/s при
600 МГц (§40), E90 — 37 Mitr/s при 503 МГц. У перерахунку на такт це 0.064 і
0.074 Mitr/s на МГц відповідно, тобто ядро E90 на цьому циклі приблизно на 15%
продуктивніше за такт. Пояснення не встановлене; тест ALU — це послідовний
ланцюжок залежних множень, тож він міряє затримку конвеєра множника, а не
пропускну здатність, і різні ревізії ARM11 тут цілком можуть відрізнятись.
Альтернативне пояснення, яке не можна відкинути без заміру, — що C5 у момент
заміру не працював на заявлених 600 МГц; за правилом проєкту тому, що
повідомляє система про частоту, віри немає.

Практичний підсумок: розігнаний E90 2007 року в цьому тесті фактично зрівнявся
з помітно новішим апаратом, поступившись лише 3% при на 100 МГц нижчій частоті.

## 41. Тестові профілі для інших OMAP 2420 і пошук глобала на апараті

Раніше (§40 і нижче) профілі для N82 і RM-159 не додавались, бо підагенти
повернули машинні uid без сліду доказів, а «дизасембл» виявився екстраполяцією
зсувом. Це лишається правильним щодо ТИХ чисел. Але сама відмова була ширшою,
ніж треба: частину адрес можна довести з образів, і це зроблено нижче власними
руками, а не звітом підагента.

### 41.1. Що доведено побайтово

Порівняння шести слів за кожною адресою прямо в образах `out/roms/*.rom`:

```
                        RM-320 (еталон)   RM-159        N82
relock-рутина 0x800a7f6c   e92d40fe...    ІДЕНТИЧНО   ІДЕНТИЧНО за +0x10
сеттер DSP    0x800ac59c   e3510009...    ІДЕНТИЧНО   ІДЕНТИЧНО за +0x10
читач множника 0x800b1544  e92d4010...    ІДЕНТИЧНО   ІДЕНТИЧНО за +0x10
тіло dvfs     0x80148410   e92d4010...    РІЗНЕ       РІЗНЕ
```

Отже зсув `+0x10` для N82 стосується коду `power.dll`, і в цих межах він
доведений. На `iDvfsBody` він НЕ поширюється: це окремий модуль, і твердження
підагента про `+0x10` для нього було помилкою.

### 41.2. `iDvfsBody` знайдено сигнатурою, і метод перевірено на відомій відповіді

Тіло `DoControl(1)` шукали за шістьма словами, з яких три беруть як є, а три
(bl, ldr, b) маскують, бо їхні зсуви залежать від розташування. У кожному з
трьох образів знайшовся РІВНО ОДИН збіг на весь 43-мегабайтний файл:

```
rm320  0x80148410   <- збігається з відомою адресою профілю
n159   0x8014b5f0
n82    0x801411e0
```

Те, що на еталонному образі метод точно відтворює відповідь, яку ми знаємо
незалежно, і є підставою вірити двом іншим числам. Шість слів для відкату при
цьому виявились однаковими в усіх трьох образах, тож `KDvfsOriginal` придатний
для всіх.

### 41.3. Глобал power-down офлайн знайти НЕ вдалось, і це важливо

Сигнатура пари геттер/сеттер (`str r0,[r1,#4]` / `ldr r0,[r0,#4]`) дає в усіх
трьох образах пул зі значенням `0xc80030ec`. Але доведений глобал RM-320 —
`0xc80030c8`, тобто сигнатура знаходить СУСІДНЮ пару. Метод не відтворює відомої
відповіді, отже його результати брати не можна, і жодного з цих чисел у профілі
немає.

Натомість адреса шукається НА АПАРАТІ. Двигун проходить вузьке вікно
`орієнтир ± 0x200` і приймає лише ту адресу, ланцюг якої
(`глобал+4 -> обʼєкт -> обʼєкт+16 -> копія SRAM`) дає копію, побайтово тотожну
оригіналу в ROM. Звірку заразом підсилено з одного слова до восьми: одного
замало саме для ПОШУКУ, бо `0xe92d40fe` трапляється в памʼяті часто.

Вікно мале навмисно. Кожна проба — це читання за довільною адресою В РЕЖИМІ
ЯДРА, і непримаплена сторінка коштувала б перезавантаження, а не помилки.

**Механізм перевірено на двох апаратах із відомими відповідями:**

```
RM-320  search -> found=c80030c8  sram=cb202000   MECHANISM OK
E90     search -> found=c8003068  sram=cb102000   MECHANISM OK
```

Обидва рази пошук відтворив саме ту адресу, яку профіль знає незалежно, причому
на різних носіях примітиву (dvfs і Usbc).

### 41.4. Чого тестові профілі НЕ знають і як це закрито

Машинного uid немає, тож автоматично вони не добираються ніколи: у профілі стоїть
нуль, а `ProfileForThisDevice` пропускає все з ознакою `iExperimental`. Вибрати
такий профіль можна лише руками, окремим рядком меню, після двох попереджень.

Версії збірки теж немає: рядка версії в резидентному XIP не виявилось (перевірено
пошуком по образах — його немає й для RM-320, чия версія відома). Тому гейт по
прошивці для цих профілів порожній, і його роль бере на себе звірка ПІДПИСУ
relock-рутини: після накладання READ-патча двигун читає вісім слів за
`iRomSramRoutine` і порівнює з тим, що лежить в образі. Це доводить одразу дві
речі — що патч живий і що адреса показує саме на relock-рутину цієї збірки.

Штатна розкладка тактування невідома, тож для таких профілів опорною точкою стає
те, що застали на старті. Через це апарат мусить бути щойно перезавантажений, і
застосунок каже про це прямо перед спробою.

**Що лишається неусувним ризиком.** Перший запис у `iDvfsBody` відбувається до
будь-якої перевірки — прочитати цю адресу, не пропатчивши її, нічим. Якщо на
апараті стоїть інша збірка, ніж та, з образу якої взято адресу, цей запис ляже
не на той код. Саме тому профіль тестовий, вибір ручний, а попередження пряме.
У флеш при цьому не пишеться нічого, тож найгірше — перезавантаження.

> **Виправлення (§42).** Цей абзац хибний у головному. Твердження «прочитати цю
> адресу, не пропатчивши її, нічим» суперечить §34, де XIP читається прямо з
> режиму користувача, і це там же й виміряно. Отже звірити байти ДО запису
> можна, і тепер саме так і робиться. Ризик не «неусувний», а усунутий.

## 42. Оригінал тіла DoControl знімається з живого ROM, а не береться з константи

При перевірці тестових профілів знайшлася вада, яка не мала стосунку до пошуку
адрес і була гіршою за все, що шукалось. Відкат патча (`RestoreKernelCode`)
записував назад константу `KDvfsOriginal` — шість слів, знятих із RM-320. Але
три з цих шести слів це `bl`, `ldr [pc,#imm]` і `b`, тобто зміщення, унікальні
для конкретної збірки. Для N82 чи RM-159 такий «відкат» записав би в їхнє тіло
чужі зміщення й лишив драйвер зіпсованим до перезавантаження — причому мовчки,
бо сам запис проходить успішно.

Тому оригінал тепер знімається з живого ROM цього апарата перед першим записом
(`CaptureOriginal`) і зберігається в двигуні; відкат іде саме цими словами.
Такий відкат правильний за побудовою для будь-якої збірки.

Та сама операція заразом закрила питання впізнання апарата. Тестовий профіль не
має ні машинного uid, ні гейта по прошивці, тож байти за адресою патча — єдине,
що відрізняє потрібний апарат від будь-якого іншого Symbian-телефона. Звірка йде
тією самою маскою, що й пошук у `tools/romscan.js`: слова 0, 1 і 4 точні, а в
слів 2, 3 і 5 звіряється лише код операції, бо зміщення там і мусять різнитись.
Не збіглося — для тестового профілю це відмова з кроком `verify body`, і в ядро
не пишеться нічого.

Для профілю з гейтом по прошивці розбіжність тлумачиться інакше: там константа
доведено відповідає саме цій збірці, а непослідовність байтів майже напевно є
слідом попереднього прогону, який не встиг відкотитись. У цьому випадку
користується константа, тобто поведінка лишається такою, як була, і апарат
лікується, а не отримує відмову.

Перевірено на N95 8GB 2026-09-11: живі слова за `0x80148410` вийшли
`e92d4010 e3a00001 eb00014c e59f11d0 e8bd4010 ea000135`, тобто точно ті самі, що
в константі; маска зійшлася, відкат підтверджено штатним `DoControl(1,0) -> 100`.
На E90 гілка носія Usbc звіряє всі шість слів точно, бо константа для нього й
була знята з живого ROM (§34); на апараті цей прогін ще не робився.

Заразом закрито дрібніше: патч не накладається взагалі, доки оригінал не знято
(перевірка стоїть у самих `ApplyReadPatch` і `ApplyExecPatch`, а не лише в
`Prepare`), а пошук глобала перевіряє, що підказка з профілю лежить у ядрових
даних і вирівняна — інакше читання пішло б за випадковою адресою в режимі ядра.

## 43. Розгін переживає вихід із застосунку; HAL-кандидати на вимикач автозапуску

### 43.1. Чому розгін скидався при виході

Користувач повідомив (2026-09-11), що після виходу із застосунку розгін
зникає. Це підтвердилось у коді, і причина виявилась не там, де очікувалось.
У двигуні давно є `KeepOnExit`, і деструктор його шанує:

```cpp
if (iApplied && !iKeep && iSram)
    { TUint32 st = 0; RestoreStock(st); }
```

Але GUI цього прапорця не виставляв ніколи, а головне — вихід іде не через
деструктор, а через `COcView::ShutdownL()`, де відновлення стояло безумовно.
Тобто прапорець працював би, та до нього просто не доходило.

Тепер обидва шляхи питають `iKeep`, а сам прапорець винесено в рядок
`KEEP ON EXIT` і типово ввімкнено. Підстава для такого замовчування проста:
частота переживає процес сама по собі, це властивість заліза, а не послуга
застосунку; закрите вікно не є причиною скасовувати те, що людина застосувала
свідомо. Ребут повертає штатне тактування в будь-якому разі.

Зняття патча ядра лишилось безумовним, і це принципово. Частота — стан заліза,
який ребут виправляє; підмінене тіло `DoControl` — міна для будь-якого іншого
клієнта драйвера, і лишати її не можна ні за яких налаштувань.

Побічний наслідок виявився кращим за саме виправлення: зі шляху виходу зникла
єдина справді небезпечна операція. Повернення зниженої шини до штатної вбило
апарат чотири рази з чотирьох (§38.2), і доти кожен вихід із застосунку зі
зниженою шиною робив рівно це.

### 43.2. Що HAL цього апарата знає про живлення й кришку

Для апаратного вимикача автозапуску (`docs/AUTOSTART.md` §7) потрібен сигнал,
який читається без повноважень і не залежить від режиму USB чи наявності
картки. Перевірено три кандидати з HAL, замір на N95 8GB:

```
EPowerExternal = 1
EPowerBatteryStatus -> err -5
ECaseState -> err -5
```

Стан кришки й статус батареї апарат не підтримує (`KErrNotSupported`), тож як
вимикач вони відпадають остаточно. `EPowerExternal` читається штатно.

**Це поки одна точка з двох.** Одиниця не доводить, що атрибут стежить за
кабелем: рівно так само виглядала б стала. Потрібен той самий рядок при
від'єднаному живленні, і до нього це здогад, позначений як здогад.

## 44. E90 підтверджено на апараті: живий ROM, стійкість частоти, шрифти

Дата: 2026-09-12. Апарат — Nokia E90 (RA-6, 400.34.93), транспорт Bluetooth
COM9. Усе нижче зняте з апарата, а не виведене з коду.

### 44.1. Гілка Usbc у `CaptureOriginal` працює, і константа тут була б хибною

`ocprobe patcher hold 96` на E90 прочитав оригінальне тіло `DoControl(69)` з
живого ROM:

```
orig body (6 words, live ROM): e92d4ff0 e24dd044 e1a04000 e1a06002 e1a07001 e3a01000
```

Порівняйте з RM-320, де перше слово `e92d4010`, а третє — `bl`. Тіла різні цілком,
не лише зсувами. Це прямо підтверджує §42: єдина константа відновлення для двох
апаратів була б не «майже правильною», а сміттям, записаним у ядро.

### 44.2. Частота переживає вихід процесу — виміряно

Порядок заміру: `patcher hold 96` (процес застосував і завершився), потім двічі
`patcher engine` — окремими процесами, з інтервалом близько п'яти хвилин
простою апарата.

```
після hold 96, +1 хв : CM_CLKSEL1_PLL = 00060400, m=96   (NOT STOCK AT START)
те саме,       +5 хв : CM_CLKSEL1_PLL = 00060400, m=96
HAL ECPUSpeed        : 368000 (штатно 330000)
```

Отже система сама множник не повертає: ні смерть процесу, ні кілька хвилин
простою його не чіпають. Скарга «після виходу розгін скидається» тому не
пояснюється поведінкою ОС, і причину треба шукати у версії застосунку на
апараті.

**Знайдена причина.** На E90 в `C:\sys\bin\ocgui.exe` лежала збірка на
80 936 байтів проти 101 544 у поточній: апарат мав версію, старшу за рядок
`KEEP ON EXIT` (§43.1), і вона знімала розгін у `ShutdownL()` безумовно.
Свіжий бінарник залито 2026-09-12.

### 44.3. Українські літери в шрифтах апарата є; немає апострофа U+02BC

Команда `ocprobe font` растеризує символ у монохромний bitmap 24×24 через
`CFbsBitGc` і звіряє контрольну суму пікселів із заздалегідь відсутнім
`U+4E00`. Збіг сум означає, що намальовано той самий «квадратик», тобто гліфа
немає. На E90:

```
Nokia Hindi S60:  U+0041 px=19  U+0430 px=14  U+0456 px=9  U+0457 px=11
                  U+0454 px=11  U+0491 px=10  U+02BC MISSING  U+4E00 MISSING
Series 60 ZDigi:  U+0041 px=22  решта MISSING            (цифровий шрифт)
```

Тобто `і`, `ї`, `є`, `ґ` у текстових гарнітурах E90 є і малюються. А модифікаторний
апостроф `U+02BC`, яким у джерелі писалося «пам'ять», гліфа не має в жодній
гарнітурі й виходив квадратиком. У `src/strings.json` він замінений на ASCII
`U+0027` (вісім входжень).

**Чого цей замір не доводить.** Він зроблений на E90, і список гарнітур там
незвичайний (три штуки, дві «Hindi»), бо на апараті стоїть сторонній
`FontZoomerRasterizer`. Для N95 8GB той самий замір ще не робився, і якщо
скарга стосується саме N95, питання про `U+0456` лишається відкритим до
запуску `ocprobe font` на ньому.

## 45. N95: та сама скарга, та сама причина - запускалась стара збірка

Дата: 2026-09-12, Nokia N95 8GB, WiFi.

Апарат зберігає два каталоги з нашим виконуваним. У меню телефон запускає
`C:\sys\bin\ocgui.exe`, і там лежала збірка на **80 936 байтів** - та сама
дореліктова, що й на E90. Учорашня 2.0.1 (**101 544 байти**) поїхала в
`E:\sys\bin\ocgui.exe`, звідки апарат її не запускає. Тобто скарга «розгін
скидається після виходу» стосувалась коду, старшого за рядок `KEEP ON EXIT`.

Свіжий бінарник залито в `C:\sys\bin`, а копію з `E:` видалено: дві копії з
одним UID - готова пастка, і саме вона тут спрацювала. Для майбутніх заливань
правило одне - `ocgui.exe` іде тільки в `C:\sys\bin`.

`ocprobe font` на N95 дав рівно те саме, що на E90:

```
Nokia Hindi S60: U+0456 px=9  U+0457 px=11  U+0454 px=11  U+0491 px=10
                 U+02BC MISSING  U+4E00 MISSING
```

Отже українські літери в шрифтах N95 є, а модифікаторний апостроф `U+02BC`
відсутній і там. Заміна на ASCII (§44.3) закриває питання на обох апаратах.

**Не закрито:** `patcher hold 96` на N95 відпрацював (328 -> 366 МГц, 518 ->
580 МБ/с), але одразу після цього демон перестав відповідати, і повторне читання
множника зробити не вдалося - тобто аналога заміру §44.2 для N95 поки немає.
Апарат лишився на множнику 96; ребут повертає 330 МГц.

## 46. Прилади виміряні самі: рядок кешу, смуга пам'яті, ціна операції

Дата: 2026-09-12, Nokia N95 8GB. Привід - зауваження власника, що смуга пам'яті
(500-600 МБ/с) виглядає завищеною, а тест кеша - незрозумілим.

### 46.1. Рядок кешу має 32 байти, і тест пам'яті через це завищував удвічі

Тест смуги в застосунку обходив буфер кроком 64 байти й рахував прочитані байти
як «читань × 64», тобто за припущенням, що одне читання підтягує рядок у
64 байти. Припущення не перевірялось ніколи.

Перевірка прямим заміром (`ocprobe membench`): якщо крок менший за рядок,
кілька читань ділять один підкачаний рядок, і час на одне читання росте разом
із кроком доти, доки крок не дорівняє довжині рядка; далі кожне читання коштує
окремого промаху, і число виходить на полицю. Прогрітий прогін:

```
stride    4 B:  43.625 ns/read      stride   32 B:  93.597 ns/read
stride    8 B:  63.619 ns/read      stride   64 B:  96.389 ns/read
stride   16 B:  60.882 ns/read      stride  128 B: 101.501 ns/read
                                    stride  256 B: 111.755 ns/read
```

Полиця починається з кроку 32 байти. Отже рядок кешу має 32 байти, як і
належить ARM1136, а не 64. Тест рахував удвічі більше байтів, ніж читав
насправді, тож усі числа смуги пам'яті, що фігурували доти (518-580 МБ/с),
**завищені рівно вдвічі**.

Виправлено інакше, ніж просто заміною сталої: тепер читається КОЖНЕ слово, а в
байти йде розмір буфера, тож припущення про рядок з обчислення зникло взагалі.

### 46.2. Справжні числа пам'яті

Суцільне читання й запис 4 МБ, цикл розгорнутий на вісім (у згорнутому вигляді
замір упирався у власні лічильник і перехід, а не в пам'ять):

```
seq read  4 MB: 199 MB/s
seq write 4 MB: 403 MB/s
cache read 4 KB (в межах L1): 541 MB/s
```

Шина в цьому прогоні стояла на 165 МГц (`l3div=4`), тобто теоретична стеля
32-розрядної SDRAM - близько 660 МБ/с. Виміряні 199 МБ/с на читання - це 30%
стелі, що для одноконвеєрного ядра без попередньої вибірки очікувано: наступний
промах не починається, доки не завершився попередній.

Перший прогін після виділення буфера систематично вдвічі повільніший за
наступні (39855 проти 20996 мкс). Причина - губернатор DVFS: він піднімає OPP
лише побачивши роботу. Тому замір без розігріву не має сенсу.

### 46.3. Тест кеша міряв арифметику, а не кеш

Доти під назвою «кеш» крутився генератор LCG із записом і звіркою кожного слова.
На одне слово припадало множення, додавання і порівняння, тобто число говорило
про АЛУ, і з тестом пам'яті не порівнювалось у принципі. Тепер там рівно той
самий цикл, що й у тесті пам'яті, з єдиною відмінністю - робочий набір 4 КБ
влазить у L1 (16 КБ). Два числа стали порівнянними, і їхнє відношення (541 проти
199 МБ/с, тобто 2.7 раза) має фізичний зміст.

### 46.4. Ціна операції в тактах

`ocprobe alubench`: кожне ядро написане асемблером із `.rept`, тож кількість
інструкцій на ітерацію відома точно, а частота береться з незалежного
NOP-заміру. Прогін при 421 МГц:

```
add dep    : 1.04 cycles/op      залежний ланцюг додавань
add indep  : 1.03 cycles/op      незалежні додавання
mul dep    : 4.94 cycles/op      залежний ланцюг множень
eor+lsr dep: 1.99 cycles/op      виключне АБО зі зсувом
lcg mul+add: 2.98 cycles/op      пара mul+add, тобто 5.96 такту на пару
```

Три висновки. Ядро одноконвеєрне: залежний і незалежний ланцюги додавань дають
однакову одиницю, тобто паралелізму на рівні інструкцій тут немає. Множення
коштує близько 5 тактів затримки, і пара `mul+add` складається рівно з цих п'яти
плюс один. Операнд зі зсувом додає такт.

Це пояснює й старе число тесту АЛУ. Ітерація LCG коштує близько 6 тактів, тобто
при 328 МГц стеля була б близько 55 Mitr/s, а тест показував 17.34. Різницю
з'їдають лічильник циклу й перезавантаження констант, згенеровані компілятором:
число міряло цикл на C, а не арифметику. Тому в застосунок додано два прямі
показники - абсолютна частота NOP-ланцюгом і такти на операцію ядром LCG в
асемблері.

## 47. Образ прошивки не дає адрес для E90, N93 і N93i; сканер живого XIP дає

### 47.1. Зсув у файлі не дорівнює адресі, і це виміряно

Для RM-320, RM-159 і N82 витягнутий образ є повним лінійним XIP, і адреса
дорівнює `0x80000000 + зсув`. Для E90, N93 і N93i - ні: образ є уламком
(1.8, 1.1 і 1.3 МБ проти майже 20 МБ живого XIP на апараті).

Різниця для E90 вимірюється прямо. Пролог `DLddUsbcChannel::DoControl` лежить в
образі за зсувом `0x94ac4`, тобто лінійна мапа дала б `0x80094ac4`. На апараті
та сама функція стоїть за `0x800bf874`. Розбіжність - `0x2adb0`.

Тому для таких апаратів офлайнові константи недійсні **в принципі**, а не «поки
не перевірені». Жодного числа для N93 і N93i з їхніх образів брати не можна.

### 47.2. Сканер живого XIP відтворює обидві відомі відповіді

Замість констант профіль може шукати адреси сам, скануванням живого XIP із
користувацького режиму (безпечність цього шляху - §34). Шукаються дві
сигнатури: пролог `DLddUsbcChannel::DoControl` (чотири слова) і relock-рутина
`power.dll` (вісім слів, із яких два - `ldr` із PC-відносним зсувом, тож ідуть
по масці). Збіг мусить бути рівно один: два збіги означають, що сигнатура не
розрізняє потрібну функцію.

Метод перевірено на двох апаратах, де правильні відповіді відомі незалежно
(`ocprobe romfind`):

```
E90 : body 0x800bf874  relock 0x80058da4   - обидві збігаються з профілем
N95 : body 0x8010bd04  relock 0x800a7f6c   - relock збігається з профілем,
                                             body збігається зі зсувом в образі
```

На N95 збіг подвійний і показовий: образ RM-320 лінійний, тож знайдена на
апараті адреса тіла мусила дорівнювати зсуву `0x10bd04` в образі - і дорівнює.

### 47.3. Профілі N93 і N93i

Додано `RM-55 N93 (TEST, auto)` і `RM-156 N93i (TEST, auto)` з порожніми
адресами й прапорцем пошуку. Драйвера `dvfs` у прошивках цих апаратів немає
жодної версії (скан по шести образах), тож носієм примітиву стоїть `Usbc`, як
на E90.

**На залізі не перевірені жодного разу.** Автоматично не добираються: машинний
uid нуль. Якщо сканер не знайде сигнатури або знайде двічі, двигун зупиняється
на кроці `EOcStepDiscover` і в ядро не пише нічого.

Чого чекати чесно. Пролог `DoControl` в уламку образу N93 не трапився взагалі,
тобто драйвер USB там або іншої збірки, або лежить у стисненій частині, якої в
уламку немає. Relock-рутина в уламку N93i знайшлася, в уламку N93 - ні. Тож
ймовірність, що на живому апараті знайдуться обидві сигнатури, невідома, і
профіль існує рівно для того, щоб власник апарата це з'ясував і повернув
результат.
