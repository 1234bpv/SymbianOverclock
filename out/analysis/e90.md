# E90 (RA-6, 400.34.93) — офлайн-адреси тактування

Образ `out/roms/e90.rom` (нестиснутий XIP `SOS+UPDAPP`, 0x1b0000, база 0x80000000).
Реєстр множника `CM_CLKSEL1_PLL = 0xc6008540` — пул `0x800b76dc` (та ще
`0x800580e0`, `0x8005eba8`). Дві адреси профілю виведено з коду й звірено з
еталоном RM-320 (`rm320-reference.md`).

## iRomSramRoutine = 0x80056874 (ПІДТВЕРДЖЕНО)

Байт-у-байт та сама рутина, що RM-320 `0x800a7f6c`:

```
80056874: e92d40fe  stmdb sp!, {r1,r2,r3,r4,r5,r6,r7, lr}
80056878: e59f1128  ldr r1, [pc, #296]
80056880: e3a03000  mov r3, #0
80056884: ee073f9a  mcr 15, 0, r3, cr7, cr10, {4}     ; барʼєр
80056888: e5914070  ldr r4, [r1, #112]
8005688c: e3844048  orr r4, r4, #72                   ; 0x48
80056890: e5814070  str r4, [r1, #112]
```

## iDspSetter = 0x80059aa4 (ПІДТВЕРДЖЕНО)

Той самий валідатор дільника (cmp проти 9/16/18, mvn r0,#5), а дія збігається з
RM-320: маска `0x1f` (біти [4:0]). Поряд є близнюк `0x80059b1c` з маскою `0x1f00`
(біти [12:8]) — це ІНШЕ поле, не наш setter.

```
80059aa4: e3510009  cmp r1, #9
80059aa8: e92d4010  stmdb sp!, {r4, lr}
80059ac4: e3510010  cmp r1, #16
80059ac8: 13510012  cmpne r1, #18
80059ad0: e3e00005  mvn r0, #5
...
80059adc: e59f032c  ldr r0, [pc, #812]  ; пул
80059ae0: e3a0101f  mov r1, #31          ; 0x1f - маска DSP-дільника (як RM-320)
80059ae4: eb00157e  bl 0x8005f0e4
```

## iPwrDownGlobal = 0xc8004194 (ПІДТВЕРДЖЕНО, на доказах)

Знайдено чисту пару геттер/сеттер контролера живлення в power-зоні E90:

```
8005ebe8: e59f1010  ldr r1, [pc, #16]   ; = 0xc8004194
8005ebec: e5810004  str r0, [r1, #4]    ; global+4 = obj  (сеттер)
8005ebf0: e12fff1e  bx lr
8005ebf4: e59f0004  ldr r0, [pc, #4]    ; = 0xc8004194
8005ebf8: e5900004  ldr r0, [r0, #4]    ; повертає [global+4] = obj  (геттер)
8005ebfc: e12fff1e  bx lr
8005ec00: c8004194  <- пул
```

Це точний аналог того, що читає двигун: `[iPwrDownGlobal+4] -> obj`, далі
`[obj+16] -> sram` (init-конструктор ставить `[obj+16]` на 0x800587d0, структура
байт-у-байт як RM-320 0x800ab2c0). Отже E90 `iPwrDownGlobal = 0xc8004194`.

## iDvfsBody = 0 (процесорного dvfs немає)

E90 не має `dvfs_interface` (рядки «dvfs» у XIP — про дисплей). `iRead` для E90
не `EReadDvfs`.

## Підсумок офлайну E90: три з чотирьох полів готові

| поле | значення | статус |
|---|---|---|
| iRomSramRoutine | 0x80056874 | підтверджено, як RM-320 |
| iDspSetter | 0x80059aa4 | підтверджено, маска 0x1f як RM-320 |
| iPwrDownGlobal | 0xc8004194 | підтверджено геттером/сеттером |
| iDvfsBody | 0 | dvfs немає |
| множник CM_CLKSEL1_PLL | 0xc6008540 (пул 0x800b76dc) | SoC-рівень, як усі |

Лишається один елемент — примітив ЧИТАННЯ для резолвінгу SRAM у рантаймі. За
рішенням користувача — бутстрап через примітив ЗАПИСУ (`patcher.ldd`): на апараті
пропатчити крихітний kernel-стаб, що прочитає ланцюг
`0xc8004194+4 -> obj -> obj+16` і поверне адресу SRAM. Далі повний WRITE-шлях E90
працює як на RM-320. Треба ще знайти користувацьки-доступну функцію E90, тіло якої
безпечно тимчасово пропатчити як виконавця стаба (аналог того, як dvfs DoControl
слугував цьому на RM-320).
