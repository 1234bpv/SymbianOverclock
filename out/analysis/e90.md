# E90 (RA-6, 400.34.93) — Offline Clocking Addresses

Image `out/roms/e90.rom` (uncompressed XIP `SOS+UPDAPP`, 0x1b0000, base 0x80000000).
Multiplier register `CM_CLKSEL1_PLL = 0xc6008540` — pool `0x800b76dc` (as well as
`0x800580e0`, `0x8005eba8`). Two profile addresses were derived from code and verified against
the RM-320 reference (`rm320-reference.md`).

## iRomSramRoutine = 0x80056874 (CONFIRMED)

Byte-for-byte the exact same routine as RM-320 `0x800a7f6c`:

```
80056874: e92d40fe  stmdb sp!, {r1,r2,r3,r4,r5,r6,r7, lr}
80056878: e59f1128  ldr r1, [pc, #296]
80056880: e3a03000  mov r3, #0
80056884: ee073f9a  mcr 15, 0, r3, cr7, cr10, {4}     ; barrier
80056888: e5914070  ldr r4, [r1, #112]
8005688c: e3844048  orr r4, r4, #72                   ; 0x48
80056890: e5814070  str r4, [r1, #112]
```

## iDspSetter = 0x80059aa4 (CONFIRMED)

The exact same divider validator (cmp against 9/16/18, mvn r0,#5), and the action matches
RM-320: mask `0x1f` (bits [4:0]). Nearby there is a twin `0x80059b1c` with mask `0x1f00`
(bits [12:8]) — this is ANOTHER field, not our setter.

```
80059aa4: e3510009  cmp r1, #9
80059aa8: e92d4010  stmdb sp!, {r4, lr}
80059ac4: e3510010  cmp r1, #16
80059ac8: 13510012  cmpne r1, #18
80059ad0: e3e00005  mvn r0, #5
...
80059adc: e59f032c  ldr r0, [pc, #812]  ; pool
80059ae0: e3a0101f  mov r1, #31          ; 0x1f - DSP divider mask (like RM-320)
80059ae4: eb00157e  bl 0x8005f0e4
```

## iPwrDownGlobal = 0xc8004194 (CONFIRMED, on evidence)

A clean getter/setter pair of the power controller was found in the E90 power zone:

```
8005ebe8: e59f1010  ldr r1, [pc, #16]   ; = 0xc8004194
8005ebec: e5810004  str r0, [r1, #4]    ; global+4 = obj  (setter)
8005ebf0: e12fff1e  bx lr
8005ebf4: e59f0004  ldr r0, [pc, #4]    ; = 0xc8004194
8005ebf8: e5900004  ldr r0, [r0, #4]    ; returns [global+4] = obj  (getter)
8005ebfc: e12fff1e  bx lr
8005ec00: c8004194  <- pool
```

This is the exact analogue of what the engine reads: `[iPwrDownGlobal+4] -> obj`, then
`[obj+16] -> sram` (the init constructor sets `[obj+16]` to 0x800587d0, structure
is byte-for-byte like RM-320 0x800ab2c0). Therefore E90 `iPwrDownGlobal = 0xc8004194`.

## iDvfsBody = 0 (No CPU DVFS)

E90 does not have `dvfs_interface` ("dvfs" strings in XIP are for display). `iRead` for E90
is not `EReadDvfs`.

## E90 Offline Summary: Three of Four Fields Ready

| field | value | status |
|---|---|---|
| iRomSramRoutine | 0x80056874 | confirmed, like RM-320 |
| iDspSetter | 0x80059aa4 | confirmed, mask 0x1f like RM-320 |
| iPwrDownGlobal | 0xc8004194 | confirmed by getter/setter |
| iDvfsBody | 0 | no dvfs |
| multiplier CM_CLKSEL1_PLL | 0xc6008540 (pool 0x800b76dc) | SoC-level, like all |

There remains one element — the READ primitive for runtime SRAM resolving. By
user decision — bootstrap via the WRITE primitive (`patcher.ldd`): on the device,
patch a tiny kernel stub that reads the chain
`0xc8004194+4 -> obj -> obj+16` and returns the SRAM address. After that, the full E90 WRITE path
works as on RM-320. It is still necessary to find a user-accessible E90 function whose body
is safe to temporarily patch as the stub executor (analogous to how dvfs DoControl
served this purpose on RM-320).
